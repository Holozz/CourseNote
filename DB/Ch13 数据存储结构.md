## 1. 从表到文件、页和记录

### 1.1 存储层次与基本假设

数据库可以存储为文件集合；一个文件由记录组成，每条记录由字段组成。关系模型中的元组与存储记录相对应，但它们不必在所有实现中一一映射到固定的物理字节布局。

课件先讨论一个简化模型（P2–P3）：

- 一种文件只存一种类型的记录，不同关系使用不同文件。
- 每条记录长度固定，且记录小于一个块。
- 后续放宽定长和单关系文件的假设。

> [!note] 定位对象
> **字段**保存属性值，**记录**组织一行的数据，**页 / 块**容纳多条记录并作为 I/O 单位，**文件**组织多个块。逻辑表如何映射到文件属于物理设计问题。

### 1.2 定长记录的定位和删除

设记录长 $n$ 字节、编号从 1 开始，不考虑页边界时，第 $i$ 条记录从偏移 $n(i-1)$ 开始。此法计算简单，但记录可能跨越两个块，需要访问两个块才能读取。

**避免跨块**：每个块内最多放 $\lfloor B/n\rfloor$ 条（$B$ 为可供记录使用的字节数），剩余空间不用。真实页通常还包含页头、对齐或其他开销，不能把整页都算给记录。

P4–P6 给出三种删除方式：

| 方法 | 删除后的变化 | 好处与代价 |
|---|---|---|
| 后续记录前移 | 删除位置后面的记录依次补位 | 保持物理顺序，但可能移动大量记录，位置引用需要处理 |
| 末条记录补位 | 末尾记录搬到被删位置 | 通常只需移动一条，但改变顺序和该记录的位置 |
| 空闲链表 | 不移动其他记录，将空槽串成链 | 插入时复用空槽；需维护空闲链，遍历可能包含空槽 |

例如 P5 将最后的 Kim 记录移入已删除的 record 3；这是一种**位置复用方式**，不表示 SQL 结果自动按原顺序返回。固定记录不移动也可能因为其他操作、重组或实现策略发生位置变化。

## 2. 变长记录与槽式页

### 2.1 变长字段如何定位

变长记录的来源（P7）包括：一个文件混合多种记录类型、字段为 `varchar` 等变长类型，或某些旧模型允许重复字段。

课件的记录布局将属性按约定顺序存放：定长部分中的每个变长字段使用固定大小的 **`(offset, length)`** 描述实际数据的位置与长度，实际变长数据放在定长部分之后。`NULL` 用位图区分；位图中某位对应哪个字段、1 代表什么由实现约定。`NULL`、空字符串和长度为 0 的非空值不能一概当成相同值。

例如一条记录 `(ID, salary, name)` 可示意为：

```text
记录头 / NULL 位图 | ID | salary | name 的 (偏移, 长度) | name 实际字节
```

偏移与长度要按实现规定的基准和字节编码解释；字符数不一定等于字节数。字段内容增长时，后续数据的位置可能变化，不能仅靠固定字节偏移找到所有字段。

### 2.2 槽式页与稳定的记录标识

> [!note] 槽式页（slotted page）
> 页头维护记录槽位目录：包括槽位数量、空闲空间边界，以及每个槽对应记录的位置和长度。记录实体可在页内移动；移动后更新槽位，外部引用通过“页标识 + 槽号”间接找到记录。

```text
页首                                                        页尾
| 页头 | 槽 0 | 槽 1 | 槽 2 |       空闲空间       | 记录实体 |
          |       |                                    ↑
          └───────┴──────────── 位置和长度 ────────────┘
```

**为什么多这一层？** 删除一条记录后可能留下洞。整理页时将其他记录移动，使记录之间不留空洞，再更新对应槽中的偏移；页号和未重新分配的槽号不变，引用仍能通过槽目录找到该记录，而不必逐一修改指向原字节位置的引用。

- 删除时可将槽标为未使用；具体是否保留槽、何时复用、是否增加代数编号因实现而异。
- 页内整理不等于全局位置永久稳定：跨页移动、槽位复用、记录删除都可能要求额外机制维护或重新解析引用。
- 目录和记录都需要占空间；总空闲字节足够时，仍要考虑目录开销与是否需要整理。

### 2.3 大对象如何存储

课件简化模型要求一条记录小于一个页，但 BLOB / CLOB 可能非常大（P9）。常见思路：

1. 放在文件系统文件中，记录保存引用。
2. 放在 DBMS 自己管理的文件或独立存储区域。
3. 拆为多个片段，放在独立关系的多条记录中，按标识和顺序重组。

课件提到 PostgreSQL TOAST 作为例子：大值可按实现规则压缩或移出主表行保存；不应理解为所有大对象都必然以同一方式存储。具体阈值、事务、恢复与清理机制依系统实现而异。

## 3. 文件组织与表分区

### 3.1 堆文件和空闲空间映射

**堆文件（heap file）**将记录放在有足够空闲空间的页中，不要求按搜索键排序。记录分配后通常不移动，但这不是不可移动的保证。插入时关键问题是：**怎样不用扫描所有数据页就找到可能放得下的页？**

课件的**空闲空间映射（free-space map）**为每个页设置一个小条目，记录空闲比例的近似值（P11）。示例每页用 3 bit，数值除以 8 表示空闲比例的量化值，如 4 表示约 $4/8$；可用值为 0–7，量化和舍入细节依实现。

还可建立第二层，每项记录第一层连续 4 项的最大值。P11 的第一层条目为：

```text
第一层： 4 2 1 4 | 7 3 6 5 | 1 2 0 1 | 1 0 5 6
第二层：    4     |    7    |    2    |    6
```

若需要约 $6/8$ 页的空间，先看第二层可跳过最大值不足 6 的组，再检查候选组中的页，最终以**数据页的实际可用空间**为准。映射会周期性持久化，某些值可能过时；试插入或检查发现不符时修正，再找其他页。粗略摘要缩小搜索范围，不保证候选页一定能容纳当前记录。

### 3.2 顺序文件、溢出块和重组

**顺序文件**按搜索键组织记录，适合按键顺序处理整个文件（P12–P13）。初始布局可将键相近的记录放在相邻物理位置，并用指针链维持逻辑次序。

- **删除**：调整相关指针，跳过删除的记录；空位可供后续复用。
- **插入**：先定位应有的键顺序位置；原位置有空间则插入，否则放在溢出块，再调整指针链使逻辑次序正确。
- **重组**：溢出块积累后，逻辑相邻记录可能不再物理相邻；定期重排可改善顺序访问，但需要额外时间和 I/O。

例如键序列 `10 → 20 → 30` 中插入 `25`：若原页已满，把 25 写入溢出块，再让指针变为 `20 → 25 → 30`。**逻辑有序不等于物理连续**；即使底层有序，SQL 查询需要结果顺序时仍应指定 `ORDER BY`。

### 3.3 多表聚簇

**多表聚簇文件组织**将多个关系的相关记录放在同一文件，尽可能使经常一起访问的记录靠近（P14–P15）。以课件的 `department` 与 `instructor` 为例，布局可为：

```text
Comp. Sci. 院系记录
  Srinivasan 教师记录
  Katz 教师记录
  Brandt 教师记录
Physics 院系记录
  Gold 教师记录
```

查询一个院系及其教师、或按院系连接两表时，相关记录可能落在较少的块中，减少 I/O；只扫描 `department` 时，教师记录反而占用块空间，可能更慢。多表记录结构不同，会形成变长或不同类型记录；还可维护同一关系记录的指针链以支持单表扫描。

这是**物理共置**，不是把两个关系逻辑上合并为一张表；也不能保证任何连接条件都因此受益。

### 3.4 哈希、B+ 树与分区

| 组织方式 | 查找和布局的核心思路 | 本章边界 |
|---|---|---|
| 哈希 | 对搜索键计算哈希值，决定记录所在桶 / 块 | 适合等值定位的直觉；冲突、扩容和具体性能需看实现 |
| B+ 树文件组织 | 按键组织并支持动态插入、删除下的有序访问 | 具体结构和算法留待后续章节 |
| 表分区 | 同一逻辑关系的记录按规则放入分别存储的分区 | 与索引、物理文件组织不是同一概念 |

例如将 `transaction` 按年份分为 2018、2019 等分区（P16）。查询全表可能要访问所有相关分区；条件能证明 `year = 2019` 时，系统可能只访问 2019 分区，称为**分区裁剪**。能否裁剪依分区规则、谓词形式和优化器能力；有分区不保证每个查询只读一个分区。

分区可将空闲空间管理等操作限制在较小范围，也能让不同分区位于不同设备，例如当年数据放 SSD、较早数据放磁盘；仍需考虑数据分布与查询模式。

## 4. 数据字典与系统元数据

**数据字典 / 系统目录（catalog）**保存描述数据库自身的元数据（P17–P18）：

| 类别 | 内容示例 |
|---|---|
| 关系与属性 | 表名、属性名、数据类型、长度、属性顺序 |
| 逻辑对象 | 视图定义、完整性约束 |
| 用户与权限相关信息 | 用户、账户和认证相关信息 |
| 统计信息 | 关系元组数量等，供管理和优化使用 |
| 物理信息 | 文件组织方式、存储位置、索引名称与定义 |

课件图示可将元数据存成关系，例如 `RelationMetadata`、`AttributeMetadata`、`IndexMetadata`、`ViewMetadata` 和 `UserMetadata`，通过关系名等字段关联；也可在内存中建立专门的数据结构以便快速访问。图中的密码字段属于概念示意，实际系统应采用安全认证和凭据保护机制，不能据此推断明文存储。

## 5. 缓冲池：从请求到写回

### 5.1 缓冲管理器的工作流程

**缓冲池（buffer pool）**是主存中缓存磁盘页副本的区域；**缓冲管理器**负责管理这些页和空闲帧。保留常用页可以减少磁盘与内存间的数据传输（P19–P20）。

一次请求的概念流程：

1. 根据页标识查找缓冲池映射；若**命中**，取得对应内存帧。
2. 若**未命中**，寻找空闲帧；没有空闲帧时选择一个可驱逐的帧。
3. 被选中的页若已修改，按系统恢复和写回规则处理；必要时先写出脏页。干净页无需因驱逐而重新写盘。
4. 将所需页读入该帧，更新映射，然后返回可访问该页的引用。
5. 使用完毕后释放相应固定和锁，使该帧有机会再次被替换。

实际实现还需协调并发加载、读写错误等；上述流程展示本章核心机制，不声称所有实现的步骤完全相同。

### 5.2 脏页、固定与并发保护

| 概念 | 回答的问题 | 核心规则 |
|---|---|---|
| 脏页（dirty page） | 内存页是否比其持久化副本更新？ | 已修改页在安全驱逐前需按恢复协议处理和写回；写回也可提前进行 |
| 固定（pin）和 pin count | 当前是否有人持有该帧、不能被替换？ | 每次使用增加计数，完成后减少；通常只有计数为 0 才可驱逐 |
| 页级共享 / 排他保护 | 并发线程能否同时访问或修改页内容？ | 多个共享可并存；排他与其他共享 / 排他互斥 |

P21 将 pinned block 描述为“不允许写回磁盘”，但同页后文的 pin count 又明确用于控制**驱逐**。这里采用通常的缓冲池语义：**固定保证帧不被替换；是否可以在固定时把页刷盘取决于实现和并发协议**。不要从 pin 推出脏页绝不可能被写回。

读取、更新或页内重组期间，固定防止帧被替换；共享 / 排他保护防止并发操作看到不一致的页内容，或同时改变相同结构。它们解决不同问题：pin count 不等于锁，也不直接等于事务级的行锁。课件称 shared / exclusive locks；一些实现会用短期 latch 等机制保护内存结构，命名依系统而异。

### 5.3 替换策略与访问模式

当没有空闲帧时，从**可驱逐**的候选中选牺牲页：

- **LRU**：淘汰最久未使用页，利用近期访问预测未来；顺序扫描大文件可能把有用热页挤出。
- **MRU**：淘汰最近使用页。某些重复循环扫描的模式下，刚处理完的页在下一轮最晚再次需要，MRU 可能优于 LRU；并非所有负载都如此。
- **toss-immediate**：确定某页的最后一条记录已处理且后续无需它时，尽快释放该页占用的空间；须依赖执行计划对访问的判断。
- **混合策略 / 提示**：优化器或执行器提供访问模式信息；频繁访问的数据字典页可被给予较高保留优先级。

例如嵌套循环连接对外表每条记录扫描一次内表：当内表循环访问序列大于可用缓冲帧时，LRU 可能在下轮用到某页前就把它逐出。能否改善取决于循环顺序、页数和可用帧；不是“连接一律不用 LRU”。

### 5.4 写入顺序、强制输出和日志

操作系统或缓冲管理器可能重排写入。若页 A 保存指向页 B 的指针，却先持久化 A、尚未持久化 B 就断电，磁盘结构可能不一致。文件系统可以检查一致性；控制写入次序、记录日志和恢复协议可减少或修复此类问题（P23–P24）。

- **强制输出（forced output）**：按恢复协议要求把指定块写到持久存储；何时视为持久、是否经过缓存与刷写屏障取决于系统。
- **非挥发写缓冲**：先将写入可靠记录在非挥发 RAM 或闪存缓冲，再择机整理并写入目标位置；电源保护和故障模型决定其保证。
- **日志盘 / 日志文件**：顺序追加更新日志，减少随机定位；日志和恢复规则让系统在故障后能够处理未完成的更新。
- **日志式文件系统（journaling）**：按其协议记录相关更新，再落实到原位置。课件强调有序日志可避免某些重排导致的不一致；不能推断所有文件系统都会把全部用户数据以相同方式记录。

> [!note] 补充：预写日志
> 典型数据库恢复协议要求相关日志先于对应脏数据页持久化（write-ahead logging，WAL）；事务提交与日志刷写的具体保证由系统和配置决定。**写回一个数据页不等于事务已经提交**，事务原子性、持久性与页替换需要恢复协议配合。

## 6. 行式、列式与内存数据库

### 6.1 行式与列式如何排列

假设教师表如下：

| ID | name | dept | salary |
|---|---|---|---:|
| 101 | Lin | CS | 60 |
| 102 | Wu | Math | 80 |
| 103 | Chen | CS | 70 |

**行式**将同一行的字段靠近：`(101, Lin, CS, 60) → (102, Wu, Math, 80) → …`；**列式**分别组织各列：`ID: 101, 102, 103`；`dept: CS, Math, CS`；`salary: 60, 80, 70`。图是概念示意，真实编码可能分块、压缩，并附有行位置或其他对应信息。

若只统计 salary，列式可只读相关列；若要读取某人的全部属性，需要把对应列的值重新组合。不同列之间必须有位置或标识等对应关系，不能把不同记录的字段随意拼接。

### 6.2 列式的收益和代价

| 列式的潜在收益 | 原因 |
|---|---|
| 读少量列时降低 I/O | 可跳过无关属性；实际仍受元数据、过滤列和文件粒度影响 |
| 改善 CPU 缓存利用 | 同类型、相邻的目标值聚集，减少无关字段进入缓存 |
| 提高压缩效果 | 同列类型和数值分布相近，可能适合字典、游程等编码 |
| 向量化处理 | 一批相同类型的值可用批处理 / SIMD 等方式执行运算 |

代价包括从多个列重构元组、删除或更新时协调列数据、压缩与解压的成本。具体成本依布局、编码、缓冲和工作负载变化；并不是所有操作都必须先完全解压。

课件的总体经验：决策支持常扫描大量行但只访问部分列，列式通常有优势；事务处理常按行读取和修改少量完整记录，传统行式常更合适。**混合行列存储**可同时支持两种表示，但要处理额外空间、同步和维护成本；仅凭“OLAP / OLTP”标签不能替代实测。

### 6.3 列式文件与内存数据库

P27 提到 ORC、Parquet 是文件内部采用列式组织的格式，常用于大数据分析。课件的 ORC 示意图显示文件分为多个数据段，每段内有各列数据与索引，文件末尾有 footer；具体文件格式、编码和谓词下推能力以对应实现和版本为准。

**内存数据库**可直接在内存组织记录，不一定需要传统“磁盘页 → 缓冲池帧”的缓冲管理器；并不意味着所有系统都没有内存管理、持久化或恢复机制。内存中的列式布局同样适合部分分析任务，压缩可以减少内存占用，但会带来编码与访问代价（P28）。

## 7. 例题

以下均为补充例题，用于检验概念和计算。

### 7.1 定长记录能装多少条

页大小为 4096 B，页头 96 B，每条记录 100 B，不跨页且忽略其他开销。每页可用于记录的空间为 $4096-96=4000$ B，故可放 $\lfloor4000/100\rfloor=40$ 条，剩余 0 B。若记录长 120 B，则最多 $\lfloor4000/120\rfloor=33$ 条，剩余 40 B。最后的 40 B 不足以放一条完整记录。

### 7.2 槽式页移动记录

页 7 的槽 2 指向偏移 300、长度 80 的记录。页内整理将记录移至偏移 500，且槽号不变。将槽 2 改为 `(500, 80)`，引用 `(页 7, 槽 2)` 仍可找到该记录；直接保存偏移 300 的引用则失效。若槽 2 被删除并复用给另一条记录，单靠旧页号和槽号不能保证仍指向原记录。

### 7.3 空闲空间映射如何查找

第一层值为 `4 2 1 4 | 7 3 6 5 | 1 2 0 1 | 1 0 5 6`，每 4 项取最大值得到 `4 7 2 6`。需要约 $6/8$ 页空间时，可先排除第 1、3 组；第 2 组的 7、6 和第 4 组的 6 是候选。若映射过时，实际检查后这些候选仍可能不满足，还要更新映射并继续查找。

### 7.4 顺序文件如何插入

按键排列为 `10 → 20 → 30 → 40`，20 和 30 所在页没有可用空间，插入键 25。将 25 放入溢出块并修改链为 `10 → 20 → 25 → 30 → 40`。逻辑遍历结果仍有序，但读取 20 后可能需要跳到远处的溢出块，再跳回 30；溢出增多时重组可改善局部性。

### 7.5 缓冲池中的命中、脏页和固定

缓冲池只有两帧，最初装有页 A、B；A 干净且 pin count = 0，B 脏且 pin count = 1。请求页 C 未命中：B 当前不可驱逐，即使它更久未使用也不能选它；可驱逐 A 时，丢弃 A 的干净副本并读入 C。之后 B 的 pin count 降到 0，它才成为可驱逐候选；若选择驱逐，必须遵循恢复协议并确保脏数据安全写出。

### 7.6 LRU 与 MRU 的一轮比较

两个空帧依次访问 `1, 2, 3, 1, 2, 3`。假设所有页可驱逐，MRU 选最近访问页：

| 请求 | LRU 帧内容 | LRU | MRU 帧内容 | MRU |
|---:|---|---|---|---|
| 1 | 1 | 未命中 | 1 | 未命中 |
| 2 | 1, 2 | 未命中 | 1, 2 | 未命中 |
| 3 | 2, 3 | 未命中，替换 1 | 1, 3 | 未命中，替换 2 |
| 1 | 3, 1 | 未命中，替换 2 | 1, 3 | 命中 |
| 2 | 1, 2 | 未命中，替换 3 | 2, 3 | 未命中，替换 1 |
| 3 | 2, 3 | 未命中，替换 1 | 2, 3 | 命中 |

该序列 LRU 发生 6 次未命中，MRU 发生 4 次；它说明访问模式的重要性，不能推出 MRU 总优于 LRU。

### 7.7 分区裁剪与行列布局

教师工资表按年度分区；查询只计算 2019 年 `salary` 的平均值。如果优化器能从谓词证明只需 2019 分区，就可跳过其他年份；若该分区按列存储，还可能只读过滤所需列和 `salary` 列。分区裁剪决定**读哪些分区**，列裁剪决定**读哪些列**；两者可以同时发生，也可能由于谓词或实现限制而未发生。

### 7.8 写入顺序为什么影响恢复

页 A 的指针更新为指向新页 B。若磁盘先保存新 A，但 B 尚未可靠写入就断电，重启后 A 可能指向不存在或未初始化的内容。仅凭“内存中 B 当时是正确的”无法保证恢复；应依实现的日志、写入屏障及恢复协议安排持久化顺序。WAL 是数据库中常见方案之一。

## 8. 易错点速查

| 误解 | 正确认识 |
|---|---|
| 定长记录必然不会跨页 | 按连续偏移存放仍可能跨边界，需要布局规则避免 |
| 空闲链表会移动所有后续记录 | 它保留其他记录位置，把空槽链接供复用 |
| 槽式页里页号和槽号永远指向同一条记录 | 页内整理可保持引用，但删除、复用和跨页迁移需额外处理 |
| 空间映射显示有空位就一定插入成功 | 值可能量化或过期，需检查实际页和目录开销 |
| 逻辑顺序等于物理连续 | 溢出块和碎片可使指针顺序与磁盘位置不同 |
| 聚簇把两个关系变成一张逻辑表 | 多表聚簇是物理共置，逻辑上仍可为不同关系 |
| 分区后每次查询只访问一个分区 | 只有谓词和优化器允许裁剪时才可能跳过无关分区 |
| pin 和排他锁是同一件事 | pin 防驱逐，锁或 latch 保护并发内容访问 |
| 脏页不能在固定期间写回 | 固定主要限制替换；写回时机由实现和并发协议决定 |
| 写回数据页等于事务提交 | 提交、日志持久化和数据页写回是不同事件 |
| 列式一定更快 | 要看访问列数、更新频率、重构、压缩及具体负载 |
| 内存数据库不需要恢复 | 是否持久化及如何恢复取决于系统设计 |

## 9. 知识点速查

| 问题 | 关键点 |
|---|---|
| 定长记录的每页容量 | $\lfloor\text{页可用字节}/\text{记录字节}\rfloor$，先扣除页头等开销 |
| 变长记录怎样找字段 | 固定大小的偏移和长度描述符，加 NULL 位图和实际数据 |
| 页内整理后怎样保持引用 | 记录标识经槽位间接定位，移动时更新槽信息 |
| 堆文件怎样找空页 | 用分层空闲空间映射寻找候选，再核实页的实际空间 |
| 顺序文件如何应对插入 | 有空位则插入，否则用溢出块和指针，必要时重组 |
| 缓冲池未命中 | 找空闲帧或可驱逐帧，必要时安全写回脏页，再装入目标页 |
| 替换候选的前提 | 通常 pin count 为 0，并满足具体实现的其他约束 |
| 行式与列式 | 同行字段相邻 vs 同列值相邻；前者偏整行访问，后者偏少列批量分析 |
