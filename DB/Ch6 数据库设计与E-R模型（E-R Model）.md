> [!abstract] 一句话概括本章
> 前五章解决"怎么用数据库"，本章解决"**怎么设计数据库**"——先把现实世界画成 **E-R 图**（实体 + 关系 + 各种约束），再**有规则地翻译成关系模式**（表）。两大主线：① **建模能力**（什么该画成实体、什么该画成属性、基数怎么标、弱实体怎么认）；② **转换能力**（E-R 图 → 表的每条规则，以及每条规则带来的冗余/空值代价）。
> 设计的总纲只有一句话：**避开"冗余"与"不完整"两大陷阱，在"避免坏设计"之上再"从一堆好设计里挑一个更合适的"**。

## 1 数据库设计概览

### 1.1 设计三阶段

**通俗理解**：盖楼分三步——先搞清**住户要什么**（需求），再画**建筑图纸**（概念/逻辑结构），最后定**施工与用料**（物理布局）。数据库设计同理。

**严谨说明**（课件 P2–P3）：

| 阶段 | 课件原文 | 干什么 | 产出 |
|---|---|---|---|
| **初始阶段** | characterize fully the data needs of the prospective database users | 全面刻画未来用户的数据需求 | 需求描述 |
| **第二阶段** | choosing a data model；applying the concepts of the chosen data model；translating these requirements into a **conceptual schema** | 选数据模型，把需求翻译成**概念模式** | 概念模式（如 E-R 图） |
| **最终阶段** | Moving from an abstract data model to the implementation | 从抽象模型走向实现 | 分**逻辑设计** + **物理设计** |

- **概念模式**要"完整发育"（fully developed），它同时指示企业的**功能需求**——还要**描述将对数据执行的操作（事务）**（课件 P2 最后一条）；
- **逻辑设计（Logical Design）** = **决定数据库模式**（Deciding on the database schema）——找到一组"好的"关系模式（relation schemas）；
- **物理设计（Physical Design）** = **决定数据库的物理布局**（physical layout）。

> [!tip] 逻辑设计里的两种决策（课件原文，常考）
> - **商业决策（Business decision）**：数据库该记录**哪些属性**？
> - **计算机科学决策（CS decision）**：该有哪些**关系模式**、属性如何**分配**到各关系模式中？
>
> 记忆：**"存什么"是业务问题，"怎么拆表"是技术问题**——前者错了一切白搭，后者错了一堆冗余。

### 1.2 两大陷阱与两种设计路线

**通俗理解**：坏设计有两个死法——**存了两遍**（改一处忘另一处 → 数据自相矛盾）；**想存的存不下**（某些业务没法表达）。

**严谨说明**（课件 P4 "Design Alternatives"）：设计模式时必须避开**两大陷阱**：

| 陷阱 | 课件原文 | 危害 |
|---|---|---|
| **冗余（Redundancy）** | a bad design may result in **repeat information** | 重复表示信息 → **各副本之间数据不一致**（data inconsistency among the various copies） |
| **不完整（Incompleteness）** | a bad design may make certain aspects of the enterprise **difficult or impossible to model** | 企业的某些方面难以甚至无法建模 |

且课件强调：**"避免坏设计"还不够**——好设计可能有很多，必须从中**选择**（Avoiding bad designs is not enough. There may be a large number of good designs from which we must choose）

**两条设计路线**（课件 P5）：

| 路线 | 思路 | 对应章节 |
|---|---|---|
| **E-R 模型（本章）** | 把企业建模为**实体（entity）的集合 + 关系（relationship）**，用 **E-R 图**可视化 | 本章 |
| **规范化理论** | **形式化定义"什么是坏设计"并加以检测**（Formalize what designs are bad, and test for them） | 第 7 章 |

**核心概念**（课件原文）：

- **实体（Entity）**：企业中**可与其它对象区分开**的"事物/对象"（a "thing" or "object" that is distinguishable from other objects），由**一组属性**描述；
- **关系（Relationship）**：**若干实体之间的联系**（an association among several entities），用 **E-R 图**图示。

> [!important] E-R 与规范化是"一体两面"
> E-R 是**自顶向下**的建模工具（先画出来）；规范化是**自底向上**的检测工具（把关系拆开，用函数依赖查冗余）。两者目标一致——**消灭冗余、保证表达力**。先 E-R 建模，再用第 7 章的范式复核，是标准流程。

## 2 E-R 模型的基本元素

### 2.1 实体与实体集

**通俗理解**：**实体 = 一个具体的东西**（张三、清华大学、2024 年元旦）；**实体集 = 同一类东西的全体**（所有人、所有公司、所有假期）。

**严谨定义**（课件 P7）：

- **实体（entity）**：**存在且可与其它对象区分**的对象（an object that exists and is distinguishable from other objects）——例：具体的人、公司、事件、工厂；
- **实体集（entity set）**：**同一类型、共享相同属性**的实体之集合（a set of entities of the same type that share the same properties）——例：所有人的集合、所有公司的集合、所有树、所有假期；
- **属性（attribute）**：实体集全体成员都具有的**描述性性质**——例：

```text
instructor = (ID, name, salary)
course     = (course_id, title, credits)
```

- **主键（primary key）**：实体集的**属性子集**，用以**唯一标识**集合中每个成员（a subset of the attributes form a primary key... uniquely identifying each member of the set）。

**E-R 图画法**（课件 P8）：

| 元素 | E-R 记号 |
|---|---|
| 实体集 | **矩形**（Rectangle） |
| 属性 | 列在矩形**内部** |
| 主键属性 | **下划线**（Underline） |

### 2.2 关系与关系集

**通俗理解**：**关系 = 一次具体的联系**（"张三选了数据库课"）；**关系集 = 所有同类联系的集合**（所有"学生—导师"配对）。

**严谨定义**（课件 P9）：

- **关系（relationship）**：**若干实体之间的联系**——例：`44553 (Peltier)` —`advisor`→ `22222 (Einstein)`，即学生实体与导师实体通过 `advisor` 关系集相连；
- **关系集（relationship set）**：$n$（$n \ge 2$）个实体之间的一个**数学意义上的关系**：

$$\{\, (e_1, e_2, \dots, e_n) \mid e_1 \in E_1,\ e_2 \in E_2,\ \dots,\ e_n \in E_n \,\}$$

其中每个 $(e_1,\dots,e_n)$ 是一条**关系（元组）**——例：`(44553, 22222) ∈ advisor`。

- **画法**：相关实体之间画一条线（Pictorially, we draw a line between related entities）；**关系集用菱形（Diamond）表示**（课件 P11）。

**关系集可以带属性**（课件 P12）：`advisor` 关系集可带属性 `date`，记录学生何时开始跟随该导师——图示如下（注意 `date` 挂在**菱形**上，不是实体上）：

![[Ch6-img-p21-87.jpeg]] ![[Ch6-img-p22-90.jpeg]]

> [!warning] 易错点：关系的属性别挂错地方
> `date`（成为导师的日期）属于"**这段师生关系**"，不属于学生也不属于导师——它必须画在**菱形（关系集）**上。若画在实体上，语义就变成了"学生固有的一个性质"，明显不对。判断口诀：**"谁的属性？离开关系就不成立的，挂关系上。"**

### 2.3 角色与关系的度

**角色（Role）**（课件 P14）：当关系集两端是**同一个实体集**时，每次出现的实体在关系中扮演一个"角色"。例：`prereq` 关系中两个标签 `course_id` 与 `prereq_id` 就是**角色名**——它们标明同一个 `course` 实体集在一条关系里分别充当"先修课"与"被先修课"。

- **何时必须写角色**：参与关系的实体集**不 distinct**（need not be distinct）时，用角色区分两端；
- 不写角色时，位置（第几元）隐含了角色。

**关系的度（Degree）**（课件 P15）：

| 术语 | 含义 |
|---|---|
| **二元关系（binary）** | 涉及**两个**实体集（degree 2） |
| **三元关系（ternary）** | 涉及**三个**实体集（degree 3） |

- 课件强调：**数据库中绝大多数关系集是二元的**（most relationship sets in a database system are binary）；多于两个实体集的关系**罕见**；
- 三元关系例子：`proj_guide`——学生在导师指导下做项目，连接 `instructor`、`student`、`project` 三个实体集。

### 2.4 属性的四种类型

**通俗理解**：给东西贴标签有四种玩法——**一个值还是多个值**（单值/多值）、**要不要拆开**（简单/复合）、**要不要现算**（派生）。

**严谨说明**（课件 P17 "Complex Attributes"）：

| 分类维度 | 类型 | 定义 | 例子 |
|---|---|---|---|
| 能否拆分 | **简单属性（simple）** | 不可再分 | `sex` |
| | **复合属性（composite）** | 可拆成子部分（其它属性） | `name` → `first_name, middle_initial, last_name`；`address` → `street, city, state, postal_code`（`street` 还能再拆 `street_number, street_name, apartment_number`） |
| 值的个数 | **单值属性（single-valued）** | 一个实体取一个值 | `ID` |
| | **多值属性（multivalued）** | 一个实体可取多个值 | `phone_numbers` |
| 是否现算 | **派生属性（derived）** | 可从其它属性**计算得出** | `age` ← 由 `date_of_birth` 算出 |

- **域（domain）**：每个属性**允许取值的集合**（the set of permitted values for each attribute）。

**复合属性的树状结构**（课件 P18）：

```text
name                          address
├── first_name                ├── street
├── middle_initial            │   ├── street_number
└── last_name                 │   ├── street_name
                              │   └── apartment_number
                              ├── city
                              ├── state
                              └── postal_code
  └── composite attributes（复合属性）      └── component attributes（成分属性）
```

> [!tip] 派生属性的本质
> `age` 不存库，随 `date_of_birth` **动态算出**——好处是永不陈旧（生日不变则年龄自动对），代价是每次读都要算。**能派生就别存**，是减少冗余的一条朴素原则（但跨表派生成本高时也可以冗余存储 + 用触发器维护，见 [[Ch5 Advanced SQL#3 触发器（Triggers）|Ch5 触发器]]）。

## 3 约束：基数与参与

### 3.1 映射基数四种类型

**通俗理解**：映射基数回答"**一个实体最多能和几个对方实体挂钩**"——这决定了两边的"配额"。

**严谨定义**（课件 P20）：**映射基数（mapping cardinality）** 表达"一个实体可以通过关系集与**多少个**其它实体相关联"；**对二元关系最有用**。二元关系的映射基数必为下列之一：

| 类型 | 含义（设关系连 A、B 两边） |
|---|---|
| **一对一（one-to-one, 1:1）** | A 中每个实体至多连 B 中 1 个，反之亦然 |
| **一对多（one-to-many, 1:N）** | A 中每个实体可连 B 中多个；B 中每个实体至多连 A 中 1 个 |
| **多对一（many-to-one, N:1）** | A 中每个实体至多连 B 中 1 个；B 中每个实体可连 A 中多个 |
| **多对多（many-to-many, M:N）** | 两边都可以连多个 |

> [!warning] 课件原注（P21/P22）
> **A、B 中的某些元素可能不与对方任何元素相映射**（Some elements in A and B may not be mapped to any elements in the other set）——即"**可为 0**"。这与"多"侧可含 0 一致（见 3.3 的 several **including 0**）。

**方向口诀**（避免 1:N 与 N:1 搞反）：**先说"一"后说"多"没用，要问"从谁看"**——"A 对 B 是多对一"= **A 中多个实体指向 B 中同一个**（B 是"一"侧）。

### 3.2 ER 图中的基数表示法

**通俗理解**：箭头 = "至多一个"，无箭头 = "可以多个"。

**严谨说明**（课件 P23）：在**关系集与实体集之间的连线**上画：

| 记号 | 含义 |
|---|---|
| **有向线段（箭头 →）** | "一"（**at most one**，至多一个） |
| **无向线段（—）** | "多"（many） |

例子（课件 P23–P26）：

| 关系类型 | 箭头方向 | 语义（以 advisor 为例） |
|---|---|---|
| **1:1** | 两边**都**画箭头 | 每个学生经 advisor 至多关联 1 个导师；每个导师至多关联 1 个学生 |
| **1:N**（instructor–student） | 指向"一"侧 | 导师可有多个（含 0 个）学生；**每个学生至多 1 个导师** |
| **N:1** | 指向"一"侧 | 导师至多关联 1 个学生；学生可有多个（含 0 个）导师 |
| **M:N** | **两边都无箭头** | 两边都可以关联多个（含 0） |

> [!warning] 最易错：箭头指向的是"一"侧，读法是"至多一个"
> 箭头**从关系指向那个"每个实体至多连一个对方"的实体集**。记忆：**箭头 = 卡钳，掐住"这一侧每条只出一个"**。看到图先问："**哪一侧被箭头指着？那侧就是'一'（至多一个）。**"
>
> ⚠️ 注意与 UML 相反：UML 里基数写在**对方**位置，课件 P75 明确 *"Note reversal of position in cardinality constraint depiction"*（见 [[#7.3 E-R 记号与 UML 类图|7.3]]）。

### 3.3 全参与与部分参与

**通俗理解**：参与约束回答"**是不是人人都得参与**"——全参与 = 必须，部分参与 = 可有可无。

**严谨定义**（课件 P27）：

| 类型 | 记号 | 定义 |
|---|---|---|
| **全参与（total participation）** | **双线**（double line） | 实体集中**每个**实体都至少参与关系集中的一条关系 |
| **部分参与（partial participation）** | 单线 | **部分**（some）实体可以不参与任何关系 |

课件例子：

- `student` 对 `advisor` 是**全参与** → **每个学生必须有导师**（every student must have an associated instructor）；
- `instructor` 对 `advisor` 是**部分参与** → 并非每个导师都带学生（可为 0）。

> [!warning] 易错点：全参与 ≠ "多"
> **参与（单/双线）管"必须吗"，基数（箭头）管"至多几个"**——两根线独立标注、独立理解。一个组合例子：`student` 画双线 + 箭头指向 student ⇒ "每个学生**必须**有导师，且**至多 1 个**"（即恰好 1 个）。**双线看"下限=1"，箭头看"上限=1"**。

### 3.4 l..h 显式约束与三元约束

**l..h 记法**（课件 P28）：连线可标注**最小..最大基数** `l..h`：

- 最小值 `l = 1` → **全参与**（A minimum value of 1 indicates total participation）；
- 最大值 `h = 1` → 实体**至多**参与一个关系（at most one relationship）；
- 最大值 `h = *` → **无上限**（no limit）。

课件例子：*Instructor can advise 0 or more students. A student must have 1 advisor; cannot have multiple advisors* ⇒ 导师侧 `0..*`，学生侧 `1..1`。

**三元关系的基数约束**（课件 P29）——细节最多的一条：

- **规定**：三元（或更高元）关系**至多允许一个箭头**（allow at most one arrow out of a ternary relationship）；
- 例：`proj_guide` 到 `instructor` 画箭头 ⇒ **每个学生在一个项目上至多有一个指导者**；
- **为何禁止多个箭头**：若三元关系 R 连 A、B、C，同时给 B、C 画箭头，含义有两种**互相冲突**的解释——
  1. 每个 A 实体关联**唯一的 (B, C) 组合**；或
  2. 每个 (A, B) 对关联唯一 C，且每个 (A, C) 对关联唯一 B；
- 不同形式化体系各取一种，**为避免混淆，直接禁止多于一个箭头**（To avoid confusion we outlaw more than one arrow）。

> [!important] 为什么二元可以画两个箭头、三元不行
> 二元关系画两个箭头就是 1:1，语义唯一；**三元关系的"箭头指向"无法唯一确定配对语义**（上面两种解释在二元里等价、在三元里不等价），所以标准化为"**至多一个箭头**"。这是三元关系最高频的考点。

## 4 主键与弱实体集

### 4.1 实体集的主键

**严谨定义**（课件 P31）：

- 按定义，各个实体天然不同；但从**数据库视角**，它们的差异必须**用属性表达**；
- 实体的属性取值必须**足以唯一标识该实体**——**实体集中不允许两个实体在所有属性上取值完全相同**；
- **实体的键（key）**：足以**彼此区分**实体的**一组属性**。

### 4.2 关系集的主键

**通俗理解**：要唯一确定"哪一条关系"，就把**参与各方的身份证号拼起来**，再补上关系自己的属性。

**严谨定义**（课件 P32）：设关系集 $R$ 涉及实体集 $E_1,\dots,E_n$，则

$$PK(R) \;=\; PK(E_1) \cup PK(E_2) \cup \cdots \cup PK(E_n) \;\cup\; \{a_1,\dots,a_m\}$$

其中 $a_1,\dots,a_m$ 是挂在关系集 $R$ 自身上的属性。

- **例**：`advisor` 的主键 = `instructor.ID` + `student.ID`；
- ⚠️ **关系集主键的选择取决于其映射基数**（The choice... depends on the mapping cardinality）——见下表。

### 4.3 二元关系的主键选择

**严谨说明**（课件 P33，按映射基数选"最小超键"）：

| 映射基数 | 关系集的主键 | 理由 |
|---|---|---|
| **多对多（M:N）** | **两侧主键的并集**（union） | 并集是**最小超键**，取为主键 |
| **一对多（1:N）** | **"多"侧**实体集的主键 | "多"侧已能唯一确定这条关系 |
| **多对一（N:1）** | **"多"侧**实体集的主键 | 同上（"多"侧是哪边？被箭头**指不到**的那侧） |
| **一对一（1:1）** | **任一**参与实体集的主键 | 两边各自都是最小超键，**任选其一** |

> [!warning] 记忆锚点：**永远选"多"侧**
> 1:1 例外（任选）；其余三种一律 **"多"侧做主键**——因为"多"侧的一个实例能唯一对应这条关系，"一"侧不能（它还连着别人）。
> 反直觉点：**1:N 和 N:1 的答案都是"多"侧**，别被名字绕进去——先画箭头找出"多"侧再决定。

### 4.4 弱实体集

**通俗理解**：有些实体"**离开宿主就不存在**"——`section`（开课班次）单独靠 `sec_id` 认不出自己，必须先知道"哪门课的"。这类实体叫**弱实体集**。

**引出问题**（课件 P34–P35，两难推理）：

设 `section` 由 `course_id, semester, year, sec_id` 唯一标识，且与 `course` 相关：

1. **方案 A**：建关系集 `sec_course` 连接 section 与 course —— ❌ 冗余！`section` 已有 `course_id` 属性表达了这层联系；
2. **方案 B**：删掉 `sec_course` —— ❌ 把关系**藏进了一个属性里**，不理想（relationship becomes implicit in an attribute, which is not desirable）；
3. **方案 C**：不存 `course_id`，只存 `sec_id, year, semester` —— ❌ 此时 `section` **没有足够属性唯一标识自己**；
4. **正解**：把 `sec_course` 当作**特殊关系**，它提供"额外识别信息"（`course_id`），使 `section` 能被唯一识别。

**严谨定义**（课件 P35–P36）：

- **弱实体集（weak entity set）**：其**存在依赖于**另一个实体（称**识别实体集，identifying entity**）的实体集；
- 对弱实体**不设主键**，改用**识别实体 + 额外属性 discriminator** 来唯一标识；
- **强实体集（strong entity set）**：非弱实体集者；
- 每个弱实体**必须**关联一个识别实体（**存在依赖，existence dependent**）；
- 识别实体集**拥有（own）** 它所识别的弱实体集；
- 连接弱实体集与识别实体集的关系集 = **识别关系（identifying relationship）**；
- ⚠️ 课件 P36 注意点：**最终生成的关系模式里仍会有 `course_id` 属性**（尽管从实体集里删掉了）——因为它作为外键被引入（见 [[#5.2 实体集的转换|5.2]]）。

**E-R 图记号**（课件 P37）：

| 元素 | 记号 |
|---|---|
| 弱实体集 | **双矩形**（double rectangle） |
| discriminator | **虚线下划线**（underlined with a dashed line） |
| 识别关系集 | **双菱形**（double diamond） |
| `section` 的主键 | `(course_id, sec_id, semester, year)`——**识别实体主键 + discriminator** |

> [!important] 弱实体三件套（背下来）
> **双矩形（弱实体）+ 双菱形（识别关系）+ 虚线下划线（discriminator）**；其"主键" = **宿主主键 + 自己的 discriminator**。`section` 是全章最标准的例子。

## 5 从 E-R 图到关系模式

### 5.1 总原则

**通俗理解**：E-R 图是"设计图"，关系模式是"施工图"——每个矩形、菱形最后都变成一张表，但有些表会被**合并/删除**以省掉冗余。

**严谨说明**（课件 P41）：

- 实体集与关系集都能**统一地**表示为关系模式；
- 符合 E-R 图的数据库可用**一组模式**表示；
- **每个实体集与关系集对应一个唯一模式**，名字沿用原名；
- 每个模式有若干列（通常对应属性），列名唯一。

### 5.2 实体集的转换

**规则**（课件 P42）：

| 实体集类型 | 转换规则 | 例子 |
|---|---|---|
| **强实体集** | 直接变成**同名同属性**的表 | `student(ID, name, tot_cred)` |
| **弱实体集** | 变成一张表，**额外加一列放识别实体集的主键** | `section(course_id, sec_id, sem, year)` |

> 注：`section` 表里的 `course_id` 正是 4.4 中"从实体集删掉、又在关系模式里出现"的那个属性——**它现在是识别实体（course）的主键，起外键作用**。

### 5.3 复合与多值属性的处理

**复合属性**（课件 P43）：**打平（flattened）**——为每个成分属性建一列：

- 例：`instructor.name` 是复合的（`first_name`, `last_name`）→ 模式里生成 `name_first_name`、`name_last_name` 两列；
- **无歧义时省略前缀**（Prefix omitted if there is no ambiguity）——`name_first_name` 可直接写 `first_name`；
- 打平后的 `instructor` 模式（忽略多值属性）：

```sql
instructor(ID,
    first_name, middle_initial, last_name,
    street_number, street_name,
    apt_number, city, state, zip_code,
    date_of_birth)
```

**多值属性**（课件 P44）：**单独建一张表**：

- 实体 $E$ 的多值属性 $M$ → 单独模式 $E_M$；
- $E_M$ 的属性 = **$E$ 的主键 + 该多值属性**；
- 例：`instructor.phone_number` 多值 → `inst_phone(ID, phone_number)`；
- **每个取值对应单独一条元组**：主键 22222 有电话 456-7890、123-4567 → 映射为 **两行**：`(22222, 456-7890)`、`(22222, 123-4567)`。

> [!warning] 易错点：复合"打平"，多值"拆表"
> 一句话分清：**复合属性 → 拆成多列（在原表里加列）；多值属性 → 拆成新表（原表 + 主键）**。记混了直接丢分。

### 5.4 关系集的转换与冗余消除

**多对多关系**（课件 P45）：**单独建一张表**，列为**两参与实体集的主键 + 关系自身的描述属性**：

```text
advisor = (s_id, i_id)          -- 两端主键
```

**消除冗余的三种手法**（课件 P46–P48，本节核心）：

| 手法 | 适用条件 | 做法 | 课件例子 |
|---|---|---|---|
| **① "多"侧加外键** | **多对一 / 一对多**，且**"多"侧为全参与** | 不建关系表，改为在"多"侧表里**加一列**放"一"侧的主键 | 不为 `inst_dept` 建表，直接在 `instructor` 表加 `dept_name` |
| **② 一对一任选一侧** | **一对一** | "多"侧可任选 → 在**任一**表里加外键即可 | 两表任选其一加列 |
| **③ 删识别关系表** | **弱实体的识别关系** | 识别关系的表**是冗余的**，删掉 | `sec_course` 表冗余（`section` 表已含这些属性） |

**代价与陷阱**（课件 P47）：

- 若"多"侧是**部分参与**，用"加外键"替代关系表 → 可能产生 **NULL 值**（could result in null values）；
- 课件 P38 也点名：`student.dept_name` 复制了 `stud_dept` 关系里的信息 → **是冗余、需要删**；**但转回表时该属性有时又被加回来**（as we will see later）——这正是 ① 的反向体现。

> [!important] 三条冗余消除的统一思想
> 全部围绕一件事：**能塞进已有表的，就不另建表**——
> - 多对一/一对多 → 外键塞"多"侧（省一张表）；
> - 一对一 → 任一侧（更自由）；
> - 弱实体识别关系 → 直接被弱实体表吸收（必然冗余）。
>
> **代价**：省表 = 可能引入 NULL（部分参与）、可能让"删关系"变成"隐式属性"（弱实体的两难里提过）。

## 6 扩展 E-R 特性

### 6.1 特化与概化

**通俗理解**：**特化 = 从大类往下分**（人 → 教师/秘书）；**概化 = 从多个小类往上合**（本科生 + 研究生 → 学生）。方向相反，画法一样。

**严谨定义**（课件 P50、P54）：

| | 特化（Specialization） | 概化（Generalization） |
|---|---|---|
| 方向 | **自顶向下**（top-down） | **自底向上**（bottom-up） |
| 做法 | 在实体集内**指定子分组**，它们区别于集内其它实体 | 把**共享相同特征的多个实体集合并**成高层实体集 |
| 结果 | 子分组成为**低层实体集**，拥有高层没有的属性/关系 | 产生**高层实体集** |
| 关系 | 二者互为简单反转（simple inversions of each other），**E-R 图画法相同**，术语**可互换使用**（used interchangeably） | 同左 |

- **ISA 三角**：用标 **ISA** 的三角形表示（如 instructor "is a" person）；
- **属性继承（attribute inheritance）**：低层实体集**继承**它所连高层实体集的**全部属性与关系参与**（inherits all the attributes and relationship participation）。

**例子**（课件 P51）：

- **重叠（Overlapping）**：`employee` 与 `student`——一个人可以既是员工又是学生；
- **不相交（Disjoint）**：`instructor` 与 `secretary`——一个人不能同时是两者；
- 还有 **total / partial** 之分（见 [[#6.3 完整性约束（total/partial）|6.3]]）。

### 6.2 特化的两种表示法与代价

**严谨说明**（课件 P52–P53）：把特化转成关系模式有两种方法，**各有缺陷**：

| 方法 | 做法 | 缺陷（课件原文） |
|---|---|---|
| **方法 1：高层 + 低层各建表** | 为高层建一个模式；为每个低层建模式，**含高层主键 + 本地属性** | 查一个 employee 的完整信息要**访问两张表**（低层 + 高层） |
| **方法 2：每个低层全量建表** | 为每个实体集建含**全部本地 + 继承属性**的模式 | 对"既是学生又是员工"的人，`name, street, city` **被重复存储**（冗余） |

> [!tip] 权衡口诀
> **方法 1 省存储、查得慢（要 JOIN）；方法 2 查得快、费存储（有冗余）**——与 [[#1.2 两大陷阱与两种设计路线|冗余陷阱]] 遥相呼应，没有免费午餐。

### 6.3 完整性约束（total/partial）

**严谨定义**（课件 P55–P56）：**完整性约束（completeness constraint）** 规定：高层实体集中的实体**是否必须**属于概化中至少一个低层实体集。

| 类型 | 含义 |
|---|---|
| **total（全）** | 实体**必须**属于某个低层实体集 |
| **partial（部分）** | 实体**不必**属于任何低层实体集 |

- ⚠️ **partial generalization 是默认**（Partial generalization is the default）；
- **指定 total 的画法**：加关键字 `total`，用**虚线**把它连到对应的**空心箭头**（单个或一组）上；
- 课件例子：`student` 概化是 **total**——所有学生必须是 graduate 或 undergraduate；
- **经验规律**：由概化得到的高层实体集通常**只由低层实体构成**，所以它的完整性约束**通常是 total**。

> [!warning] 易错点：默认是 partial，不是 total
> 高频判断题："不标注即为 total" → **错**，**默认 partial**；要 total 必须显式加 `total` 关键字 + 虚线连接。这条反直觉，务必记住。

### 6.4 聚合（Aggregation）

**通俗理解**：有时候要"**对一段关系再建关系**"——"某人在某项目上被评价如何"这个评价，挂靠的是"**导师—学生—项目**三者的关系"，而不是某一个实体。**聚合把关系打包成一个"伪实体"，从而能被再次关联**。

**引出问题**（课件 P57–P58）：

- 设三元关系 `proj_guide`（导师指导学生做项目）；
- 现要记录**导师对学生在该项目上的评价（evaluation）**——新建关系集 `eval_for`；
- **冗余分析**（课件 P58）：
  - 每个 `eval_for` 关系都对应一个 `proj_guide` 关系；
  - 但**并非每个 `proj_guide` 都有对应的 `eval_for`**（有的还没评价）；
  - → 二者**信息重叠**，但**不能丢掉 `proj_guide`**（So we can't discard the proj_guide relationship）；
- **解法：聚合（aggregation）**——**把关系当作抽象实体**（Treat relationship as an abstract entity），允许"**关系之间的关系**"（Allows relationships between relationships），即**关系的抽象化**（Abstraction of relationship into new entity）。

**聚合后的语义**（课件 P59）：

- 某学生在某项目上由某特定导师指导；
- 某个（学生, 导师, 项目）三元组**可以**有一个关联的评价。

**转成关系模式**（课件 P60）：为聚合建一张表，含：

1. **被聚合关系的主键**；
2. **关联实体集的主键**；
3. **任何描述属性**。

```text
eval_for(s_ID, project_id, i_ID, evaluation_id)
proj_guide 的模式是冗余的（可删）
```

> [!important] 聚合解决什么
> 没有聚合时，"关系上的关系"只能靠**把关系降级成实体 + 冗余表**来表达（`eval_for` 和 `proj_guide` 重叠）。聚合用一个统一抽象把这层打包，**消除重叠**，且转换后 `proj_guide` 表可省。判断口诀：**要给"一段联系"挂属性/再建联系 → 用聚合**。

## 7 设计问题与记号体系

### 7.1 实体 vs 属性、实体 vs 关系

**实体 vs 属性**（课件 P64）：关键看**要不要给这个对象本身再记更多信息**。

- 课件例子：把 `phone` 做成**实体**（而非属性）→ 可以记录**关于电话号码的额外信息**，并且天然支持**多个电话号码**（multivalued）；
- 指南：**若该对象还需自己的属性、或需要多值 → 升级为实体集**。

**实体 vs 关系集**（课件 P65）：

- 一条**可能的指南**：用**关系集**描述**实体之间发生的动作（an action that occurs between entities）**；
- **关系属性放哪**：例 `date` 是放 `advisor` 上还是 `student` 上？——放**关系**上（它是"成为导师"这个动作的时间，见 [[#2.2 关系与关系集|2.2]]）。

### 7.2 二元 vs 非二元关系

**严谨说明**（课件 P66–P68）：

- 虽然任何 $n$ 元（$n>2$）关系都可拆成多个二元关系，但 **n 元关系更清楚地表明"多个实体共同参与同一条关系"**；
- **看似非二元、实则更适合二元**的例子：三元 `parents`（孩子—父亲—母亲）**最好拆成两个二元关系** `father` 和 `mother`——这样**允许部分信息**（比如只知道母亲）；
- **天然非二元**的例子：`proj_guide`（确实需要三个实体同现）。

**把非二元拆成二元的通用方法**（课件 P67）：引入**人工实体集（artificial entity set）**：

- 用实体集 $E$ + 三个关系集 $R_A, R_B, R_C$ 取代 A、B、C 间的 $R$；
- 给 $E$ 建识别属性，并把 $R$ 的属性加进 $E$；
- 对 $R$ 中每条 $(a_i, b_i, c_i)$：在 $E$ 中建新实体 $e_i$，并加入 $(e_i,a_i) \in R_A$、$(e_i,b_i) \in R_B$、$(e_i,c_i) \in R_C$。

**代价与练习**（课件 P68）：

- **还要翻译约束**；**并非所有约束都能翻译**——转换后的模式可能出现**无法对应 $R$ 任何实例的实例**（不能保证语义等价）；
- 课件练习：给 $R_A, R_B, R_C$ 加约束，确保新建实体**恰好**关联 A、B、C 各一个实体；
- 可以**不建识别属性**：把 $E$ 做成由三个关系集识别的**弱实体集**。

> [!tip] 拆分二元的取舍（答题模板）
> **能二元就二元**（允许部分信息、更常用），**但天然多元的别硬拆**（拆了要引入人工实体 + 补约束，还可能不等价）——两句话正好对应课件的 parents 与 proj_guide 两个例子。

### 7.3 E-R 记号与 UML 类图

**E-R 记号总结**（课件 P70–P71 的符号表，本节背诵重点）：

| 元素 | 记号 |
|---|---|
| 实体集 | 矩形 |
| 关系集 | 菱形 |
| 属性 | 椭圆（列在实体内亦可） |
| 主键属性 | 实线下划线 |
| 弱实体集 | **双矩形** |
| discriminator | **虚线下划线** |
| 识别关系 | **双菱形** |
| 派生属性 | 虚线椭圆 |
| 多值属性 | 双线椭圆 |
| 全参与 | **双线**（连线） |
| 基数"一" | **箭头 →** |
| ISA / 特化 | 三角形（标 ISA） |
| total 完整性 | 关键字 `total` + 虚线连到空心箭头 |

**替代记号**（课件 P72–P73）：**Chen 记号**、**IDE1FX（Crows feet，鸟爪记号）** 等——同一套语义有多种画法，读图先认清用的哪套。

**UML 类图对照**（课件 P74–P76）：

- **UML = Unified Modeling Language**，有很多组件图形化建模软件系统的不同侧面；
- **UML 类图对应 E-R 图，但有若干差异**；
- ⚠️ **最关键差异：基数约束的位置相反**（课件 P75 原注：*Note reversal of position in cardinality constraint depiction*）——E-R 的箭头 vs UML 的多重度标记位置互换；
- 课件 P76 给了完整对照表，其中：**特化既可用合并箭头也可用独立箭头，与 disjoint/overlapping 无关**（Generalization can use merged or separate arrows independent of disjoint/overlapping）。

**UML 中关系的画法**（课件 P77）：

- 二元关系集：直接**连线**，关系名写在**线旁**；
- 角色名写在**线靠实体集的一侧**；
- 关系集名也可写在**盒子里**（连同关系属性），用**点线**连到表示关系的那条线。

### 7.4 设计决策清单

**六大约束设计决策**（课件 P69 "E-R Design Decisions"，答题可直接列）：

1. 用**属性还是实体集**表示一个对象？
2. 一个现实世界概念用**实体集还是关系集**表达最好？
3. 用**三元关系还是一对二元关系**？

## 9 综合例题（难度偏高）

**例题 1（设计阶段与陷阱辨析）** 判断下列各属于哪一阶段、或属于哪种陷阱：

(a) 决定 `instructor` 表要建 `salary` 列；(b) 决定把 `dept_name` 放进 `instructor` 还是单独建 `department` 表；(c) 决定数据在磁盘上的存放与索引布局；(d) 每个学生的系名同时存在 `student` 表和 `stud_dept` 关系里，改系时两处只改了一处；(e) 某企业需要记录"每次电话通话的时长与对端号码"，但设计里电话只是一个字段，无法表达。

<details><summary>参考解答</summary>

| 小问 | 归属 | 理由 |
|---|---|---|
| (a) | **逻辑设计 · 商业决策** | "该记录哪些属性"——业务问题 |
| (b) | **逻辑设计 · 计算机科学决策** | "该有哪些关系模式、属性如何分配到各模式"——技术问题 |
| (c) | **物理设计** | 决定物理布局（physical layout） |
| (d) | **冗余陷阱** | 重复信息 → 改一处忘一处 → **数据不一致**（课件 redundancy 的直接后果） |
| (e) | **不完整陷阱** | 设计使企业某些方面**难以/无法建模**（incompleteness） |

**区分要点**：(a)(b) 同属逻辑设计但一个问"存什么"、一个问"怎么拆"；(d)(e) 分别对应两大陷阱的定义原文——**冗余看"是否重复存储导致不一致"，不完整看"是否表达不出来"**。

</details>

**例题 2（基数与参与的读图）** 某 `enroll` 关系连接 `student` 与 `course`：连线在 `student` 侧为**双线 + 无箭头**，在 `course` 侧为**单线 + 箭头**。请回答：(a) 这是哪种映射基数？(b) 学生的参与是全还是部分？课程呢？(c) "一个学生一学期最多选 3 门课"能否用现有记号表达？(d) 用 `l..h` 重写两侧约束。

<details><summary>参考解答</summary>

**(a) 多对一？先别急——按"箭头指一"原则**：箭头指向 `course`，说明**从 course 看每个实体至多连一个 student**，即"每门课至多被一个学生选" ⇒ 关系是 **student → course 为多对一（N:1，多个学生对一门课）**…… 但注意这不符合常理（一门课通常多个学生选），**题目给的图就是如此**——读图只认记号不认直觉。

**(b)** `student` 侧**双线 = 全参与**：**每个学生必须选课**（不能一门都不选）；`course` 侧**单线 = 部分参与**：**并非每门课都有人选**（可为 0）。

**(c) 不能。** 现有 E-R 记号只有"至多一个（箭头）/ 多（无箭头）/ 参与是否必须（单双线）/ `l..h`"——**`l..h` 的上限只能是具体数字或 `*`**，写 `0..3` 可表达"至多 3 门"！所以严格说：**用 `l..h` 可以（`0..3` 或 `1..3`），用箭头/无箭头不行**（箭头只能表达"至多 1"，无法表达"至多 3"）。

**(d)** 学生侧全参与 → `1..*`（每生至少 1 门、可多门，若限 3 门则 `1..3`）；课程侧部分参与且每课至多 1 生 → `0..1`。

**核心收获**：**箭头只能表达"至多 1"；要表达"至多 n"必须用 `l..h` 显式标注**——这是 l..h 记法存在的意义。

</details>

**例题 3（关系集主键选择）** 分别给出 `advisor`（instructor–student）、`proj_guide`（instructor–student–project 三元）在下列基数下的关系集主键：(a) M:N；(b) 1:N（学生侧为"多"）；(c) 1:1；(d) 三元且未标箭头。

<details><summary>参考解答</summary>

| 情形 | 主键 | 依据 |
|---|---|---|
| (a) M:N | `{instructor.ID, student.ID}` | 两侧主键**并集**是**最小超键**（P33） |
| (b) 1:N（学生为"多"） | `{student.ID}` | **"多"侧**主键即最小超键（一门…一个导师带多个学生，学生ID 唯一定位） |
| (c) 1:1 | `{instructor.ID}` 或 `{student.ID}` **任选** | 两侧各自都是最小超键（either one can be chosen） |
| (d) 三元未标箭头 | `{instructor.ID, student.ID, project.ID}` | 无基数约束 → 默认取**全部参与实体主键并集 + 关系属性**（P32 通则） |

**易错提醒**：(b) 别写成"教师 ID"——**永远选"多"侧**；(c) 别以为只有一种答案，1:1 **两侧都行**；(d) 三元在**没有箭头**时回到通则（并集），只有标了箭头才按"至多一个"裁剪。

</details>

**例题 4（弱实体集全流程）** 以 `section` 为例：(a) 为什么它是弱实体集？(b) 三件套记号是什么？(c) 它的"主键"怎么构成？(d) 转成关系模式后 `course_id` 出现在哪、起什么作用？(e) `sec_course` 识别关系的表要不要保留？

<details><summary>参考解答</summary>

**(a)** `section` 单靠 `sec_id, semester, year` **无法唯一标识**自己——不同课程可有同名班次；它的存在**依赖于 `course`**（先有课才有班），属**存在依赖**（existence dependent），故为弱实体集。

**(b)** 三件套：**双矩形**（弱实体集）、**双菱形**（识别关系 `sec_course`）、**discriminator 的虚线下划线**（`sec_id` 等区分属性）。

**(c)** 主键 = **识别实体的主键 + 自己的 discriminator**：

$$PK(section) = (course\_id,\ sec\_id,\ semester,\ year)$$

其中 `course_id` 来自 `course`，其余是 discriminator（P37）。

**(d)** 转换后 `course_id` **出现在 `section` 表内部**，作为列——它就是识别实体（course）的主键在此表中的**外键**。这印证了 P36：实体集里删掉的 `course_id`，在**关系模式里又被加回来**（作为连接宿主的纽带）。

**(e)** **不保留**。`sec_course` 的表是**冗余的**（P48）——`section` 表已包含它会出现的全部属性，直接删掉即可。

</details>

**例题 5（复合 vs 多值属性转换）** 设 `instructor` 有复合属性 `name(first_name, last_name)`、复合属性 `address(street, city)`、多值属性 `phone_numbers`、派生属性 `age`、单值 `ID`。请给出转换后的关系模式，并说明每个属性的处理方式。

<details><summary>参考解答</summary>

```sql
-- ① 主键 ID：单值 → 直接作为一列，并作主键
-- ② 复合 name、address：打平成多列（无歧义时可省前缀）
-- ③ 多值 phone_numbers：单独建表
-- ④ 派生 age：不建列（运行时由 date_of_birth 计算，若存了生日）
instructor(ID, first_name, last_name, street, city)

inst_phone(ID, phone_number)     -- 多值属性拆表：E的主键 + 多值属性
```

| 属性 | 类型 | 处理 |
|---|---|---|
| `ID` | 单值 | 一列 + 主键 |
| `name` | **复合** | **打平**为 `first_name, last_name`（原表加列） |
| `address` | **复合** | **打平**为 `street, city` |
| `phone_numbers` | **多值** | **单独建表** `inst_phone(ID, phone_number)`，一值一行 |
| `age` | **派生** | **不存**，由其它属性算出 |

**关键分界**（P43/P44）：**复合 → 在原表拆成多列（flatten）；多值 → 另起一张表（每个取值一行）**。多值示例：ID 22222 有 456-7890 与 123-4567 → `inst_phone` 中是 **2 行**。

</details>

**例题 6（关系集转换与冗余消除）** 对下列三种关系，各说明如何转成关系模式、会产生什么表、有何代价：(a) M:N 的 `takes`；(b) N:1 且学生**全参与**的 `stud_dept`；(c) N:1 但学生**部分参与**的 `advisor`。

<details><summary>参考解答</summary>

| 情形 | 做法 | 产生的表 | 代价/注意 |
|---|---|---|---|
| (a) M:N | **单独建表**：两端主键 + 关系属性 | `takes(ID, course_id, ..., grade)` | 无冗余，正常代价 |
| (b) N:1 全参与 | **不建关系表**，"多"侧加外键（P46） | `student(..., dept_name)` | 省一张表；因全参与，`dept_name` **不会为 NULL** |
| (c) N:1 部分参与 | 同样可加外键 | `instructor(..., advisor_id)` | ⚠️ **部分参与 → 可能产生 NULL 值**（P47：could result in null values） |

**辨析**：(b) 与 (c) 手法相同，**差别只在 NULL**——"多"侧若允许不参与，外键列就必须允许 NULL。这正是课件把"部分参与"单列为代价的原因。

**统一思想**（P46–P48）：**能塞进已有表就不另建表**——多对一/一对多塞"多"侧、一对一任选一侧、弱实体识别关系直接删（被吸收）。

</details>

**例题 7（特化/概化的方向与表示）** (a) 特化与概化方向分别？画法是否相同？(b) `person → instructor, secretary` 属于 disjoint 还是 overlapping？`person → employee, student` 呢？(c) 属性继承指什么？(d) 完整性约束默认是 total 还是 partial？如何显式标 total？(e) 特化转关系模式的两种方法及各自缺陷？

<details><summary>参考解答</summary>

| 小问 | 答案 |
|---|---|
| (a) | 特化**自顶向下**（在实体集内划子分组）；概化**自底向上**（合并共享特征的实体集）。**画法相同**（都用 ISA 三角），术语**可互换**（互为简单反转） |
| (b) | `instructor/secretary` → **disjoint**（一人不能同时是两者，P51）；`employee/student` → **overlapping**（可兼具，P51） |
| (c) | **属性继承**：低层实体集**继承所连高层实体集的全部属性与关系参与**（inherits all attributes and relationship participation） |
| (d) | **默认 partial**（P56：Partial generalization is the default）；显式标 total 需加关键字 `total` + **虚线**连到对应**空心箭头** |
| (e) | **方法1**：高层 + 低层各建表（低层含高层主键+本地属性）→ 缺陷：查完整信息**要访问两张表**；**方法2**：每个低层建含全部属性的表 → 缺陷：兼具者**属性冗余存储**（name/street/city 重复） |

**记忆钩子**：方向"**特下概上**"；默认"**partial**"；两法"**1 省存储要 JOIN，2 查得快有冗余**"。

</details>

**例题 8（聚合：从问题到模式）** 承上：`proj_guide` 为三元关系，现要记录"导师对学生在该项目上的评价"。(a) 直接新建 `eval_for` 关系有何冗余？为什么不能删 `proj_guide`？(b) 聚合如何解决？(c) 聚合后 `eval_for` 的关系模式含哪些列？`proj_guide` 的表还要吗？

<details><summary>参考解答</summary>

**(a) 冗余分析**（P58）：`eval_for` 与 `proj_guide` **信息重叠**——每个 `eval_for` 都对应一个 `proj_guide`，但**并非每个 `proj_guide` 都有 `eval_for`**（有的还没评价）。**不能删 `proj_guide`**，否则"指导关系"里那些"尚无评价"的记录就丢了。

**(b) 聚合（aggregation）**：**把 `proj_guide` 这段关系当作抽象实体**（treat relationship as an abstract entity），从而允许"**关系之间的关系**"——`eval_for` 直接关联"（被打包的 proj_guide）+ 评价"，把重叠的两层压成一层，**消除冗余**（eliminate this redundancy via aggregation）。

**(c)** 聚合建表三成分（P60）：**被聚合关系的主键 + 关联实体集的主键 + 描述属性**：

```text
eval_for(s_ID, project_id, i_ID, evaluation_id)
-- proj_guide 的模式是冗余的，可删
```

**判断口诀**：**要给"一段联系"再挂属性/再建联系 → 聚合**（否则只能靠冗余表硬凑）。

</details>

**例题 9（二元 vs 非二元的取舍与拆分）** (a) 三元 `parents(child, father, mother)` 为什么最好拆成两个二元关系？(b) `proj_guide` 为什么不适合拆？(c) 给出把任意三元 R(A,B,C) 拆成二元的通用步骤。(d) 拆分有什么固有代价？

<details><summary>参考解答</summary>

| 小问 | 答案 |
|---|---|
| (a) | 拆成 `father`、`mother` 两个二元后，**允许部分信息**——比如**只知道母亲**也能表达（P66）；强行用三元则要求三者同现 |
| (b) | `proj_guide` 是**天然非二元**的——"某学生在某项目上由某导师指导"必须三者同时在场才有意义，拆开反而失真（P66: some relationships are naturally non-binary） |
| (c) | 引**人工实体集 E** + 三个关系集 $R_A,R_B,R_C$（连 E–A、E–B、E–C）；给 E 建识别属性并把 R 的属性并入 E；对 R 中每条 $(a_i,b_i,c_i)$ 建新实体 $e_i$，加入 $(e_i,a_i)\in R_A$、$(e_i,b_i)\in R_B$、$(e_i,c_i)\in R_C$（P67） |
| (d) | ① **约束翻译可能不完全**——转换后可能出现**对应不到 R 任何实例的实例**（语义不等价）；② 需给 $R_A,R_B,R_C$ **补约束**以保证 $e_i$ 恰好连 A、B、C 各一个；③ 可改用**弱实体集**免去识别属性，但又引入弱实体机制（P68） |

**取舍总纲**：**能二元就二元**（灵活、支持部分信息），**天然多元别硬拆**（拆了要人工实体 + 补约束 + 可能不等价）。

</details>

**例题 11（综合：小系统 E-R 设计 + 转换）** 设计"图书借阅"系统：`Book`（ISBN, title, price）、`Publisher`（name, address）、`Reader`（rid, rname, phones 多值）、`Loan`（借阅，含 date 属性）。要求：读者必须借书（全参与），一本书可被多人借（多对多），书必须属于一个出版社（全参与），出版社可出多本书。请：(a) 画 E-R（文字描述）；(b) 指出各关系的基数与参与；(c) 给出转换后的关系模式。

<details><summary>参考解答</summary>

**(a)(b) E-R 描述**：

- 实体集：`Book`、`Publisher`、`Reader`（`phones` 为**多值属性**，双线椭圆）；
- 关系 1：`published_by(Book, Publisher)`——基数 **N:1**（多本书对一个出版社；箭头指向 Publisher），`Book` 侧**双线**（每本书必须有出版社 = 全参与），`Publisher` 侧**单线**（可出 0 本）；
- 关系 2：`loan(Book, Reader, date)`——基数 **M:N**（两边都无箭头），`Reader` 侧**双线**（每个读者必须借书 = 全参与），`Book` 侧单线；`date` 是**关系属性**（挂在菱形上）；
- 各关系主键：`published_by` → **"多"侧 Book 的主键 `{ISBN}`**；`loan` → **M:N 取并集 `{ISBN, rid}` + 关系属性 date**。

**(c) 转换后模式**：

```sql
publisher(name, address)                    -- 强实体，直接转换
book(isbn, title, price, name)              -- 强实体 + N:1"多"侧加外键 name（全参与→不为 NULL）
                                                  -- published_by 关系表被省掉（冗余消除手法①）
reader(rid, rname)                          -- 强实体（多值属性不在此）
reader_phone(rid, phone)                    -- 多值属性单独建表，一值一行
loan(isbn, rid, date)                       -- M:N 单独建表：两端主键 + 关系属性 date
```

**亮点说明**：`published_by` 因**全参与的 N:1** 被折叠进 `book`（手法①，无 NULL 之忧）；`loan` 是 M:N 必须单独建表；`phones` 多值拆成 `reader_phone`。**一张图里同时用到三类转换规则**——这正是本章的考法。

</details>

|---|---|---|
| 设计三阶段 | 需求 → 概念模式（选数据模型）→ 逻辑 + 物理 | conceptual schema 指示功能需求 |
| 逻辑设计两问 | 商业：存哪些属性；CS：哪些模式、属性怎么分 | business vs CS decision |
| 两大陷阱 | 冗余→不一致；不完整→建不了模 | 避免坏设计还不够，要优中选优 |
| 两条路线 | E-R（自顶向下建模）vs 规范化（形式化检测坏设计） | 第 7 章 = normalization |

| 关系/关系集 | 关系集 = $\{(e_1..e_n)\mid e_i\in E_i\}$；画菱形 | `(44553,22222) ∈ advisor` |

| 角色 | 同一实体集参与两端时须标角色 | prereq: course_id / prereq_id |
| 关系的度 | 二元最常见，三元罕见 | proj_guide 为三元 |
| 属性四类 | 简单/复合、单值/多值、派生 + 域 | phone 多值，age 派生 |
| 映射基数 | 1:1、1:N、N:1、M:N；"多"侧可为 0 | 二元关系最常用 |

### 核心思想总结

1. **本章是"从现实到表"的翻译学**：一端是自然语言描述的企业（需求），另一端是关系模式（表），中间靠 **E-R 图**这座桥。设计能力 = **建模能力**（画得对）+ **转换能力**（翻译得对），二者缺一不可。
2. **一切设计都在对抗两大陷阱**：冗余（存两遍→不一致）与不完整（存不下→没法建模）。整章的规则几乎都能溯源到这两条——**复合拆列、多值拆表、关系折叠进外键**是为了少冗余；**弱实体、聚合、非二元**是为了不丢表达力。
3. **约束的三个正交维度**：**基数**（至多几个 ↔ 箭头/`l..h`）、**参与**（必须吗 ↔ 单双线）、**主键**（怎么认 ↔ 下划线/discriminator）。读图时把三者拆开逐一看，就不会被组合搞晕。
4. **转换规则的本质是"空间换连接"的权衡**：单独建表（清晰、无冗余、要 JOIN）vs 折叠进已有表（省表、可能 NULL、可能隐式化）——**多对一全参与折叠、多对多保留、弱实体必然吸收识别关系**，都是这笔账的不同结论。
5. **扩展特性 = 给 E-R 加"复用与打包"能力**：特化/概化是**纵向复用**（继承）、聚合是**横向打包**（把联系当实体）、完整性约束是**继承的开关**（默认 partial）——三者让 E-R 能表达更复杂的企业结构而不失简洁。
6. **E-R 只是起点不是终点**：本章产出的是**概念/逻辑设计**，第 7 章的规范化要用函数依赖检测它是否还残留冗余，而物理设计、模式演进、数据流则在更后面展开——**先画对、再验对、再存对**。
