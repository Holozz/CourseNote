## 1. 文件的基本概念

### 1.1 文件的定义与特点

**通俗理解**：文件就是操作系统帮我们把磁盘上那些乱七八糟的"物理扇区"封装好之后，呈现给用户的一个有名字、有内容的"逻辑单元"。就像你不需要知道书的纸张是怎么印刷的，只需要知道书名和内容。

> **严谨定义**：文件是操作系统对存储设备物理属性进行抽象后定义的逻辑存储单位，是由创建者定义的一组相关信息的具名集合，由操作系统负责将其映射到物理存储设备上。

文件的三大核心特点：

|特点|说明|
|---|---|
|**Long-term existence（持久性）**|存储在磁盘等辅助存储器上，用户注销后不消失|
|**Sharable between processes（可共享性）**|文件有名字和访问权限，可被多个进程受控地共享|
|**Structure（结构性）**|文件可组织成层次或更复杂的结构，反映文件间关系|

**文件的逻辑视图**：文件在用户看来是一段**连续的逻辑地址空间**，可以按字节/字/记录访问，而不关心底层如何存储。

### 1.2 文件属性

文件属性保存在磁盘的**目录结构**中，是 OS 管理文件的元数据。

|属性|说明|
|---|---|
|**名称（Name）**|唯一的人类可读标识，仅以符号形式存储|
|**标识符（Identifier）**|文件系统内部唯一编号（如 inode 号），不对用户可见|
|**类型（Type）**|区分文件类型（文本、可执行、目录等）|
|**位置（Location）**|指向存储设备上文件实际位置的指针|
|**大小（Size）**|文件当前字节数|
|**保护（Protection）**|访问控制信息，控制谁可以读/写/执行|
|**时间、日期、用户标识**|创建时间、最近修改时间、所有者，用于安全审计|

> ⚠️ **重要**：目录结构本身和文件数据**都存放在磁盘上**，不是只有文件数据在磁盘。

### 1.3 文件类型

**Windows** 通过**文件扩展名**识别类型；**Unix/Linux** 通过文件头部的 **magic number（魔数）** 识别类型（更可靠，不依赖名称）。

|文件类型|常见扩展名|说明|
|---|---|---|
|executable|exe, com, bin|可直接运行的机器码程序|
|object|obj, o|编译后未链接的目标文件|
|source code|c, java, py|各语言源代码|
|batch|bat, sh|命令解释器脚本|
|text|txt, doc|文本数据|
|library|lib, so, dll|程序库文件|
|archive|zip, tar|打包/压缩文件|
|multimedia|mp3, avi|音视频二进制文件|

> 💡 **易错点**：Unix 系统的文件类型不靠扩展名，靠文件内容开头的 magic number，所以把 `.sh` 改成 `.txt` 不影响 Unix 识别其类型。

### 1.4 文件结构

文件在逻辑上可以有三种组织形式：

1. **无结构（None）**：纯字节/字序列，OS 不关心内容格式，由应用程序自行解析（Unix 哲学：一切皆字节流）
2. **简单记录结构（Simple record structure）**：
    - 按行分隔（Lines）
    - 固定长度记录（Fixed length）
    - 可变长度记录（Variable length）
3. **复杂结构（Complex Structures）**：
    - 格式化文档（如 Word .docx）
    - 可重定位加载文件（relocatable load file）

> 💡 后两种结构可以用第一种（字节序列）加上适当**控制字符**来模拟。

**谁来决定文件结构**？可以是操作系统（OS 负责解析），也可以是应用程序（OS 只管存字节）。Unix 选择了后者，更灵活。

## 2. 文件操作

### 2.1 基本操作集合

以下 **6 个基本操作**构成文件操作的最小集合，其他操作都可由它们组合实现：

|操作|说明|
|---|---|
|**Create**|在文件系统中分配空间，创建目录项|
|**Write**|在写指针（write pointer）位置写入数据，写完后指针后移|
|**Read**|在读指针（read pointer）位置读取数据，读完后指针后移|
|**Seek（Reposition）**|移动文件位置指针到指定位置，不做实际 I/O|
|**Delete**|释放文件占用空间，删除目录项|
|**Truncate（截断）**|清空文件内容但保留文件属性（如保留文件名、权限），把文件大小清零|

> 💡 **Truncate vs Delete**：Truncate 保留文件"外壳"（目录项、属性），只删数据；Delete 连外壳也删掉。

**Open 和 Close** 不在基本操作集合里，但是实际使用中非常关键：

- `Open(Fi)`：在磁盘的目录结构中搜索文件 Fi，将其目录项**加载到内存**中的打开文件表，返回一个文件描述符（fd）
- `Close(Fi)`：将内存中打开文件表里 Fi 的条目**写回磁盘**目录结构，释放内存中的条目

### 2.2 文件打开（Open）机制

为了管理已打开的文件，OS 维护以下几个数据结构：

```
进程 A                进程 B
  |                      |
  v                      v
进程打开表(per-process)  进程打开表(per-process)
  - 文件指针(fp)           - 文件指针(fp)  ← 每个进程独立的读写位置
  - 访问权限               - 访问权限
  - 指向系统打开表的指针    - 指向系统打开表的指针
         \                   /
          v                 v
       系统打开文件表(system-wide)
         - 文件打开计数（file-open count）
         - 磁盘位置（disk location）
         - 其他元信息
```

各字段含义：

|字段|作用|
|---|---|
|**Open-file table**|分为进程级和系统级，追踪所有已打开文件|
|**File pointer**|每个进程独立维护，记录上次读/写位置（即使多进程打开同一文件，fp 也互不影响）|
|**File-open count**|系统级计数，记录有多少进程打开了该文件；减到 0 才真正从系统打开表中移除|
|**Disk location**|文件在磁盘上的位置缓存，避免每次操作都访问磁盘目录|
|**Access rights**|每个进程打开文件时指定的访问模式（读/写/执行等）|

> ⚠️ **易错点**：文件指针（file pointer）是**每个进程独立**的，不在系统打开表里，在进程打开表里。多个进程打开同一文件，各自维护独立的读写位置。

### 2.3 文件锁（File Lock）

文件锁用于在多进程并发访问时协调对文件的访问，类似读写锁。

|类型|说明|类比|
|---|---|---|
|**Shared lock（共享锁）**|类似读锁，多个进程可同时持有|图书馆读书：多人可同时看同一本书|
|**Exclusive lock（互斥锁）**|类似写锁，同时只有一个进程可持有|修书：只能一人修，修的时候别人不能看|

文件锁的执行方式：

- **Mandatory（强制性）**：OS 强制执行，进程请求被锁定的文件时直接拒绝。**Windows** 采用此方式。
- **Advisory（建议性）**：OS 不强制，进程可以查询锁状态后自行决定是否等待。**Unix/Linux** 采用此方式（`flock`、`fcntl`）。

> ⚠️ **易错点**：Unix 的文件锁是建议性的（Advisory），程序必须主动检查锁状态并遵守，OS 本身不会阻止无视锁的访问。这与强制性锁（Mandatory）截然不同。

**Java 文件锁示例（理解语义）**：

```java
FileChannel ch = raf.getChannel();
// 对文件前半段加互斥锁（EXCLUSIVE = false）
FileLock exclusiveLock = ch.lock(0, raf.length()/2, false);
// ... 修改数据 ...
exclusiveLock.release();

// 对文件后半段加共享锁（SHARED = true）
FileLock sharedLock = ch.lock(raf.length()/2+1, raf.length(), true);
// ... 读取数据 ...
sharedLock.release();
```

> 💡 Java 的 `ch.lock(start, end, shared)` 第三个参数：`true` = 共享锁，`false` = 互斥锁。注意课件中常量定义 `EXCLUSIVE = false`，这是**反直觉**的，很容易考！

## 3. 文件访问方法

### 3.1 顺序访问

**最简单、最常见**的访问方式，像磁带一样从头到尾按顺序读写。

操作：

- `read next`：读当前位置数据，指针后移
- `write next`：写当前位置，指针后移
- `reset`：将指针归零（回到文件开头）

```
beginning        current position              end
|----------------|------------------------------|
        ◄ rewind            read/write ►
```

适用场景：编译器读源代码、顺序处理日志文件。

### 3.2 直接访问（随机访问）

可以**直接跳到文件的任意位置**读写，不需要从头扫描。

操作：

- `read n`：读第 n 个逻辑块
- `write n`：写第 n 个逻辑块
- `position to n`：定位到第 n 块，然后可以 `read next` / `write next`

其中 **n 是相对块号（relative block number）**，是相对于文件开头的偏移，而不是磁盘上的物理块号。OS 负责将相对块号映射到物理地址。

> 适用于**固定长度记录**组成的文件（如数据库）

**直接访问模拟顺序访问**（利用当前位置指针 cp）：

|顺序访问操作|直接访问实现|
|---|---|
|reset|cp = 0|
|read next|read cp; cp = cp + 1|
|write next|write cp; cp = cp + 1|

### 3.3 其他访问方法（索引访问）

在直接访问基础上建立**索引**，实现更快的查找：

**核心思想**：为文件建立索引（key → 逻辑记录号），索引放在内存中，通过索引快速定位记录，再用直接访问去读数据。

典型实现：**IBM 的 ISAM（索引顺序访问方法）**

- 小型**主索引**（常驻内存）→ 指向磁盘上的**二级索引块** → 指向实际数据
- 文件按键值有序排列
- 通过键至多 **2 次** 磁盘访问即可定位记录

```
内存中的主索引
  ↓
磁盘上的二级索引
  ↓
数据记录
```

> 💡 这是数据库 B+Tree 索引的思想原型。

## 4. 磁盘与存储结构

**层次关系**：物理磁盘 → 分区（Partition）→ 卷（Volume）→ 文件系统

|概念|说明|
|---|---|
|**分区（Partition）**|磁盘的物理划分，也叫"迷你磁盘"或"分片"；一个磁盘可有多个分区|
|**卷（Volume）**|包含文件系统的实体；可以是一个分区，也可以跨多个磁盘（如 RAID）|
|**RAID**|磁盘或分区的冗余阵列，用于容错保护|
|**卷目录/设备目录**|每个卷维护的关于本文件系统的元信息|

磁盘可以：

1. **不格式化**，直接作为裸设备（raw device）使用（数据库有时这样做，绕过文件系统）
2. **格式化**为某种文件系统后使用

一个 OS 中通常同时存在**多种文件系统**，例如 Solaris：

|文件系统|类型|用途|
|---|---|---|
|tmpfs|特殊|基于内存的临时文件，断电消失，速度极快|
|procfs|特殊|内核接口，`/proc` 下的进程信息|
|objfs|特殊|内核符号表，用于调试|
|lofs|特殊|回环文件系统，将一个 FS 挂载到另一个路径|
|ufs, zfs|通用|通用持久化文件系统|

## 5. 目录结构

### 5.1 目录的功能

**通俗理解**：目录就是文件系统的"索引书"，里面每一条记录（目录项）把文件名与文件实体对应起来。

> **严谨定义**：目录是包含所有文件信息的节点集合，本质上是一个**符号表（symbol table）**，将文件名映射为目录条目（包含文件属性和磁盘位置等信息）。目录结构和文件数据**都存在磁盘上**。

目录要支持的操作：搜索文件、创建文件、删除文件、列出目录、重命名文件、遍历文件系统。

目录结构设计的三个目标：

|目标|说明|
|---|---|
|**Efficiency（效率）**|能快速定位文件|
|**Naming（命名）**|方便用户命名；不同用户可用同名指不同文件；同一文件可有多个名字|
|**Grouping（分组）**|按属性对文件逻辑分组（如所有 Java 程序放一起）|

### 5.2 单级目录

**结构**：整个系统只有一个目录，所有文件都在里面。

```
directory: [cat][bo][a][test][data][mail][cont][hex][records]
               ↓   ↓   ↓    ↓     ↓    ↓     ↓    ↓    ↓
files:       (F) (F) (F)  (F)   (F)  (F)   (F) (F)  (F)
```

**缺点**：

- **Naming problem**：所有用户共用一个目录，不同用户不能有同名文件
- **Grouping problem**：无法按用户或类型分组，文件混在一起难以管理

### 5.3 两级目录

**结构**：顶层为主文件目录（Master File Directory, MFD），每个用户有独立的用户文件目录（User File Directory, UFD）。

```
MFD: [user1][user2][user3][user4]
        ↓       ↓
UFD1: [cat][bo][a][test]    UFD2: [a][data]
```

**优点**：

- 解决了命名冲突：不同用户可以有同名文件（`/user1/a` 和 `/user2/a` 不冲突）
- 搜索效率高：只需在当前用户目录中搜索
- 引入了**路径名（path name）**概念

**缺点**：用户之间难以共享文件。

### 5.4 树形目录

**结构**：将两级目录推广到任意层次，每个目录可包含文件和子目录，形成树状结构。这是现代 OS（Linux、Windows）的主要目录结构。

```
/root
 ├── spell/
 │   ├── stat
 │   ├── mail/
 │   │   └── prog/
 │   └── dist
 ├── bin/
 │   ├── find
 │   └── hex
 └── programs/
     └── ...
```

**关键概念**：

- **绝对路径**：从根目录 `/` 开始的完整路径，如 `/spell/mail/prog`
- **相对路径**：从当前工作目录（current working directory）出发的路径
- **删除目录**：删除一个目录 ⇒ 删除以该目录为根的整个子树

> ⚠️ **重要**：树形目录中**每个文件只有唯一路径**，不支持文件共享（同一文件无法出现在两个目录下）。

### 5.5 无环图目录

**动机**：树形目录不支持文件共享，但实践中多个用户/目录经常需要共享同一文件或子目录，于是引入**无环图目录（Acyclic-graph directory）**。

**结构**：允许同一文件/子目录有**多个父目录**，图中没有环。

**两种链接方式**：

- **硬链接（Hard link）**：目录项直接指向文件的 inode（磁盘上的实体），多个名字指向**同一个实体**。删除一个名字不影响文件，只有所有硬链接都删除（引用计数归零）才真正删文件。
- **软链接/符号链接（Soft link / Symbolic link）**：目录项存储的是另一个文件的路径字符串，相当于快捷方式。若原文件被删除，会断连，软链接变成**悬空指针（dangling pointer）**，尝试打开时会显示找不到文件

**悬空指针问题及解决方案**：

当一个目录删除了它指向的文件，持有该文件软链接的其他目录就会出现悬空指针。解决方案：

|方案|原理|
|---|---|
|**反向指针（Backpointers）**|文件记录所有指向它的目录项，删除时清理所有指针（记录大小可变，实现复杂）|
|**Daisy chain 组织**|用链表串联所有反向指针|
|**Entry-hold-count（引用计数）**|记录有多少目录项指向该文件，减到 0 才真正删除（即 inode 的 link count，硬链接就是这个原理）|

> ⚠️ **易错点**：硬链接和软链接的本质区别——硬链接删除任意一个名字，文件还在（只要还有其他硬链接）；软链接的原文件删除后，链接就失效（悬空）。

### 5.6 通用图目录

**结构**：允许目录结构中存在**环（cycle）**，即子目录可以通过链接指向其祖先目录。

**问题**：遍历时可能无限循环；垃圾回收复杂。

**如何保证无环（How do we guarantee no cycles?）**：

1. **只允许链接指向文件，不允许链接指向子目录**（最简单）
2. **垃圾收集（Garbage collection）**：整体扫描找到不可达节点
3. **每次添加链接时运行环检测算法**，检测是否引入环

> 💡 通用图目录主要是理论讨论，实际文件系统（如 ext4）通过限制软链接层数等方式避免环带来的问题。

## 6. 文件系统保护

### 6.1 访问类型

文件所有者/创建者应能控制：**谁（whom）** 可以做 **什么（what）**。

受控的访问类型：

|操作|说明|
|---|---|
|**Read**|读取文件内容|
|**Write**|修改文件内容|
|**Execute**|将文件作为程序运行|
|**Append**|向文件末尾追加内容（不能修改已有内容）|
|**Delete**|删除文件|
|**List**|列出目录内容（对目录的权限）|

### 6.2 Linux 文件权限

Linux/Unix 把用户分为三类，每类独立设置 RWX 三位权限：

```
权限字符串示例：-rwxr-xr--
                ↑↑↑↑ ↑↑↑  ↑↑↑
                │└┬┘ └┬┘  └┬┘
                │owner group public
                └文件类型（-=普通文件，d=目录，l=链接）
```

|用户类|含义|
|---|---|
|**owner（属主）**|文件的创建者/所有者|
|**group（属组）**|文件所属的用户组成员|
|**public/other（其他）**|系统上其他所有用户|

每类权限用 3 个二进制位（RWX）表示，也可用一个八进制数字表示：

|权限|二进制|八进制|
|---|---|---|
|rwx（全权）|111|7|
|rw-（读写）|110|6|
|r-x（读执行）|101|5|
|r--（只读）|100|4|
|--x（只执行）|001|1|
|---（无权）|000|0|

**示例**：`chmod 761 game`

- owner: 7 = rwx（读写执行）
- group: 6 = rw-（读写）
- public: 1 = --x（只执行）

**相关命令**：

```bash
chmod 761 game       # 修改权限
chgrp G game         # 将文件 game 的所属组改为 G
```

**读取 Unix 目录列表**（`ls -l` 输出解读）：

```
-rw-rw-r--  1 pbg staff 31200 Sep 3 08:30 intro.ps
↑↑↑ ↑↑↑ ↑↑↑
│ └─┘ └─┘ └─┘
│owner grp public
└文件类型（-普通文件，d目录）
```

- `drwx------`：目录，owner 全权，其他人无任何权限（私有目录）
- `drwxrwxrwx`：目录，所有人全权（危险！）

## 7. 例题

### 例题 1：文件打开表的理解

**题目**：进程 A 和进程 B 同时打开了同一个文件 `data.txt`。进程 A 读到文件中间位置后，进程 B 开始从文件头读取，问：

1. 进程 A 的读指针是否会受进程 B 读取操作的影响？
2. `data.txt` 在系统打开文件表中有几个条目？
3. 若 A 关闭文件，B 的访问是否受影响？

**解答**：

1. **不影响**。文件指针（file pointer）存放在**进程打开表（per-process open-file table）**中，每个进程独立维护，进程 B 的读取操作绝不会改变进程 A 的文件指针位置。
    
2. 系统打开文件表（system-wide open-file table）中 `data.txt` 只有 **1 个条目**（因为是同一个文件），但 file-open count = 2（两个进程打开了它）。每个进程的进程打开表中各有 1 条记录指向这个系统条目。
    
3. 进程 A 关闭后，file-open count 变为 1，**不为 0，所以系统打开表中的条目不会删除**，进程 B 继续正常访问。只有 file-open count 降到 0（最后一个进程关闭文件），该条目才从系统打开表中移除。

### 例题 2：文件锁的强制性 vs 建议性

**题目**：以下说法哪些正确？

- A. Windows 的文件锁是建议性的，进程可以无视它
- B. Unix 的 advisory 文件锁若被某进程无视，OS 不会阻止
- C. 共享锁（shared lock）同时只允许一个进程持有
- D. 互斥锁（exclusive lock）持有期间，其他进程无法获取共享锁

**解答**：正确答案为 **B、D**。

- A 错：Windows 是 Mandatory（强制性），OS 会强制执行，进程无法绕过。
- B 正确：Unix 是 Advisory（建议性），锁只是"建议"，进程完全可以无视，OS 不会强制。
- C 错：共享锁（类似读锁）允许**多个进程同时持有**，这是它的设计意图。
- D 正确：互斥锁持有时，其他进程既不能获取互斥锁，也不能获取共享锁（与共享锁互斥）。

### 例题 3：目录结构辨析

**题目**：分析以下场景，指出它属于哪种目录结构，并说明可能存在的问题：

用户 Alice 在 `/home/alice/project/` 下有文件 `code.c`；用户 Bob 在 `/home/bob/shared/` 下创建了一个软链接 `code_link -> /home/alice/project/code.c`；Alice 后来删除了 `code.c`。

1. 这是什么目录结构？
2. 删除 `code.c` 后 `code_link` 会发生什么？
3. 如果 Bob 创建的是硬链接而非软链接，结果会有何不同？

**解答**：

1. 这是**无环图目录（Acyclic-graph directory）**结构，通过链接实现文件共享。
    
2. `code.c` 被删除后，`code_link`（软链接/符号链接）变成了**悬空指针（dangling pointer）**。当 Bob 试图通过 `code_link` 访问文件时，OS 会报"No such file or directory"错误，因为它指向的路径已不存在。
    
3. 如果是**硬链接**：Alice 删除 `/home/alice/project/code.c`，只是删除了一个目录项（硬链接），文件的 inode 引用计数从 2 减为 1，**文件实际内容仍然存在**。Bob 的 `code_link` 仍然有效，可以正常访问。只有当所有硬链接（引用计数归零）都被删除，文件内容才真正从磁盘删除。

### 例题 4：文件访问方法与适用场景

**题目**：数据库系统需要频繁按员工编号（如 EMP001）直接查询某条员工记录，而不是从第一条扫描到目标条。请问：

1. 应使用什么访问方法？
2. 如果数据库中有 100 万条记录，如何高效实现？描述索引访问方法的工作流程。
3. 顺序访问能否模拟直接访问？反之呢？

**解答**：

1. 应使用**直接访问（direct access / random access）**，通过相对块号直接定位，无需从头扫描。
    
2. 使用**索引访问方法**（如 ISAM）：
    
    - 建立索引文件：`员工编号 → 逻辑记录号`，索引按键值排序
    - 将索引（或至少主索引）加载到**内存**
    - 查询 EMP001 时：先在内存主索引中找到对应的二级索引磁盘块号 → 读取该磁盘块的二级索引 → 得到 EMP001 的逻辑记录号 → 直接访问该记录
    - 最多 **2 次磁盘 I/O**（读二级索引块 + 读数据块）即可定位，效率远高于顺序扫描 100 万条。
3. **直接访问可以模拟顺序访问**（用当前位置指针 cp，每次 `read cp; cp++` 即可）；但**顺序访问无法模拟直接访问**（顺序访问无法直接跳到任意位置，只能从头扫到目标，效率极低）。

### 例题 5：Linux 权限计算

**题目**：某文件的权限字符串为 `drwxr-x---`，所有者为 alice，所属组为 dev。

1. 这是文件还是目录？
2. 用八进制表示该权限。
3. 用户 bob（不在 dev 组）是否可以进入该目录？
4. dev 组成员 carol 是否可以在该目录下创建文件？
5. `chmod 755 somefile` 后，somefile 的权限字符串是什么？

**解答**：

1. **目录**（首字符 `d` 表示 directory）。
    
2. owner=rwx=111=**7**，group=r-x=101=**5**，other=---=000=**0** → 八进制为 **750**。
    
3. **不可以**。bob 属于 other 类，权限为 `---`，没有任何权限，无法进入（execute 权限在目录上表示"进入"权限）。
    
4. **不可以**。dev 组成员（carol 属于 group 类）权限为 `r-x`，有读和执行（进入）权限，**但没有写（w）权限**，因此不能在该目录下创建文件。创建文件需要对目录有写权限。
    
5. 755 → owner=7=rwx，group=5=r-x，other=5=r-x → `-rwxr-xr-x`。

### 例题 6：通用图目录的环检测问题

**题目**：在一个允许目录间任意链接的文件系统（通用图目录）中，为什么单纯"只让文件被删除时，引用计数减到 0 才删除"的策略在这里可能失效？应如何处理？

**解答**：

引用计数（Entry-hold-count）方案在**无环图**下可以正确工作：当所有指向文件的链接都删除，计数归零，文件删除。

但在**通用图（有环）**情况下会出现问题：假设目录 A 有子目录 B，B 又链接回 A（形成环），当用户"删除" A 和 B 时，A 的引用计数因 B 对它的链接而不为 0，B 的引用计数因 A 对它的链接也不为 0——两者互相引用，引用计数永远不为 0，但这两个目录实际上已经**不可达（unreachable）**，造成内存/磁盘泄漏。

解决方案：

1. **限制链接只指向文件，不指向目录**（最简单有效，防止目录间成环）
2. **垃圾收集（Garbage collection）**：定期扫描整个文件系统，找到不可从根目录到达的节点，回收其空间（类似 JVM 的 GC）
3. **每次添加链接时执行环检测算法**（类似拓扑排序，有代价但能防患于未然）

> 💡 现代 Linux（ext4）的 `ln` 命令默认不允许对目录创建硬链接，正是为了避免这个问题。
