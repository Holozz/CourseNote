## 1. 文件系统结构概述

### 核心概念

**文件**是逻辑存储单元，是相关信息的集合。文件系统驻留在**辅助存储（磁盘）** 上，其核心任务是：

- 将**逻辑文件系统**映射到**物理外存设备**；
- 提供对磁盘数据的高效、方便的存储、定位与检索；

### 磁盘特性

磁盘支持两种重要特性，使文件系统得以建立其上：

1. **原地重写（in-place rewrite）**：可以直接覆盖已有数据，而不像磁带只能顺序写；
2. **随机访问（random access）**：可以任意跳转到磁盘的任何位置读取数据；

磁盘 I/O 以**扇区块**为单位传输，通常每块 **512 字节**（或更大，如 4096 字节）。

### 文件控制块（FCB, File Control Block）

> **严谨定义**：FCB 是操作系统为每个文件维护的、存储该文件所有元数据（metadata）的数据结构。在 UNIX/Linux 中称为 **inode**，在 Windows NTFS 中对应**主文件表（MFT）条目**。

FCB 包含：文件权限、时间戳（创建/访问/修改）、所有者与组、ACL、文件大小、以及**指向文件数据块的指针**。

> ⚠️ **易错**：FCB 存储的是文件的**元数据**，不是文件的实际数据内容。文件名通常不存在 FCB/inode 中，而是在目录项里。

## 2. 分层设计的文件系统

文件系统采用**分层架构**，每层向上提供服务、向下调用服务。

```
应用程序
    ↓
逻辑文件系统 (Logical File System)
    ↓
文件组织模块 (File-Organization Module)
    ↓
基本文件系统 (Basic File System)
    ↓
I/O 控制 (I/O Control)
    ↓
设备 (Devices)
```

### 各层职责详解

| 层次          | 职责                                        | 典型操作示例                          |
| ----------- | ----------------------------------------- | ------------------------------- |
| **I/O 控制层** | 设备驱动程序，管理物理 I/O，将低级硬件的相关命令输出到硬件控制器        | 发出命令：读驱动器1, 柱面72, 磁道2, 扇区10     |
| **基本文件系统**  | 发出通用块命令（如"检索块123"），管理内存缓冲区与缓存             | 分配/释放/替换缓冲区                     |
| **文件组织模块**  | 知道文件、**逻辑地址与物理块的对应关系**；管理空闲空间             | 将逻辑块号转换为物理块号                    |
| **逻辑文件系统**  | 管理元数据；**维护 FCB**；将文件名转换为文件号/句柄/位置；目录管理；保护 | `open("file.txt")` → 找到对应 inode |

### 缓冲区 vs 缓存

|         概念         | 作用                                                                                                                               | 实现                                                                                                                                           |
|:--------------------:|:---------------------------------------------------------------------------------------------------------------------------------- |:---------------------------------------------------------------------------------------------------------------------------------------------- |
| **缓冲区（Buffer）** | 保存**传输中**的数据（临时中转）利用内存中的存储空间暂存从磁盘读取的盘块数据。这些数据在逻辑上是磁盘内容的副本物理上则驻留在内存中 | 一种是在内存中开辟固定大小的专用缓存区；另一种是将系统空闲内存作为动态缓冲池，供请求分页系统和磁盘I/O子系统共享使用                            |
|  **缓存（Cache）**   | 保存**常用**数据（提高命中率）                                                                                                     | 实现方法包括：<br>1)采用硬件缓冲器，但由于成本较高，除一些关键部位外一般不采用。<br>2)利用内存作为缓冲区，本节要介绍的正是由内存组成的缓冲区。 |

> ⚠️ **分层的利弊**：分层设计**降低了复杂性和冗余**，但**增加了系统调用开销**，可能降低性能。

### 常见文件系统格式

- CD-ROM：ISO 9660
- Unix：UFS、FFS
- Windows：FAT、FAT32、**NTFS**
- Linux：**ext3、ext4**（主流）
- 新型：ZFS、GoogleFS、FUSE

## 3. 文件系统的磁盘与内存实现

### 3.1 磁盘上的结构

磁盘上存储的文件系统结构（从低地址到高地址，典型布局）：

```
| 引导控制块 | 逻辑卷控制块(超级块) | 目录结构 | 文件控制块(inode)区 | 数据块区 |
```

- **引导控制块（Boot Control Block）**：仅当该卷包含操作系统时才需要，通常是卷的**第一个块**。包含系统引导所需信息。
- **逻辑卷控制块（超级块/主文件表）**：存储整个卷的总体信息：块总数、可用块数、块大小、空闲块的指针/数组。
- **目录结构**：组织文件，存储文件名与对应 inode 编号的映射。
- **FCB（inode）区**：每个文件一个 FCB，存储文件元数据。

### 3.2 文件控制块 FCB / inode

FCB 字段示例：

```
┌─────────────────────────────────────┐
│  file permissions（权限位）           │
├─────────────────────────────────────┤
│  file dates (create, access, write) │
├─────────────────────────────────────┤
│  file owner, group, ACL             │
├─────────────────────────────────────┤
│  file size（文件大小）                │
├─────────────────────────────────────┤
│  file data blocks（数据块指针）        │
└─────────────────────────────────────┘
```

> 💡 **每个文件有唯一标识号**（inode number），通过这个号码而非文件名来定位文件。这就是为什么**硬链接**可以让多个文件名指向同一个 inode。

### 3.3 内存中的文件结构

操作系统在**内核内存**中维护以下结构：

1. **文件系统挂载表（Mount Table）**：记录已挂载的文件系统及其挂载点、类型；
2. **系统范围的打开文件表（System-wide Open File Table）**：全局共享，包含所有已打开文件的 FCB 副本及其他信息（如引用计数），存储与进程无关的文件属性，如磁盘位置、文件大小、访问时间等；每项都包含一个打开计数器(Open Count),记录有多少进程打开了该文件。
3. **每进程的打开文件表（Per-Process Open File Table）**：每个进程独立维护，包含指向系统打开文件表中对应条目的**指针**，以及该进程私有的信息（如文件偏移量，当前读/写指针、访问权限及文件打开模式。该表中的每一项均指向系统打开文件表的对应项，实现资源共享与独立控制的统一。

#### 文件打开与读取流程

**打开文件 `open(filename)` 的过程**（图12-3(a)）：

1. 在用户空间调用 `open()`；
	系统首先根据用户提供的文件路径逐级遍历目录，将所需的目录文件从磁盘加载至内存
2. 内核在内存目录结构中搜索文件名；
	定位目标文件的目录项；随后从中提取其**索引节点编号**
3. 并以**此**为关键字在系统打开文件表中查找对应项
	若未缓存，从磁盘的目录结构和 FCB 中读取；
4. 在系统打开文件表中创建条目（含 FCB 副本）：
	若未找到，则从磁盘读取该索引节点至内核缓冲区，在系统表中创建新项，并将打开计数初始化为1;若已存在，则仅将该项的打开计数加1。
5. 在进程打开文件表中创建条目（含指向系统表的指针）
	在发起请求的进程所属的进程打开文件表中分配一个新表项，用于记录其指向系统表项的索引；
6. 将该表项的索引号作为**文件描述符**（Unix）或**文件句柄**（Windows）返回给用户。

**读取文件 `read(fd, buf, n)` 的过程**（图12-3(b)）：

1. 通过文件描述符（索引）找到进程打开文件表中的条目；
2. 通过指针找到系统打开文件表中的 FCB；
3. 根据 FCB 中的数据块指针，找到磁盘上的数据块；
4. 将数据读入内核缓冲区，再复制到用户缓冲区。

> ⚠️ **易错**：文件描述符（fd）是进程打开文件表的**索引**，它指向进程表条目，进程表条目再指向系统打开文件表。fd 不是 inode 号，不是磁盘地址。

## 4. 目录实现
目录本质上是文件名到 FCB（或 inode 号）的**映射表**。主要有两种实现方式：
### 线性列表（Linear List）

将文件名与指向数据块的指针按顺序存储：

- **优点**：实现简单；
- **缺点**：查找时间是 O(n)，线性搜索，文件多时极慢；
- **改进**：保持按字母序排列（用链表或 B+ 树）；

### 哈希表（Hash Table）

在线性列表的基础上，额外维护一个哈希结构：

- **优点**：大幅减少目录搜索时间，接近 O(1)；
- **缺点**：存在**哈希碰撞**（两个不同文件名哈希到同一位置）；
    - 解决方法：**链式溢出（chained-overflow）**，即碰撞桶用链表串接；
- 固定大小的条目才真正好用，变长文件名需要特殊处理；

> [!Warning] **易错**：哈希表不能消除碰撞，只能处理碰撞。碰撞会导致同一哈希槽指向多个文件，需要顺序比较才能确认。

## 5. 磁盘块分配方法

**核心问题**：如何把一个文件的数据分配到磁盘的各个块上？
### 5.1 连续分配（Contiguous Allocation）

#### 原理

每个文件占用一组**连续**的磁盘块。目录项只需记录：**起始块号**和**文件长度（块数）**。
由于磁盘地址本身具有线性顺序，这种布局使得进程访问文件时所需的**寻道次数**和**寻道时间**最小
#### 地址转换

给定逻辑地址 LA，块大小为 512 字节：

```
Q = LA / 512      （商 = 相对于起始块的偏移块数）
R = LA mod 512    （余数 = 块内偏移）

物理块号 = 起始块号 + Q
块内偏移 = R
```

**例**：文件 `mail`，起始块 19，访问逻辑地址 LA = 1200

- Q = 1200 / 512 = 2（整除），R = 1200 mod 512 = 176
- 物理块 = 19 + 2 = 21，块内偏移 = 176

#### 优缺点

| 优点                                           | 缺点                         |
| -------------------------------------------- | -------------------------- |
| **性能最好**（寻道次数最少）                             | 必须分配连续的空间，容易产生大量**外部碎片**   |
| 实现简单                                         | 需要提前知道文件大小                 |
| **同时支持顺序访问和直接访问**                            | 文件增长困难（需要搬移）               |
| 顺序访问高效且速度快，因为文件所占的块通常位于一条或少数几条相邻磁道上，磁头移动距离最小 | 碎片整理需要离线（downtime）或在线（代价高） |

> ⚠️ **重点**：连续分配会产生**外部碎片**，不会产生内部碎片（因为块是连续的，不存在"分配了但用不到"的块）。

### 5.2 基于扩展的系统（Extent-Based）

是连续分配的**改进**，用于 Veritas File System 等：

- 一个**扩展（Extent）** = 一段连续的磁盘块；
- 一个文件由**一个或多个扩展**组成；
- 每个扩展记录：**起始地址 + 块数 + 指向下一个扩展的指针**；
- 兼顾了连续性（扩展内连续）和灵活性（跨多个扩展）；

### 5.3 链接分配（Linked Allocation）（隐式链接）

#### 原理

每个文件是磁盘块组成的**链表**，每个块末尾存放指向下一块的**指针**，文件以 `nil` 指针结束。目录项只记录：**起始块号**和**结束块号**。

```
目录项: jeep | start=9 | end=25

磁盘块链: 9 → 1 → 5 → 13 → 22 → 25 → nil
```

#### 优缺点

| 优点              | 缺点                    |
| --------------- | --------------------- |
| **无外部碎片**       | **不支持随机访问**（只能顺序遍历）   |
| 文件大小可动态扩展       | 每块都占用空间存指针（指针浪费空间）    |
| 无需连续空间          | **可靠性差**：一个指针损坏导致文件截断 |
| 文件的插入删除修改操作十分便捷 | 访问第 n 块需要 n 次磁盘 I/O   |

**改进**：*块分组*策略将多个块聚合为**簇（cluster）**，减少指针数量，但会增加内部碎片。

> ⚠️ **重点**：链接分配有效用于**顺序访问**，不适合随机访问。指针断裂（pointer corruption）是其最大的可靠性隐患。

### 5.4 文件分配表（FAT, File Allocation Table）（显式链接）

FAT 是链接分配的一个**重要变种**：将所有块的"下一块指针"集中存放在磁盘开头的一张大表中，而不是分散在每个块内。将用于链接文件各物理块的指针集中存放在内存中的一张全局表中，该表在整个文件系统中仅设一张，称为文件分配表(File AllocationTable,FAT)
FAT的每个表项对应一个磁盘块，并存放指向下一个盘块的指针。因此，文件目录项只需记录该文件的起始块号，后续所有块号均可通过依次查询FAT获得。例如，某磁盘共有100个盘块，其中存放了两个文件：文件“aaa”占用三个块，链接顺序为2→8→5;文件“bbb”占用两个块，链接顺序为7→1。其余盘块均为空闲块
![[Pasted image 20260610153937.png|400]]

```
目录项: test | start=217

FAT表:
  ...
  217 → 618
  ...
  618 → 339
  ...
  339 → -1  (文件结束)
```

**优点**：
- FAT 在系统启动时被**缓存在内存中**，使随机访问速度大幅提升（不需要读磁盘块去找指针）；
- 支持 **顺序访问** 和 **直接访问**
- Windows FAT/FAT32/exFAT 均基于此；

**缺点**：
- FAT 表本身占用磁盘空间，且需要保护；
- 对于大磁盘，FAT 表很大，内存开销显著；

> ⚠️ **FAT vs 纯链接分配的区别**：FAT 把指针集中管理，可以在不读数据块的情况下遍历整个文件的块链，大大提升了随机访问效率。

### 5.5 索引分配（Indexed Allocation）

#### 原理

每个文件有自己的**索引块（Index Block）**，索引块中集中存放该文件所有数据块的地址。目录项只记录**索引块号**。

```
目录项: jeep | index_block=19

索引块 19:
  [0] → 9
  [1] → 16
  [2] → 1
  [3] → 10
  [4] → 25
  [5] → -1  (空)
  ...
```

#### 地址转换（小文件，单级索引）

块大小 = 512 字节，最大文件 = 256KB（索引块放得下 512/4=128 个指针，能寻址 128×512 = 64KB；若块大小更大则更多）：

```
Q = LA / 512   → 进入索引表的位移（第 Q 个指针）
R = LA mod 512 → 数据块内偏移
```

#### 大文件的处理：多级索引

**问题**：单个索引块能存的指针数有限，超大文件怎么办？

**方案一：链接索引块** 索引块装满后，最后一个槽存放下一个索引块的地址（类似链表），无大小限制。

**方案二：两级索引**

外部索引块的每个指针指向一个二级索引块，二级索引块的指针才指向数据块。

以 512 字节块为例：

```
Q1 = LA / (512 × 512)       → 进入外部索引的位移
R1 = LA mod (512 × 512)

Q2 = R1 / 512               → 进入二级索引块的位移
R2 = R1 mod 512             → 数据块内偏移
```

4K 块、32位地址时：单个索引块可存 1K（4KB/(4B/个地址)）个指针，两级索引最大文件 = 1024 × 1024 × 4KB = **4GB**

**方案三：组合方案（UNIX inode 的经典设计）**

这是最实用的方案，inode 中包含：

```
inode
├── 文件元数据
├── 12 个直接块指针 (direct blocks)       → 直接指向数据块
├── 1 个一级间接指针 (single indirect)    → 指向一个索引块，索引块存数据块地址
├── 1 个二级间接指针 (double indirect)    → 指向外部索引块，外部索引块指向二级索引块
└── 1 个三级间接指针 (triple indirect)    → 三层索引
```

以 4KB 块、4字节指针为例：

- 直接块：12 × 4KB = 48KB
- 一级间接：1024 × 4KB = 4MB
- 二级间接：1024 × 1024 × 4KB = 4GB
- 三级间接：1024³ × 4KB = 4TB

这样**大多数小文件只用直接块**，访问只需 1~2 次 I/O；大文件才用多级索引，权衡很好。

> ⚠️ **重点**：组合方案的设计哲学——绝大多数文件都是小文件，对小文件要快，对大文件要能支持。注意不同级别的**I/O 次数**不同（直接块 1 次，一级间接 2 次，二级间接 3 次）。

### 5.6 各分配方法性能比较

| 特性     | 连续   | 链接     | FAT      | 索引（inode） |
| ------ | ---- | ------ | -------- | --------- |
| 顺序访问   | ✅ 最优 | ✅ 好    | ✅ 好      | ✅ 好       |
| 随机访问   | ✅ 好  | ❌ 差    | ✅ 缓存后好   | ✅ 好       |
| 外部碎片   | ❌ 有  | ✅ 无    | ✅ 无      | ✅ 无       |
| 内部碎片   | ✅ 少  | 有（簇）   | 有（簇）     | ✅ 少       |
| 文件动态增长 | ❌ 难  | ✅ 易    | ✅ 易      | ✅ 易       |
| 可靠性    | ✅ 高  | ❌ 指针断裂 | 中（FAT损坏） | ✅ 较高      |

## 6. 空闲空间管理
文件系统需要知道哪些块是空闲的，以便分配新块。
### 6.1 位图法（Bit Map / Bit Vector）

用一个位（bit）表示一个块的状态：`1` = 空闲，`0` = 已占用

```
bit[i] = 1  → block[i] 空闲
bit[i] = 0  → block[i] 已被占用
```

**查找第一个空闲块的计算**：

```
块号 = (每个字的位数) × (值为0的字的个数) + 第一个1位在该字中的偏移
```

CPU 有专门指令可以快速返回一个字中第一个"1"位的位置

**空间开销计算**：

```
块大小 = 4KB = 2¹² 字节
磁盘大小 = 2⁴⁰ 字节（1TB）
位图大小 = 2⁴⁰ / 2¹² = 2²⁸ bits = 32MB
（若每 4 块为一簇，则只需 8MB）
```

**优点**：实现简单，**易于找到连续空闲块**（扫描位图中连续的 1）；

**缺点**：位图本身需要额外空间，大磁盘位图较大，可能无法完全常驻内存；

### 6.2 链表法（Free List）

将所有空闲块用**链表**串接起来，头指针指向第一个空闲块，每个空闲块中存下一个空闲块的地址。

**优点**：

- 不浪费额外空间（空闲块本身存指针）；
- 记录了空闲块总数时，无需遍历整个链表；

**缺点**：

- **难以找到连续空闲块**（因为空闲块散布在磁盘各处）；
- 每次分配/释放需要修改链表；

### 6.3 分组法与计数法

**分组法（Grouping）**：

改进链表，第一个空闲块中存储接下来 n-1 个空闲块的地址，外加一个指向下一组的指针。这样一次 I/O 就能获得 n 个空闲块地址，减少了 I/O 次数。

**计数法（Counting）**：

利用"空间通常被连续分配和释放"的规律，每个条目记录：**第一个空闲块的地址** + **后续连续空闲块的数量**。适合连续分配、扩展分配的场景。

### 6.4 空间映射 Space Maps（ZFS）

专为超大文件系统设计（ZFS 使用）：

- 大文件系统的位图可能高达 GB 级，无法全部载入内存；
- 将磁盘空间划分为**元盘（metaslab）**单元；
- 每个 metaslab 有一个**space map**（使用计数算法）；
- Space map 以**日志形式**记录所有块操作（时间顺序），而非直接修改文件系统结构；
- 使用 metaslab 时，将其 space map 加载到内存中的**平衡树**（按偏移量索引），重放日志，合并相邻空闲块；

> 💡 Space Maps 的本质是：**懒惰求值 + 日志合并**，避免了频繁更新大型位图结构。

## 7. 效率与性能

### 影响效率的因素

- 磁盘分配和目录算法的选择；
- 目录项中保存的数据类型；
- 元数据结构是预分配还是按需分配；
- 数据结构是固定大小还是可变大小；

### 7.1 缓冲区缓存与页缓存

**性能优化思路**：

- **保持数据与元数据相邻**：减少寻道时间；
- **缓冲区缓存（Buffer Cache）**：内存中专门用于缓存频繁访问的磁盘块；
- **同步写（Synchronous Write）**：写操作必须真正落盘才返回确认，**无缓冲**，保证一致性但慢；
- **异步写（Asynchronous Write）**：数据写入缓冲区即返回，后台再写磁盘，**更快但有数据丢失风险**；
- **Free-behind**：顺序读时，读完一块立即释放其缓存，为后续块腾出空间；
- **Read-ahead（预读）**：在请求当前块的同时预取下一块（顺序访问优化）；

> 💡 读通常比写**慢**吗？——这取决于缓存命中率：写可以异步缓冲后立即返回，而读必须等数据就绪；但若读命中缓存则很快。这是课件中故意问的一个反直觉问题（"Reads frequently slower than writes?"）。

**页缓存（Page Cache）**：

- 使用**虚拟内存技术**，以页（而非磁盘块）为单位缓存；
- 内存映射 I/O（mmap）使用页缓存；
- 普通文件系统 I/O（read/write）使用缓冲区缓存；

### 没有统一缓存时的双缓存问题

```
memory-mapped I/O ↔ page cache ↔ buffer cache ↔ file system
           read/write I/O ↗
```

同一份数据可能**同时存在于页缓存和缓冲区缓存**，浪费内存，且存在一致性问题（double caching）。

### 7.2 统一缓冲区缓存（Unified Buffer Cache）

**定义**：使用**同一个页缓存**来缓存内存映射页和普通文件系统 I/O，消除双重缓存。

```
memory-mapped I/O ↘           ↗ read/write I/O
                   buffer cache
                        ↕
                   file system
```

**优点**：消除 double caching，统一管理内存；

**新问题**：哪类缓存优先？用什么替换算法（LRU？ARC？）？这是操作系统设计的权衡问题。

> ⚠️ **易错**：统一缓冲区缓存是用**同一片内存**服务 mmap 和 read/write，不是两套独立的缓存系统合并。

## 8. 恢复与一致性

### 8.1 一致性检查（Consistency Checking）

**问题来源**：系统崩溃时，内存缓冲区中尚未写回磁盘的数据丢失，导致磁盘上的目录结构与数据块不一致（如：目录说文件有5个块，但只有3个块有效数据）。

**解决方法**：

- 启动时运行一致性检查程序（如 Unix 的 `fsck`，Windows 的 `chkdsk`）；
- 比较目录结构与磁盘数据块的信息，尝试修复不一致；
- **缺点**：速度慢，有时无法完全修复；

**备份与恢复**：

- 定期将磁盘数据备份到其他存储设备（磁带、另一块磁盘、光学存储）；
- 出现数据丢失时，从备份恢复；

### 8.2 基于日志的文件系统（Log-Structured / Journaling）

这是现代文件系统（ext3、ext4、NTFS）普遍采用的方案：

#### 核心思想

将每次**元数据更新**作为一个**事务（Transaction）**先写入日志，再异步应用到文件系统。

#### 详细流程

```
1. 开始事务，将元数据更新内容顺序写入日志（log）
2. 事务写入日志完成 → 认为"已提交（committed）"
   （此时文件系统本身还未更新）
3. 异步地将日志中的事务应用到文件系统结构
4. 文件系统结构更新完成 → 从日志中删除该事务
```

#### 崩溃恢复

- 若崩溃发生在步骤1（事务未完全写入日志）：直接丢弃该事务，文件系统一致；
- 若崩溃发生在步骤3（事务已在日志中，但未完全应用）：重启后**重放（replay）**日志中未完成的事务；

#### 优点

- **快速恢复**：只需重放日志，不需要扫描整个磁盘；
- **消除元数据不一致**的可能性；
- 日志是顺序写入，性能较好；

> ⚠️ **易错点**：日志记录的是**元数据**更新事务，不一定记录文件数据（取决于日志模式：metadata-only 或 data journaling）。事务"已提交"的含义是**已写入日志**，不是已写入文件系统！

## 9. 例题与综合练习

### 例题 1：连续分配地址转换（★★★）

**题目**：某文件系统块大小为 512 字节，采用连续分配。文件 `data` 起始块为 36，文件大小为 10 块。现要访问该文件的逻辑地址 LA = 1800（字节）。

1. 计算访问的物理块号；
2. 计算块内偏移；
3. 如果逻辑地址 LA = 5300，是否合法？

**解答**：

```
块大小 = 512 字节
LA = 1800

Q = 1800 / 512 = 3  （整数部分，即第 3 块，0起）
R = 1800 mod 512 = 1800 - 3×512 = 1800 - 1536 = 264

物理块号 = 36 + 3 = 39
块内偏移 = 264

LA = 5300:
Q = 5300 / 512 = 10（整数部分）
文件只有 10 块（块号 0~9），第 10 块超出范围，非法访问。
```

---

### 例题 2：索引分配地址转换（★★★☆）

**题目**：某文件系统块大小为 512 字节，采用单级索引分配。文件 `jeep` 的索引块为第 19 块，索引块内容依次为：[9, 16, 1, 10, 25, -1, -1, -1]。现访问逻辑地址 LA = 1030。

1. 计算应访问的数据块号；
2. 计算块内偏移。

**解答**：

```
Q = 1030 / 512 = 2  （访问索引块的第 2 项，0起）
R = 1030 mod 512 = 1030 - 1024 = 6

索引块第 2 项 = 1（物理块号）
块内偏移 = 6

需要 2 次 I/O：第 1 次读索引块 19，第 2 次读数据块 1。
```

---

### 例题 3：两级索引地址转换（★★★★）

**题目**：某文件系统块大小为 512 字节，指针大小 4 字节，采用两级索引分配，每个索引块可存 128 个指针（512/4=128）。访问逻辑地址 LA = 200,000 字节。

1. 计算访问的一级索引块位移 Q1；
2. 计算二级索引块位移 Q2；
3. 计算块内偏移 R；
4. 共需几次 I/O（假设索引块不在缓存中）？

**解答**：

```
每个一级索引块可寻址：128 × 512 = 65,536 字节

LA / (512 × 128) = 200,000 / 65,536 = 3 余 3,392
  Q1 = 3           → 进入外部索引表的第 3 项

R1 = 3,392
R1 / 512 = 3,392 / 512 = 6 余 320
  Q2 = 6           → 进入该二级索引块的第 6 项
  R = 320          → 数据块内偏移

I/O 次数：
  1. 读外部索引块（outer index）
  2. 读一级索引块（第 Q1=3 项指向的块）
  3. 读数据块（第 Q2=6 项指向的块）
共 3 次 I/O。
```

---

### 例题 4：位图法空闲块管理（★★★）

**题目**：某磁盘共有 32 个块，当前位图（每位对应一个块，1=空闲）如下（从 bit 0 开始）：

```
字0（块0-15）: 0000 1111 0000 0110   （十六进制 0x0F06）
字1（块16-31）: 1100 0000 0000 0001  （十六进制 0xC001）
```

1. 哪些块是空闲的？
2. 如果要分配 3 个连续块，最小起始块号是多少？
3. 使用公式计算第一个空闲块号（每字 16 位）。

**解答**：

```
字0 = 0000 1111 0000 0110（高位在前，bit 0 对应最高位）
空闲位（值为1）：bit 4~7（块4~7），bit 9~10（块9~10）
→ 空闲块：4, 5, 6, 7, 9, 10

字1 = 1100 0000 0000 0001
空闲块：16, 17, 31

2. 连续3块：块4,5,6 满足（最小起始 = 4）

3. 第一个空闲块：
   字0 = 0x0F06，不全为0（含有1），第一个1在 bit 4（从高位数）
   块号 = 16 × 0 + 4 = 4
```

---

### 例题 5：inode 组合方案最大文件大小（★★★★）

**题目**：某 UNIX 文件系统，块大小 4KB，指针大小 4 字节（每块可存 1024 个指针）。inode 中有 12 个直接块指针、1 个一级间接指针、1 个二级间接指针、1 个三级间接指针。

1. 计算最大文件大小；
2. 若要访问文件逻辑偏移 = 100MB 处的字节，需要几次 I/O（忽略 inode 读取，所有索引块均不在缓存中）？

**解答**：

```
直接块：12 × 4KB = 48KB
一级间接：1024 × 4KB = 4MB
二级间接：1024 × 1024 × 4KB = 4GB
三级间接：1024³ × 4KB = 4TB

最大文件大小 ≈ 4TB（由三级间接主导）

2. 100MB = 102,400KB
   直接块覆盖：48KB（不够）
   一级间接覆盖：48KB + 4MB = 4144KB（不够）
   二级间接覆盖：4144KB + 4GB（100MB 在此范围内）

   需要通过二级间接访问：
   I/O 1：读一级间接块（二级间接的外部索引块）
   I/O 2：读二级间接的内层索引块
   I/O 3：读实际数据块
   共 3 次 I/O。
```

---

### 例题 6：日志文件系统崩溃分析（★★★）

**题目**：系统执行"创建文件 foo"操作，涉及以下元数据更新：

1. 分配一个 inode；
2. 在目录中添加文件名与 inode 号的映射；
3. 更新空闲块位图；

系统在操作 2 完成后（3 尚未完成）发生崩溃。分别描述以下情形下的结果：

- A. 无日志文件系统；
- B. 有日志文件系统（只记录元数据事务）；

**解答**：

A. 无日志：

- 位图未更新，inode 被分配但系统认为对应磁盘块仍空闲；
- 可能导致**空间泄漏**（该 inode 对应的块既被标记为占用，又可能被再次分配给其他文件）；
- fsck 启动时会检测到 inode 被使用但位图显示对应块空闲，需手动修复；

B. 有日志：

- 整个事务（操作1,2,3）作为原子单元写入日志；
- 崩溃时，日志中记录了完整事务但尚未完全应用；
- 重启后，系统重放日志，补全操作 3（更新位图），恢复一致性；
- 不存在元数据不一致的问题；

### 例题 7：FAT 文件访问路径（★★★）

**题目**：某 FAT 文件系统，文件 `test` 起始块为 217。FAT 表内容：

```
FAT[217] = 618
FAT[618] = 339
FAT[339] = -1 (EOF)
```

1. 文件 `test` 包含哪些块？
2. 若要随机访问文件第 3 块（0起），需要读几次 FAT 表？
3. 如果 FAT 整张表已缓存在内存中，随机访问第 3 块需要几次磁盘 I/O？

**解答**：

```
1. 块链：217 → 618 → 339 → EOF
   文件包含块：217, 618, 339（共 3 块）

2. 访问第 3 块（即块 339，索引从0数：217=0, 618=1, 339=2）
   需读 FAT[217]→618（1次），FAT[618]→339（2次），共2次 FAT 读取
   （或从头遍历：读3次 FAT 才确认是第2项=索引2的物理块）

3. FAT 已在内存：
   无需磁盘读 FAT，直接在内存中查 FAT[217]=618, FAT[618]=339
   只需 1 次磁盘 I/O（读数据块 339）
```

> 💡 这说明 FAT 缓存在内存中的重要性——可以把随机访问的磁盘 I/O 从 O(n) 降至 O(1)。

## 总结速查表

|知识点|核心结论|
|---|---|
|FCB / inode|存元数据，不存文件名和数据内容|
|文件描述符|进程打开文件表的索引，不是 inode 号|
|连续分配|性能最好，有外部碎片，支持顺序+随机访问|
|链接分配|无外部碎片，只适合顺序访问，指针断裂可靠性差|
|FAT|链接分配的改进，FAT 缓存后随机访问快|
|索引分配|无外部碎片，支持随机访问，小文件额外开销大|
|inode 组合方案|直接+一级+二级+三级间接，兼顾小文件和大文件|
|位图法|易找连续空闲块，空间开销固定|
|日志文件系统|事务写日志后即"已提交"，崩溃重放日志恢复|
|统一缓冲区缓存|消除 mmap 和 read/write 的双重缓存问题|
