## 1. 为什么需要内存管理

**核心动机**：

- 程序必须加载到内存中才能由CPU执行（CPU从内存取指令）
- 多道程序设计（Multiprogramming）要求同时将**多个进程**驻留内存，以提高CPU利用率和系统响应性
- 内存资源有限，必须**高效管理**

> [!NOTE] **关键约束**：
> 
> - 主存（RAM）和寄存器是CPU可直接访问的存储介质
> - 寄存器访问：1个CPU时钟周期（极快）
> - 主存访问：可能需要多个周期，引发 **暂停（stall）**
> - Cache介于两者之间，作为加速缓冲
> - 内存管理不仅追求速度，还必须保护OS和进程的安全，由硬件（MMU）实现，CPU不直接干预

## 2. 用户空间内存结构（进程地址空间）

一个进程的内存空间（用户态）从低地址到高地址依次分为：

```
高地址 (0xFFFFFFFF)
┌──────────────────┐
│   Stack（栈）     │  ← 局部变量，向下增长
├──────────────────┤
│       ↓  ↑       │  （未分配区域）
├──────────────────┤
│   Heap（堆）      │  ← 动态分配内存，向上增长
├──────────────────┤
│  BSS Segment     │  ← 未初始化的全局/静态变量
├──────────────────┤
│  Data Segment    │  ← 已初始化的全局/静态变量
├──────────────────┤
│  Code + Constant │  ← 代码和常量，只读
└──────────────────┘
低地址 (0x00000000)
```

> ⚠️ **易错点**：不同进程中相同变量的地址**不一定相同**，因为每个进程有独立的虚拟地址空间。

---

### 2.1 代码段与常量段（Code + Constant）

- 存放程序的**机器指令**和**字符串常量**等
- **只读**（read-only）：任何写操作均触发段错误
- 常量在编译时已确定地址，通过指针（地址）访问

**经典示例（易错）**：

```c
int main(void) {
    char *string = "hello";   // "hello" 存在代码/常量段
    string[4] = '\0';         // ❌ 写只读段 → Segmentation fault！
    return 0;
}
```

> **关键**：`"hello"` 字面量存于只读的代码/常量段，`string` 只是指向它的指针，不能通过该指针修改。若要修改，应使用 `char string[] = "hello";`（存于栈上，可写）。

---

### 2.2 数据段与BSS段

|特征|Data Segment|BSS Segment|
|---|---|---|
|存储内容|**已初始化**的全局/静态变量|**未初始化**的全局/静态变量|
|磁盘占用|**实际占用**文件空间（大数组→大文件）|**不占用**文件空间（只记录符号）|
|运行时|加载时直接读入|进程启动时由OS按需分配（自动清零）|

**BSS = "Block Started by Symbol"**（符号起始块）

**证明Data vs BSS文件大小差异**：

```c
// data_large.c — 已初始化大数组
char a[1000000] = {10};   // Data段 → 可执行文件约1MB

// bss_large.c — 未初始化大数组  
char a[1000000];          // BSS段 → 可执行文件仍约4KB（不变！）
```

> ⚠️ **重要结论**：BSS节省了磁盘空间，实际内存在进程运行时才分配并清零。

**静态变量与全局变量同属数据段**：

```c
int global_int = 10;        // Data段（0x804a014）
static int static_int = 10; // Data段（0x804a018）← 紧邻！
// 说明两者在同一段中
```

**数据段大小限制**：

- `ulimit -d` 查看（默认 unlimited）
- 但受制于数组下标为32位有符号整数，最大单个数组 < 2GB
- 32位Linux用户空间总大小约3GB（内核占1GB）

---

### 2.3 栈（Stack）

- **FILO（先进后出）**结构
- 函数调用时：局部变量、参数、返回地址被**压栈**（push）
- 函数返回时：自动**弹栈**（pop），空间释放
- **向低地址方向增长**

**函数调用栈帧示意**：

```
fun2() 调用时的栈（从顶到底）：
┌─────────────┐  ← 栈顶（低地址）
│   c = 10    │  fun2的局部变量
│ return addr2│  返回地址
│   y = 1    │  fun2的参数
│   x = 2    │
├─────────────┤
│ return addr1│
│   v = 2    │  fun1的参数
│   u = 1    │
├─────────────┤
│   b = 2    │  main的局部变量
│   a = 1    │
└─────────────┘  ← 栈底（高地址）
```

**栈大小限制**：

```bash
$ ulimit -s          # 查看栈大小限制（默认8192 KB = 8 MB）
$ ulimit -s 81920    # 修改为80MB
```

> ⚠️ **易错点**：定义超过栈大小的局部数组 → **Segmentation fault**！

---

### 2.4 堆（Heap）

- 用于**动态内存分配**（`malloc`/`new`）
- 向**高地址方向增长**
- 需要手动管理（`free`/`delete`），否则内存泄漏

---

### 2.5 段错误（Segmentation Fault）深度解析

**本质**：程序访问了不被允许访问的内存区域（越界、非法权限等）

**各段读写权限表**：

|内存区域|可读|可写|
|---|---|---|
|Unusable（0x0及最高地址）|✅ YES|✅ YES|
|Allocated Stack（已分配栈）|❌ NO（越界）|❌ NO（越界）|
|Unallocated Zone（未分配区）|✅ YES|✅ YES|
|Allocated Heap（已分配堆）|❌ NO（越界）|❌ NO（越界）|
|BSS|❌ NO（越界）|❌ NO（越界）|
|Data|❌ NO（越界）|❌ NO（越界）|
|**Code + Constant**|❌ NO|**✅ YES（写 → Segfault！）**|

> 注意：上表中"NO"指的是**非法访问该段**（如越界/写只读段）才会Segfault；已分配的合法区域读写是允许的。核心规则如下：

**触发Segmentation Fault的三种情形**：

|操作|只读段（Code/Const）|已分配可读写段|未分配/非法区域|
|---|---|---|---|
|读（Read）|无问题 ✅|无问题 ✅|**Segfault** ❌|
|写（Write）|**Segfault** ❌|无问题 ✅|**Segfault** ❌|

**经典NULL指针解引用**：

```c
char *ptr = NULL;   // NULL = 0x00000000（地址最低区，不可访问）
char c = *ptr;      // 读0x00000000 → Segmentation fault
```

## 3. 内存管理基础概念

### 3.1 地址绑定（Address Binding）

程序在生命周期中，地址经历三个阶段的绑定：

```
源代码（符号地址）
    ↓ 编译/汇编
目标模块（可重定位地址，如"模块开头14字节处"）
    ↓ 链接器（静态链接）
加载模块（Load Module）
    ↓ 加载器（Loader）
内存中的进程（绝对物理地址）
    ↑ 动态链接库（运行时加载）
```

**三种绑定时机**：

|时机|说明|特点|
|---|---|---|
|**编译时（Compile Time）**|内存位置预先已知，生成绝对代码|起始位置变化必须重新编译（.COM文件）|
|**加载时（Load Time）**|编译时位置未知，生成可重定位代码|加载器在装入时确定最终地址|
|**执行时（Execution Time）**|进程运行中可移动，绑定延迟到运行时|需要硬件支持（基址+界限寄存器），现代OS采用|

> ⭐ **重点**：现代操作系统采用**执行时绑定**，这是支持进程动态移动、虚拟内存的基础。

---

### 3.2 逻辑地址与物理地址

|概念|别名|生成者|说明|
|---|---|---|---|
|**逻辑地址（Logical Address）**|虚拟地址（Virtual Address）|CPU|程序员/程序看到的地址|
|**物理地址（Physical Address）**|—|MMU转换后|内存条实际看到的地址|

- 编译时/加载时绑定：逻辑地址 = 物理地址（无区别）
- **执行时绑定**：逻辑地址 ≠ 物理地址（有MMU动态映射）

> ⭐ **核心**：逻辑地址空间与物理地址空间的分离是内存管理的根本机制，使得进程可以拥有比物理内存更大的地址空间，且多个进程可以安全共存。

---

### 3.3 MMU（内存管理单元）

**定义**：在程序运行时，将虚拟（逻辑）地址动态映射到物理地址的**硬件设备**。

```
CPU → [逻辑地址] → MMU → [物理地址] → 物理内存
```

**简单MMU（重定位寄存器方案）**：

- 逻辑地址 + 重定位寄存器值（基址）= 物理地址
- 例：基址 = 14000，逻辑地址 = 346 → 物理地址 = **14346**
- 用户程序只见逻辑地址，运行时绑定在引用时发生

---

### 3.4 内存保护（基址与界限寄存器）

**机制**：用一对寄存器限定进程可访问的物理地址范围：

- **基址寄存器（Base Register）**：进程可访问的**最小物理地址**
- **界限寄存器（Limit Register）**：进程的逻辑地址空间**范围大小**

**硬件检查流程**：

```
CPU发出逻辑地址
    ↓
检查：逻辑地址 < 界限寄存器？
    ↓ Yes              ↓ No
物理地址 = 基址 + 逻辑地址    陷阱 → OS → 非法地址错误
    ↓
访问物理内存
```

> ⭐ **关键**：加载基址/界限寄存器的指令是**特权指令**，只有OS（内核态）才能执行！用户程序无法篡改自己的地址范围，从而保护了OS和其他进程。

## 4. 动态加载与动态链接

### 动态加载（Dynamic Loading）

**问题**：传统方式要求整个程序在内存才能执行 → 浪费内存

**解决**：程序的每个例程（routine）只在**被调用时**才加载到内存。

- 程序以**可重定位加载格式**存储在磁盘
- 优点：未使用的代码（如异常处理程序）永远不被加载
- **不需要OS特殊支持**，可由程序自己实现（OS可提供库支持）

### 动态链接（Dynamic Linking）与共享库

|对比维度|静态链接|动态链接|
|---|---|---|
|时机|编译/加载时|**运行时**|
|库的副本|每个可执行文件各自包含一份|内存中只有**一份共享副本**|
|更新库|需重新编译所有程序|直接替换库文件即可|
|磁盘空间|浪费（重复存储）|节省|

**存根（Stub）机制**：

1. 可执行文件中包含一小段存根代码，指向库函数
2. 首次调用时，存根定位内存中的库（若不在内存则加载）
3. 存根将自身替换为库函数的真实地址
4. 之后直接调用库函数，存根不再执行

> **共享库（Shared Library）** = 动态链接库（DLL/`.so`），在Linux中称为 `.so`（Shared Object），Windows中称为 `.dll`。

## 5. 交换（Swapping）

**基本思想**：进程可以临时从内存**换出（swap out）** 到后备存储（磁盘），之后再**换入（swap in）** 继续执行。

```
主内存              后备存储（磁盘）
┌──────────┐       ┌──────────────┐
│  OS      │  ①swap out →  │ Process P1   │
│          │  ② swap in ← │ Process P2   │
│ 用户空间  │               └──────────────┘
└──────────┘
```

- 使得所有进程的**物理地址空间总和可超过实际物理内存**
- **交换代价极高**（依赖内存-磁盘传输速率）

**现代系统策略**：

- 正常情况**禁止交换**，仅当空闲内存低于阈值时启用
- 通常与**虚拟内存**配合工作（交换页而非整个进程）

**移动设备（iOS/Android）**：

- 通常**禁止传统交换**（闪存寿命有限，写入次数受限）
- 内存不足时直接终止进程（终止前将状态保存到闪存）

## 6. 连续内存分配

### 6.1 固定分区（Fixed Partition）

- 内存被划分为**预设数量的固定大小分区**（等大或不等大）
- 每个分区容纳一个进程

**缺点**：

1. 分区数量固定 → 限制了同时活跃进程的数量
2. 小进程在大分区中运行 → **内部碎片**严重浪费

---

### 6.2 可变分区与动态分区

**可变分区（Variable Partition）**：分区大小按进程需求动态调整

- **孔（Hole）**：可用的空闲内存块，分散在内存中
- 进程到来：从足够大的孔中分配内存
- 进程离开：释放分区，相邻空闲区**合并**

**三种空闲区分配算法**：

| 算法                  | 策略             | 优点         | 缺点                    |
| ------------------- | -------------- | ---------- | --------------------- |
| **首次适应（First Fit）** | 分配**第一个**足够大的孔 | 最简单，通常最快最好 | 前端积累大量小碎片             |
| **最佳适应（Best Fit）**  | 分配**最小的**足够大的孔 | 剩余孔最小      | 需遍历整个列表；产生大量细小碎片，性能最差 |
| **最差适应（Worst Fit）** | 分配**最大的**孔     | 剩余大孔可继续使用  | 需遍历整个列表；破坏大孔          |

> ⭐ **结论**：在速度和利用率方面，**首次适应 ≥ 最佳适应 > 最差适应**。首次适应不仅最简单，通常也是最快和最好的。

---

### 6.3 碎片（Fragmentation）

**外部碎片（External Fragmentation）**：

- 空闲内存总量足以满足请求，但**不连续**，无法分配
- 解决方案：**压缩（Compaction）**（移动进程合并空闲区，代价高；或**允许逻辑地址不连续**→ 分段/分页）

**内部碎片（Internal Fragmentation）**：

- 分配的内存**略大于**请求大小，多余部分在分区内部浪费
- 分页中必然存在（最后一页通常未填满）

**50%规则**（首次适应的经验统计）：

- 给定N个已分配块，约0.5N个块因外部碎片丢失
- 即约1/3的内存可能无法使用

## 7. 分段（Segmentation）

### 基本概念

**思想**：按程序的**逻辑结构**划分内存，符合程序员的思维方式。

- 程序被划分为若干**段（Segment）**（代码段、数据段、栈段等）
- 各段**长度不等**，但有最大限制
- **逻辑地址 = <段号 s, 偏移量 d>**（二维地址）

**对程序员可见**：程序员（或编译器）显式地将程序划分为不同段，实现模块化设计。

### 段表（Segment Table）

每个进程有一张段表，每个条目包含：

- **基址（Base）**：该段在物理内存的起始地址
- **界限（Limit）**：该段的长度

**地址转换流程**：

```
逻辑地址 <s, d>
    ↓
以s为索引查段表 → 获得 (limit, base)
    ↓
检查 d < limit?
    ↓ Yes              ↓ No
物理地址 = base + d     陷阱 → 地址错误
```

### 分段的特性

- 消除**内部碎片**（段按需分配，精确大小）
- 但仍存在**外部碎片**（不同长度的段在内存中分散）
- 类似于动态分区，但一个进程可占多个不连续分区

## 8. 分页（Paging）⭐⭐⭐⭐⭐

分页是现代操作系统最核心的内存管理机制，**必须深入理解**。

### 8.1 分页基本原理

**核心思想**：将物理内存和逻辑内存都划分为**相同大小的固定块**，消除外部碎片。

|概念|位置|说明|
|---|---|---|
|**帧/页框（Frame）**|物理内存|物理内存被划分为固定大小的块|
|**页（Page）**|逻辑内存|逻辑内存被划分为相同大小的块|

**页面大小**：

- 必须是**2的幂次**（便于地址拆分）
- 典型大小：512B ~ 16MB（现代系统常用4KB）
- 大小随时代增长（Solaris支持8KB和4MB）

**关键优点**：

- **消除外部碎片**（物理帧可任意分散分配）
- **仍有内部碎片**（最后一页通常不满，平均浪费半页）

**仍有内部碎片（计算示例）**：

- 页面大小 = 2048 字节，进程大小 = 72766 字节
- 需要 35 页 + 1086 字节的剩余
- 最后一页分配 2048 字节，实际用 1086 字节
- **内部碎片 = 2048 - 1086 = 962 字节**
- 最坏情况：1帧 - 1字节；平均：1/2帧大小

---

### 8.2 分页地址转换

**逻辑地址结构**（设逻辑地址空间为 $2^m$，页面大小为 $2^n$）：

```
┌──────────────────┬──────────────┐
│  页码 p (m-n位)  │  偏移 d (n位) │
└──────────────────┴──────────────┘
```

**转换过程**：

1. CPU生成逻辑地址，拆分为 **(p, d)**
2. 以 **p** 为索引查**页表（Page Table）**，得到**帧号 f**
3. 物理地址 = **f × 页面大小 + d** = **(f, d)**

```
逻辑地址 [p | d]
    ↓ 以p查页表
    f（帧号）
    ↓
物理地址 [f | d] → 物理内存中的帧f，偏移d处
```

**具体示例**（n=2位偏移，即页面大小=4字节；m=4位，即16字节逻辑空间）：

|逻辑页|物理帧|
|---|---|
|页0|帧5|
|页1|帧6|
|页2|帧1|
|页3|帧2|

- 逻辑地址 8（=二进制`1000`）→ 页号 p=2，偏移 d=0 → 帧1 → 物理地址 = 1×4+0 = **4**
- 逻辑地址 13（=二进制`1101`）→ 页号 p=3，偏移 d=1 → 帧2 → 物理地址 = 2×4+1 = **9**

### 8.3 页表的实现与TLB

#### 基本页表（存在内存中）

- 每个进程有一张**页表**，存储在主存中
- **PTBR（页表基址寄存器）**：指向当前进程页表的起始地址
- **PTLR（页表长度寄存器）**：指示页表大小

**问题**：每次内存访问需要**两次**内存操作：

1. 访问页表（查帧号）
2. 访问实际数据/指令

→ 性能降低一倍！

#### TLB（Translation Lookaside Buffer，快表）

**本质**：一种超高速的**硬件缓存**，缓存最近使用的页表条目（<页码, 帧号>对）。

**工作原理**（并行查找）：

```
逻辑地址 (p, d)
    ↓
同时查TLB中所有条目（全关联/组关联）
    ↓
TLB命中（hit）→ 直接取帧号f，只需1次内存访问
TLB未命中（miss）→ 查内存页表（2次内存访问），并将结果加入TLB
```
![[Pasted image 20260518083407.png|500]]

**ASID（地址空间标识符）**：

- 某些TLB每条目存储ASID，唯一标识进程
- 避免上下文切换时刷新TLB（节省时间）
- 无ASID时：每次上下文切换必须**刷新整个TLB**

**TLB特性**：

- 容量很小（64 ~ 1024条目）
- 未命中时将新条目加入TLB（需替换策略，如LRU）
- 某些条目可被**固定（pinned）**，永久缓存（如内核页表）

---

### 8.4 有效访问时间（EAT）计算

设：

- **α（hit ratio）** = TLB命中率
- **τ**（TLB查找时间，通常可忽略或极小）
- **m** = 内存访问时间

**EAT公式**： $$\begin{aligned}
EAT &= \alpha \cdot (m + \tau) + (1 - \alpha) \cdot (2m + \tau)\\
&=2m + \tau - \alpha m
\end{aligned}$$

**（近似，忽略TLB查找时间 τ）**： $$EAT = \alpha \cdot m + (1-\alpha) \cdot 2m = (2 - \alpha) \cdot m$$

**数值示例**：

- 内存访问时间 m = 10 ns

|命中率 α|EAT|时间开销|
|---|---|---|
|80%|0.8×10 + 0.2×20 = **12 ns**|增加 20%|
|99%|0.99×10 + 0.01×20 = **10.1 ns**|增加 1%|

> ⭐ **结论**：现实中TLB命中率通常达99%以上，因此分页机制的性能开销极小（约1%）。这是TLB设计的精妙之处——利用**局部性原理**，以极小的硬件成本换取接近直接访问的性能。

---

### 8.5 分页内存保护

**每个页表条目（PTE）附加的保护位**：

- **读/写/执行权限位**：区分只读页（代码段）和可读写页（数据段）
- **有效-无效位（Valid-Invalid bit）**：
    - `valid`：该页在进程逻辑地址空间内，可合法访问
    - `invalid`：该页不在进程地址空间内（如超出程序大小的部分），任何访问均触发**内核陷阱（trap）**

**PTLR（页表长度寄存器）**：限制逻辑地址不超过页表大小，防止越界。

---

### 8.6 共享页

**共享代码（只读代码）**：

- 多个进程的页表条目可以指向**同一个物理帧**
- 典型应用：文本编辑器、编译器、C运行库等
- 在物理内存中只需**一份副本**，节省内存

**条件**：共享的代码必须是**可重入（reentrant）**的（无状态，只读）

**私有数据**：

- 每个进程有独立的数据页
- 可出现在逻辑地址空间的任意位置

**共享页示例**（3个进程共享同一编辑器代码ed1/ed2/ed3）：

- P1、P2、P3的页表中ed1/ed2/ed3条目均指向物理帧3、4、6
- 每个进程的data页分别指向独立帧（1、7、2）

### 8.7 页表结构

**问题**：32位地址空间 + 4KB页面 → 页表有 $2^{20}$ ≈ 100万条目 → 每个进程需要4MB页表空间，且需连续物理内存！

**三种解决方案**：

#### ① 分层页表（Hierarchical / Multi-Level Paging）

**两级页表**（32位，4KB页）：

- 20位页码拆分为：10位（外层页目录）+ 10位（内层页表）
- 逻辑地址结构：`[p1(10) | p2(10) | d(12)]`

```
p1 → 外层页目录 → 指向内层页表基址
    + p2 → 内层页表 → 帧号 f
        + d → 物理地址
```

**优点**：页表本身可以分散在不连续的内存中，不需要巨大连续空间。

**64位问题**：

- 4KB页面 → 页表有 $2^{52}$ 个条目，两级根本不够
- 需要三级（p1=32, p2=10, d=12）甚至四级分页
- 每次内存访问需要多次内存访问（性能问题，靠TLB缓解）

#### ② 散列页表（Hashed Page Table）

- 以**虚拟页码**为哈希值，映射到链式哈希表
- 每个链表节点包含：(虚拟页码, 帧号, 下一节点指针)
- 查找时遍历链表匹配虚拟页码
- ![[Pasted image 20260518090555.png|550]]
- 适合地址空间 > 32位的系统
- **聚簇页表（Clustered Page Table）**：每个条目覆盖多个连续页（如16页），适合稀疏地址空间

#### ③ 倒排页表（Inverted Page Table）

**思想**：不为每个进程建页表，而是为每个**物理帧**建一个条目（全局共享一张表）。

- 表大小 = 物理内存帧数（固定、较小）
- 每条目：(进程ID, 虚拟页码)
- 逻辑地址 (pid, p, d) → 在倒排表中**搜索**匹配的 (pid, p) → 得到帧号 i → 物理地址 (i, d)
- ![[Pasted image 20260518091615.png|550]]

**优点**：全系统只需一张表，节省大量内存。

**缺点**：查找时需线性扫描整个表（慢），通常用哈希加速；难以支持共享内存（一物理地址只能对应一个虚拟地址条目）。

## 9. 伙伴系统（Buddy System）

**思想**：融合固定分区和动态分区的优点，以2的幂次大小分配内存块。

**规则**：

- 内存块大小为 $2^K$，$L \leq K \leq U$
    - $2^L$：最小可分配块
    - $2^U$：最大可分配块（通常等于总内存）
- 分配请求：找到最小的满足需求的 $2^K$ 块
    - 若需要更小的块，将块**对半分裂**，得到两个"伙伴（buddy）"
    - 其中一半用于分配，另一半保留
- 释放：若其"伙伴"也是空闲的，则**合并**为更大的块（递归向上合并）

**示例追踪**（1MB内存）：

| 操作     | 内存状态                                              |
| ------ | ------------------------------------------------- |
| 初始     | [1M空闲]                                            |
| 申请100K | *A=128K* \| 128K \| 256K \| 512K                  |
| 申请240K | A=128K \| 128K \| *B=256K* \| 512K                |
| 申请64K  | A=128K \| *C=64K*\|64K \| B=256K \| 512K          |
| 申请256K | A=128K \| C=64K\|64K \| B=256K \|*D=256K*\|256K   |
| 释放B    | A=128K \| C=64K\|64K \| **256K空** \| D=256K\|256K |
| 释放A    | **128K空** \| C=64K\|64K \| 256K \| D=256K\|256K   |
| 申请75K  | *E=128K* \| C=64K\|64K \| 256K \| D=256K\|256K    |
| 释放C    | E=128K \| 128K \| 256K \| D=256K\|256K            |
| 释放E    | **512K空** \| D=256K\|256K                         |
| 释放D    | **1M空闲**                                          |

**优缺点**：

- 优点：快速分配和合并，实现简单（Linux内核使用此方案管理物理页框）
- 缺点：内部碎片（块大小取整为2的幂，最多浪费50%）

## 10. 实际架构案例

### Intel IA-32（32位 x86）架构

Intel IA-32支持**分段+分页**的两级地址转换：

```
逻辑地址（段选择子+偏移）
    ↓ 分段单元（Segmentation Unit）
32位线性地址
    ↓ 分页单元（Paging Unit，相当于MMU）
物理地址
```

**分页结构**（两级，4KB页）：

- 地址位划分：`[p1(10) | p2(10) | d(12)]`
- CR3寄存器：指向页目录的物理地址
- 也支持4MB大页（直接从目录跳转）

**PAE（页地址扩展）**：

- 允许32位系统访问超过4GB内存（最大64GB）
- 扩展为3级页表，页目录条目扩展为64位
- 地址位扩展到36位

### Intel x86-64（64位）架构

- 理论64位地址空间（> 16 EB）
- 实际实现**48位寻址**（128TB）
- 4级页表：`[PML4(9) | PDPT(9) | PDT(9) | PT(9) | d(12)]`
    - 各级：Page Map Level 4, Page Directory Pointer Table, Page Directory, Page Table
- 支持4KB、2MB（大页）、1GB（超大页）三种页面大小

### 【例题1】地址绑定时机辨析（难度：★★★）

**题目**：下列四种情况，各属于哪种地址绑定时机？哪种情况不需要基址寄存器？

A. 编译器将全局变量 `x` 绑定到地址 `0x0804a020`，该地址写入目标文件，程序每次运行都在该物理地址 B. 目标文件中记录"变量y在模块开头偏移40字节处"，加载器根据实际加载位置确定物理地址 C. 程序运行时，CPU生成逻辑地址346，MMU加上重定位寄存器值14000得到物理地址14346 D. 源代码中变量名`counter`，编译后成为汇编中的标号

**答案与解析**：

- **A → 编译时绑定**：逻辑地址=物理地址，起始位置变化须重新编译。**不需要基址寄存器**（地址已写死）。
- **B → 加载时绑定**：可重定位代码，加载器计算最终物理地址，程序每次加载位置可不同，但运行期间不变。**不需要运行时基址寄存器**（但加载器需要调整代码中所有地址）。
- **C → 执行时绑定**：需要重定位（基址）寄存器，运行时动态映射。**需要基址寄存器**（或MMU）。
- **D → 符号地址**（还不是绑定，是编译前的源代码阶段）。

**结论**：只有执行时绑定需要硬件基址寄存器支持；编译时绑定的程序灵活性最差（COM文件）。

### 【例题2】分页地址转换计算（难度：★★★★）

**题目**：某系统的逻辑地址空间为 $2^{16}$ 字节，页面大小为 1KB（$2^{10}$ 字节），物理内存大小为 $2^{14}$ 字节。进程P的页表如下：

|页号|帧号|有效位|
|---|---|---|
|0|5|v|
|1|3|v|
|2|—|i（无效）|
|3|7|v|
|4|1|v|

1. 逻辑地址 `0x1234` 对应的物理地址是什么？
2. 逻辑地址 `0x2A00` 对应的物理地址是什么？
3. 逻辑地址 `0x3FFF` 对应的物理地址是什么？
4. 该进程有多少内部碎片？

**解析**：

页面大小 = 1KB = $2^{10}$，故偏移位 = 10位，页号位 = 16-10 = 6位。

**分析各逻辑地址**：

**1. 逻辑地址 `0x1234` = 十进制 4660**

- 二进制：`0001 0010 0011 0100`
- 页号 p = 高6位 = `000100` = **4**
- 偏移 d = 低10位 = `10 0011 0100` = 0x234 = **564**
- 查页表：页4 → 帧1（有效）
- 物理地址 = 帧1 × 1024 + 564 = 1024 + 564 = **1588** = `0x0634`

**2. 逻辑地址 `0x2A00` = 十进制 10752**

- 页号 = 10752 / 1024 = **10**（十进制）
- 但页表只有0~4页！超出PTLR范围 → **陷阱（非法地址访问）**

**3. 逻辑地址 `0x3FFF` = 十进制 16383**

- 页号 = 16383 / 1024 = **15**（超出页表范围）→ **非法访问**

> **修正**：题目中仅有页0-4，所以逻辑地址范围最大为5×1024-1=5119字节。实际访问0x1234（4660）勉强在范围内（属于页4）；0x2A00（10752）超出范围。

**4. 内部碎片**：

- 进程使用了页0、1、3、4共4页（页2无效，未分配）
- 若进程实际大小 = 4.5页 × 1024 = 4608字节（举例）
- 内部碎片 = 5 × 1024 - 4608 = 512字节（最后一页只用了一半）

### 【例题3】TLB有效访问时间计算（难度：★★★）

**题目**：某系统内存访问时间为100ns，TLB访问时间为5ns，TLB命中率为95%。请计算：

1. 使用TLB时的有效访问时间（EAT）
2. 若不用TLB（纯页表），访问时间是多少？
3. 使用TLB带来的性能提升百分比是多少？

**解析**：

**1. 带TLB的EAT**：

$$EAT = \alpha \times (t_{TLB} + t_{mem}) + (1-\alpha) \times (t_{TLB} + 2 \times t_{mem})$$

$$= 0.95 \times (5+100) + 0.05 \times (5 + 200)$$

$$= 0.95 \times 105 + 0.05 \times 205$$

$$= 99.75 + 10.25 = \mathbf{110 \text{ ns}}$$

**2. 不用TLB（两次内存访问）**： $$t_{no_TLB} = 2 \times 100 = \mathbf{200 \text{ ns}}$$

**3. 性能提升**： $$提升 = \frac{200 - 110}{200} \times 100% = \mathbf{45%}$$

> **说明**：该例中TLB访问时间不可忽略（5ns），所以用完整公式。现代CPU的TLB查找通常在1-2个时钟周期内完成，相对内存访问（几十纳秒）几乎可忽略。

### 【例题4】动态内存分配算法比较（难度：★★★★）

**题目**：内存中空闲区列表如下（按地址顺序）：

|空闲区序号|起始地址|大小|
|---|---|---|
|1|100|60KB|
|2|300|20KB|
|3|500|100KB|
|4|800|40KB|
|5|1000|90KB|

现有三个进程依次申请：P1申请25KB，P2申请70KB，P3申请35KB。

分别使用**首次适应（FF）**、**最佳适应（BF）**、**最差适应（WF）**算法分配，并比较各自完成后的内存碎片情况。

**解析**：

**首次适应（First Fit）**：

- P1申请25KB → 空闲区1（60KB）→ 分配，剩余35KB
- P2申请70KB → 空闲区1剩35KB不够；空闲区2(20KB)不够；空闲区3(100KB)够 → 分配，剩余30KB
- P3申请35KB → 空闲区1(35KB)正好 → 分配，剩余0KB

最终剩余空闲区：区2(20KB)、区3(30KB)、区4(40KB)、区5(90KB)，总计180KB，最小碎片20KB。

**最佳适应（Best Fit）**（按大小升序搜索）：

- P1申请25KB → 最小满足的是区2(20KB 不够) → 区4(40KB) → 分配，剩余15KB
- P2申请70KB → 最小满足的是区5(90KB) → 分配，剩余20KB
- P3申请35KB → 最小满足的是区4剩余(15KB 不够) → 区3(100KB) → 分配，剩余65KB

最终：区1(60KB)、区2(20KB)、区3(65KB)、区4剩余(15KB)、区5剩余(20KB)。最小碎片15KB。**产生更多细小碎片。**

**最差适应（Worst Fit）**（分配最大孔）：

- P1申请25KB → 最大空闲区3(100KB) → 分配，剩余75KB
- P2申请70KB → 最大空闲区3剩余(75KB)够 → 分配，剩余5KB
- P3申请35KB → 最大空闲区5(90KB) → 分配，剩余55KB

最终：区1(60KB)、区2(20KB)、区3(5KB)、区4(40KB)、区5(55KB)。

**对比总结**：

|算法|P3能否分配|最小碎片|评价|
|---|---|---|---|
|FF|✅ 可以|0KB（恰好用完一个孔）|最简单、通常最好|
|BF|✅ 可以|15KB（有细小碎片）|细小碎片多，性能较差|
|WF|✅ 可以|5KB|破坏大孔，不推荐|

### 【例题5】伙伴系统分配计算（难度：★★★★）

**题目**：一个512KB的伙伴系统，最小分配单位为64KB。按顺序处理以下请求：

1. 申请100KB（分配给A）
2. 申请240KB（分配给B）
3. 申请64KB（分配给C）
4. 释放A
5. 申请80KB（分配给D）
6. 释放B

8. 释放C

请画出每步后的内存状态，并说明何时发生合并。

**解析**：

伙伴系统分配单位：64KB, 128KB, 256KB, 512KB（2的幂次）

|步骤|内存状态|说明|
|---|---|---|
|初始|[512KB空]|—|
|1. 申请100KB → A|A=128K \| 128K \| 256K|512K分裂为256+256，左256再分裂为128+128，A占左128K|

|6. 释放B|D=128K \| C=64K\|64K \| **256K空**|B释放，其伙伴（256K中的...实际与D和C在同侧，不可合并） → 暂不合并|

|8. 释放C|**全部512K空**|C释放，64K与伙伴64K合并→128K，128K与另128K合并→256K，两个256K合并→**512K完全恢复**|

### 【例题6】页表结构与地址位数（难度：★★★★★）

**题目**：某64位系统，采用4级页表，每页大小4KB，每个页表条目8字节。

1. 该系统如何划分64位地址（每级页表位数是多少）？
2. 每个进程的页表最大占用多少内存？（仅需顶级页表）
3. 若某进程只使用了1MB的地址空间，实际需要多少页表内存？

**解析**：

**1. 地址划分**：

- 页大小 = 4KB = $2^{12}$ → 偏移位 = 12位
- 剩余 64 - 12 = 52位用于4级页表索引
- Intel x86-64实际只用48位 → 52-4=48位有效，高16位须符号扩展
- 每级 = 48 / 4 = **9位**（与Intel实际设计吻合）
- 地址结构：`[unused(16) | PML4(9) | PDPT(9) | PDT(9) | PT(9) | offset(12)]`

**2. 顶级页表（PML4）大小**：

- PML4有 $2^9$ = 512个条目，每条目8字节
- PML4大小 = 512 × 8 = **4096字节 = 1页（4KB）**
- 每个进程只需1页顶级页表！（这是多级页表的精妙所在）

**3. 1MB地址空间的页表开销**：

- 1MB = $2^{20}$ 字节，页大小 $2^{12}$，需要 $2^{8}$ = **256个页**
- 需要1个PT页（Page Table，能容纳512条目，256 < 512，1页够）
- 需要1个PDT条目（指向该PT）→ 1个PDT页
- 需要1个PDPT条目 → 1个PDPT页
- 需要1个PML4条目 → 1个PML4页
- 共需 **4页 × 4KB = 16KB** 的页表内存（相比1MB实际数据，开销仅1.5%）

> **对比单级页表**：1MB空间中只有256个有效页，但单级页表需要为整个地址空间（$2^{48-12}$=256G条目）预留……这显然不现实，多级页表的优势显而易见。

## 重点总结与易错点汇总

### ⭐ 核心知识点清单

1. **进程地址空间布局**：从低到高：代码段→数据段→BSS→堆（↑）···栈（↓）
2. **Data vs BSS**：Data已初始化占磁盘空间；BSS未初始化不占磁盘空间，运行时分配
3. **地址绑定三时机**：编译时/加载时/执行时，现代OS用执行时绑定
4. **逻辑地址 ≠ 物理地址**（执行时绑定时），MMU负责转换
5. **基址+界限寄存器是特权寄存器**，只有OS可以修改
6. **分页消除外部碎片，但存在内部碎片**（最多浪费1页-1字节）
7. **TLB命中率≈99%时，分页开销仅约1%**（有效访问时间公式）
8. **TLB无ASID时，上下文切换必须刷新TLB**
9. **共享页要求代码可重入（只读）**
10. **倒排页表节省内存但查找慢**，通常用哈希加速

### ⚠️ 高频易错点

1. **BSS段大文件误判**：未初始化的大数组不会增大可执行文件大小（BSS只记录符号）
2. **常量字符串写操作**：`char *p = "hello"; p[0]='H';` → Segfault！应用 `char p[] = "hello";`
3. **栈溢出方向**：栈向低地址增长，大数组定义在栈上易越界
4. **内部碎片计算**：最后一页碎片 = 页大小 - (进程大小 mod 页大小)，若整除则无碎片
5. **EAT公式**：TLB命中只需1次内存访问（帧号来自TLB）；未命中需2次（1查页表+1访数据）
6. **分段消除内部碎片但有外部碎片**；**分页消除外部碎片但有内部碎片**
7. **动态链接的存根**：首次调用后存根被替换为真实地址（自修改代码）
8. **伙伴系统只有相邻且大小相同的伙伴才能合并**，不是任意两个相邻空闲块
