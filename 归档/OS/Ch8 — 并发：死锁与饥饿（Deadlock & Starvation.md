## 一、死锁的本质与定义

### 1.1 直觉理解

想象十字路口：四个方向的车辆各自占据了路口的一角，每辆车都等待前方的车挪走，而前方的车同样在等待，于是所有车都永远无法移动。这就是死锁的现实类比——**每个参与者都在等一个永远不会发生的事件**。

### 1.2 严格定义

> 当一组进程中，**每个进程都在等待某个事件（通常是释放某资源）**，而该事件只能由**这组进程中另一个同样被阻塞的进程**触发时，则称该组进程发生了**死锁（Deadlock）**。

几个关键点务必记住：

**死锁是永久性的。** 一旦死锁形成，没有任何一个进程能自行解脱，除非外力介入（操作系统干预）。这与"暂时等待"有本质区别——暂时等待的进程总会等到资源，死锁进程永远等不到。

**死锁没有通用且高效的解决方案。** 这是操作系统领域一个根本性的困难，正因如此，绝大多数通用操作系统（如 Linux、Windows）默认选择**忽略死锁**（鸵鸟算法），将责任交给程序员。

### 1.3 死锁 vs 饥饿（Starvation）

这两个概念容易混淆，必须区分清楚：

- **死锁**：一组进程互相等待，**所有人**都无法推进，形成闭环。
- **饥饿**：某个进程**长期**得不到资源，但**不是因为循环等待**，而是因为调度不公平（其他进程总被优先选中）。饥饿在理论上有可能自行解除（如果"抢资源"的进程最终结束），死锁则绝对不会。

## 二、资源分类

理解资源类型有助于理解哪种情境下容易发生死锁。

### 2.1 可重用资源（Reusable Resource）

可重用资源是指**一次只能被一个进程安全使用，但使用完后可以归还，供其他进程再次使用的资源**。例如：处理器、内存、磁盘、I/O 设备、文件、数据库记录、信号量等。

进程使用可重用资源的正确顺序是：**申请（Request）→ 使用（Use）→ 释放（Release）**。如果进程在"申请"阶段无法立即获得资源，就进入等待状态。死锁最常发生在对可重用资源的竞争中。

**经典死锁场景（可重用资源）：**

```
进程 P 持有磁盘 D，等待磁带机 T
进程 Q 持有磁带机 T，等待磁盘 D

→ 互相等待，永远无法推进，死锁。
```

### 2.2 可消耗资源（Consumable Resource）

可消耗资源是指**可以被创建（生产）和消毁（消耗）**的资源，例如：消息、中断信号、I/O 缓冲区中的数据。一个进程创建（发送）消息，另一个进程消耗（接收）它。

**可消耗资源也能导致死锁：**

```
P1: Receive(P2);  // 等待 P2 的消息
    Send(P2, M1);

P2: Receive(P1);  // 等待 P1 的消息
    Send(P1, M2);
```

P1 和 P2 都先等对方发消息，再发自己的消息，于是两者永远都等不到消息。这类死锁尤其隐蔽，因为**程序可能正常运行很长时间**，只有在特定执行顺序下才会触发。

## 三、死锁的四个必要条件 ⭐

> ⚠️ **最重要的基础知识点**：这四个条件是死锁存在的必要条件，即死锁发生时这四个条件**一定同时成立**；反过来，**只要破坏其中任何一个**，死锁就不可能发生。

### 3.1 互斥（Mutual Exclusion）

一次只有一个进程可以使用某个资源；其他进程不能同时访问已被分配的资源。

**理解**：互斥本身是正确同步的必要手段（临界区保护），所以这个条件通常难以直接破坏，必须保留。只有对"可共享资源"（如只读文件，可以被多个进程同时读取）才能考虑放弃互斥。

### 3.2 占有且等待（Hold and Wait）

一个进程在等待其他进程释放资源的同时，继续**占有**已经分配给自己的资源，不主动释放。

**理解**：这是死锁的"贪婪性"来源。进程"一边抱着，一边要更多"，才形成了循环等待的基础。

### 3.3 非抢占（No Preemption）

已经分配给一个进程的资源，**不能被强制剥夺**，只能由该进程主动释放。

**理解**：如果操作系统可以强行从进程手中取走资源，就可以打破循环等待。但许多资源（如打印机、文件锁）强制剥夺会导致数据不一致，代价很高。

### 3.4 循环等待（Circular Wait）

存在一个**闭合的进程链**，链中每个进程都在等待下一个进程所持有的资源。

**形式化表达**：存在进程集合 {P0, P1, ..., Pn}，使得：

- P0 等待 P1 持有的资源
- P1 等待 P2 持有的资源
- ……
- Pn 等待 P0 持有的资源

**注意层次关系**：前三个条件合称"**死锁的可能性**"（必要但不充分），四个条件同时满足才是"**死锁的存在性**"。换言之，前三个条件营造了死锁的土壤，循环等待是死锁真正发生的导火索。

## 四、资源分配图（Resource Allocation Graph, RAG）

资源分配图是 Holt 引入的一种用于形式化描述系统资源分配状态、辅助判断死锁的工具。

### 4.1 图的构成

资源分配图中包含两类节点和两类有向边：

**节点**：圆形节点表示**进程**；方形节点表示**资源类型**（方框内的点代表该类资源的实例数量）。

**边**：从进程指向资源的箭头称为**请求边**（Pi → Rj），表示进程 Pi 正在等待资源 Rj 的一个实例；从资源指向进程的箭头称为**分配边**（Rj → Pi），表示资源 Rj 的一个实例当前被分配给进程 Pi。

### 4.2 死锁判断规则

**规则一（充分条件的逆否）**：如果资源分配图中**没有环**，则系统**一定没有死锁**。

**规则二（必要但不充分）**：如果图中**有环**，则系统**可能**存在死锁——究竟是否死锁，取决于环涉及的资源是否有多个实例。

**特殊情况（单实例资源）**：当每种资源类型只有**一个实例**时，图中有环**等价于**存在死锁。这是充要条件。

**多实例资源有环但不一定死锁的例子**：假设资源 Ra 有 3 个实例，P1 和 P2 都请求 Ra，同时 P3 已持有 Ra 的一个实例但不在环中，P3 完成后可以释放，让 P1 或 P2 继续运行，因此有环也不死锁。

### 4.3 资源分配图的应用场景

在"死锁避免"的**资源分配图算法**中，图还增加了一种**需求边（Claim Edge）**（用虚线表示），表示进程将来**可能**请求某资源，但尚未实际请求。这种算法仅适用于每种资源只有单个实例的系统。

## 五、处理死锁的四种策略

操作系统对死锁的态度有三大类、四种具体做法：

**策略一——死锁预防（Prevention）**：从设计上破坏四个必要条件之一，使死锁**不可能发生**。限制最严格，资源利用率最低。

**策略二——死锁避免（Avoidance）**：允许进程动态申请资源，但每次分配前，系统用算法判断分配后是否仍处于**安全状态**，若不安全则拒绝分配。需要进程事先声明最大需求。

**策略三——死锁检测与恢复（Detection & Recovery）**：对资源分配不加限制，允许死锁发生，但周期性地运行检测算法，一旦检测到死锁就采取恢复措施。最宽松，代价在于恢复。

**策略四——忽略（Ostrich Algorithm，鸵鸟算法）**：假装死锁不存在，如果真的发生了，就重启系统。绝大多数通用操作系统（Linux、Windows、macOS）采用此方法，因为死锁在实际中发生概率低，而预防或避免的代价过高。

## 六、死锁预防（Deadlock Prevention）⭐⭐

死锁预防的核心思路：**使四个必要条件中的某一个永远无法成立**。

### 6.1 破坏互斥条件

对可共享的资源（如只读文件），允许多个进程同时访问，不需要互斥保护。但对于**必须互斥的资源**（打印机、写操作等），无法破坏此条件。因此，这一策略**通常不可行**，只能在特定资源类型上有限应用。

### 6.2 破坏占有且等待条件 ⭐

**方案一：进程启动时一次性申请所有资源。** 进程在开始执行前，必须申请并获得其整个运行期间所需的全部资源；若无法全部获得，则等待（不执行，不占用任何资源）。

**方案二：申请新资源前，释放所有已持有资源。** 进程只在未持有任何资源时才被允许申请新资源。

**两种方案的共同缺点：资源利用率低**（进程占着大量资源却不一定马上用）；**可能导致饥饿**（需要多种资源的进程可能长期等不到所有资源同时可用）。

### 6.3 破坏非抢占条件

当一个进程持有某些资源，又在申请一个无法立即获得的新资源时，**强制释放其当前持有的所有资源**（隐式抢占）。这些被释放的资源被加入进程的等待列表，进程只有当它能重新获得所有原有资源加上新申请的资源时，才被重新启动。

**适用范围有限**：只适用于状态可以方便保存和恢复的资源（如 CPU 寄存器、内存页），对于磁盘 I/O、打印机等，强制中断可能导致数据损坏，代价太高。

### 6.4 破坏循环等待条件 ⭐⭐

这是**最常用、最实用**的死锁预防策略。

**核心方法：资源全局编号 + 顺序申请（Resource Ordering）**

为系统中所有资源类型分配一个全局唯一的编号（枚举函数 F），规定**所有进程必须按照编号递增的顺序申请资源**。即：若进程已持有编号为 F(Ri) 的资源，则只能继续申请编号 F(Rj) > F(Ri) 的资源。

**为什么这样能消除循环等待？（反证法）**

假设仍存在循环等待，设涉及的进程序列为 {T0, T1, ..., Tn}，其中 Ti 等待 Ri（被 Ti+1 持有）。由于每个进程持有 Ri 的同时在申请 Ri+1，根据顺序申请规则，必须有 F(R0) < F(R1) < ... < F(Rn) < F(R0)，由传递性得 F(R0) < F(R0)，矛盾！故循环等待不存在。

**重要注意：动态锁获取仍可能死锁！**

即使规定了资源顺序，如果锁是**运行时动态获取**的（锁的对象在运行时才确定），仍可能发生死锁。经典反例：

```c
// 银行转账函数，from 和 to 是运行时确定的账户对象
void transaction(Account from, Account to, double amount) {
    lock1 = get_lock(from);   // 运行时获取 from 对应的锁
    lock2 = get_lock(to);     // 运行时获取 to 对应的锁
    acquire(lock1);
    acquire(lock2);
    // ...
}

// 线程1：transaction(checking, savings, 25)
// 线程2：transaction(savings, checking, 50)
// 两者互相等待对方的锁 → 死锁！
```

因为 `checking` 和 `savings` 账户的锁编号在运行时才能确定，两个线程的实际加锁顺序可能正好相反。解决方案是在获取两把锁之前，先比较它们的地址（或其他全局编号），始终按固定顺序加锁。

## 七、死锁避免（Deadlock Avoidance）⭐⭐⭐

死锁避免不像预防那样静态禁止某些行为，而是在每次资源分配时**动态判断**：如果分配该资源后，系统是否仍然处于"安全状态"。只有安全才分配，不安全则让进程等待。

### 7.1 安全状态（Safe State）⭐⭐⭐

**安全状态**是理解死锁避免的核心概念，必须彻底理解。

> **定义**：如果系统能找到一个所有进程的执行序列 <P1, P2, ..., Pn>，使得对于其中每个进程 Pi，Pi **还需要的资源**能够由**当前可用资源 + 所有排在 Pi 前面的进程 Pj（j < i）所持有的资源**来满足，则称该序列为**安全序列**，系统处于**安全状态**。

**更直白的解释**：安全序列意味着，按这个顺序执行，每个进程都能在有限时间内完成——因为前面的进程完成并释放资源后，后面的进程总能凑够所需资源。系统在安全状态下，一定不会发生死锁。

**三种状态的关系（极其重要，考试常考！）**：

```
┌─────────────────────────────────────────────┐
│                  不安全（Unsafe）            │
│   ┌───────────────────────────────────┐      │
│   │           死锁（Deadlock）        │      │
│   └───────────────────────────────────┘      │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│               安全（Safe）                  │
└─────────────────────────────────────────────┘
```

- **安全状态 ⊆ 非死锁状态**：安全状态一定不是死锁状态（充分条件）
- **死锁状态 ⊆ 不安全状态**：死锁状态一定是不安全状态（必要条件）
- **不安全状态 ≠ 必然死锁**：不安全状态不一定会死锁，但**存在死锁的可能性**

> ⚠️ **易错点**：不安全状态并不意味着"已经死锁"，而是意味着"如果进程以某种方式运行，可能会死锁"。死锁避免的目标是**始终维持系统在安全状态**，从而杜绝死锁的可能。

**安全状态举例**（12个磁带机，3个进程）：

|进程|最大需求|当前已分配|
|---|---|---|
|P0|10|5|
|P1|4|2|
|P2|9|2|

当前已分配总量 = 5+2+2 = 9，可用 = 12-9 = 3。

安全序列分析 <P1, P0, P2>：

- P1 还需 4-2=2 个，可用 3 ≥ 2，P1 可完成，完成后释放 2 个，可用变为 3+2=5
- P0 还需 10-5=5 个，可用 5 ≥ 5，P0 可完成，完成后释放 5 个，可用变为 5+5=10
- P2 还需 9-2=7 个，可用 10 ≥ 7，P2 可完成 ✓

故系统处于安全状态。若此时 P2 再申请 1 个（使其已分配变为 3，可用变为 2），则：

- P1 还需 2，可用 2 ≥ 2，完成后可用变为 4
- P0 还需 5，可用 4 < 5，无法完成！
- P2 还需 6，可用 4 < 6，无法完成！

没有安全序列，**系统进入不安全状态**，故不能批准此申请。

### 7.2 死锁避免的两种方法

课件提到两种思路：**进程启动拒绝（Process Initiation Denial）** 和 **资源分配拒绝（Resource Allocation Denial，即银行家算法）**。前者在新进程启动时判断是否会导致未来死锁，过于保守；后者是主流，下面重点介绍。

### 7.3 资源分配图算法（单实例资源）

当系统中每种资源**只有单个实例**时，可以用增强的资源分配图来实现死锁避免：

在普通的请求边和分配边之外，增加**需求边（Claim Edge）**（用虚线表示），表示进程将来可能请求该资源。

**分配规则**：当进程 Pi 请求资源 Rj 时，只有将请求边转化为分配边**不会在图中形成环**时，才允许分配。用环检测算法（O(n²)）验证安全性。

### 7.4 银行家算法（Banker's Algorithm）⭐⭐⭐

适用于**每种资源有多个实例**的情况（单实例资源分配图算法无法处理多实例），是死锁避免最重要的算法。名字来源于"银行家"——银行家不会把钱贷出去到无法收回的地步。

#### 数据结构

设系统有 n 个进程，m 种资源类型：

- `Available[j]`：资源类型 Rj 当前可用的实例数
- `Max[i][j]`：进程 Pi 最多可以申请 Rj 的实例数（**事先声明**）
- `Allocation[i][j]`：当前已分配给 Pi 的 Rj 实例数
- `Need[i][j]`：Pi 还需要多少 Rj，计算公式为：`Need[i][j] = Max[i][j] - Allocation[i][j]`

关系约束：所有资源要么可用，要么已被分配，即 `R[j] = Available[j] + Σ Allocation[i][j]`（对所有 i 求和）。

#### 安全性算法（Safety Algorithm）

判断当前状态是否安全，时间复杂度为 **O(m × n²)**：

```
输入：当前 Available、Allocation、Need
输出：是否安全，若安全则给出安全序列

1. 初始化：
   Work = Available（工作向量，模拟资源归还过程）
   Finish[i] = false（所有进程初始标记为"未完成"）

2. 寻找满足以下两个条件的进程 i：
   (a) Finish[i] == false（进程尚未完成）
   (b) Need[i] <= Work（进程当前的剩余需求可以被满足）
   若找不到这样的 i，跳到步骤 4

3. 模拟 Pi 完成并释放资源：
   Work = Work + Allocation[i]（Pi 归还其所有资源）
   Finish[i] = true（标记 Pi 为已完成）
   回到步骤 2

4. 若所有 Finish[i] == true，系统处于安全状态；
   否则，系统处于不安全状态（Finish[i]==false 的进程可能死锁）
```

**理解算法本质**：这个算法在模拟"最好情况"——假设每个资源需求能被满足的进程都会完成并释放资源，看是否能让所有进程都顺利完成。如果连最好情况都不行，则系统不安全。

#### 资源请求算法（Request Algorithm）

当进程 Pi 发出资源请求 `Request[i]` 时，按以下步骤处理：

```
步骤1：检查 Request[i] <= Need[i]
        若不满足，报错（进程申请超过其声明的最大量）

步骤2：检查 Request[i] <= Available
        若不满足，Pi 必须等待（资源暂时不可用）

步骤3：假装分配（试探性分配），修改状态：
        Available  = Available  - Request[i]
        Allocation[i] = Allocation[i] + Request[i]
        Need[i]    = Need[i]    - Request[i]

步骤4：运行安全性算法，判断新状态是否安全：
        若安全  → 正式分配，进程继续执行
        若不安全 → 撤销试探性分配，恢复原状态，Pi 等待
```

#### 银行家算法完整举例

**初始状态**：5 个进程（P0–P4），3 种资源（A:10个, B:5个, C:7个）

|进程|Allocation(A,B,C)|Max(A,B,C)|Available(A,B,C)|
|---|---|---|---|
|P0|0, 1, 0|7, 5, 3|3, 3, 2|
|P1|2, 0, 0|3, 2, 2||
|P2|3, 0, 2|9, 0, 2||
|P3|2, 1, 1|2, 2, 2||
|P4|0, 0, 2|4, 3, 3||

首先计算 Need 矩阵（Need = Max - Allocation）：

|进程|Need(A,B,C)|
|---|---|
|P0|7, 4, 3|
|P1|1, 2, 2|
|P2|6, 0, 0|
|P3|0, 1, 1|
|P4|4, 3, 1|

**运行安全性算法**（Work 初始 = (3,3,2)）：

第一轮：寻找 Need[i] ≤ Work=(3,3,2) 的进程：

- P1 的 Need=(1,2,2) ≤ (3,3,2) ✓ → 选 P1，Work=(3,3,2)+(2,0,0)=(5,3,2)，Finish[1]=true

第二轮：Work=(5,3,2)，寻找剩余进程：

- P3 的 Need=(0,1,1) ≤ (5,3,2) ✓ → 选 P3，Work=(5,3,2)+(2,1,1)=(7,4,3)，Finish[3]=true

第三轮：Work=(7,4,3)：

- P4 的 Need=(4,3,1) ≤ (7,4,3) ✓ → 选 P4，Work=(7,4,3)+(0,0,2)=(7,4,5)，Finish[4]=true

第四轮：Work=(7,4,5)：

- P0 的 Need=(7,4,3) ≤ (7,4,5) ✓ → 选 P0，Work=(7,4,5)+(0,1,0)=(7,5,5)，Finish[0]=true

第五轮：Work=(7,5,5)：

- P2 的 Need=(6,0,0) ≤ (7,5,5) ✓ → 选 P2，Finish[2]=true

所有 Finish 为 true，**安全序列为 <P1, P3, P4, P0, P2>，系统处于安全状态**。

**判断 P1 申请 (1,0,2) 是否可以批准**：

- (1,0,2) ≤ Need[1]=(1,2,2) ✓
- (1,0,2) ≤ Available=(3,3,2) ✓
- 假装分配后：Available=(2,3,0)，Allocation[1]=(3,0,2)，Need[1]=(0,2,0)
- 重新运行安全性算法，可以找到序列 <P1,P3,P4,P0,P2>，安全 → **批准分配**

**判断 P4 申请 (3,3,0) 是否可以批准**：

- (3,3,0) ≤ Need[4]=(4,3,1) ✓
- (3,3,0) ≤ Available=(3,3,2) ✓
- 假装分配后：Available=(0,0,2)，重新运行安全算法……
- 此时 Need=(1,0,1) 的 P1 可能满足（Available=(0,0,2)，P1需A=1→不满足）
- 实际上找不到安全序列 → **拒绝，P4 等待**

### 7.5 银行家算法的局限性

死锁避免虽然比预防更宽松，但仍有明显限制：每个进程必须事先声明最大资源需求（实际很难做到）；进程之间必须相互独立（无同步约束）；资源数量必须固定；持有资源的进程不能中途退出。这些限制使得银行家算法在实际系统中几乎没有被直接使用。

## 八、死锁检测（Deadlock Detection）⭐⭐

死锁检测的思路是"放任自流，事后处理"——对资源分配没有任何限制，但定期运行检测算法，一旦发现死锁就采取恢复措施。

### 8.1 单实例资源：等待图（Wait-for Graph）

将资源分配图中的资源节点消去，若进程 Pi 正在等待进程 Pj 持有的资源，则在等待图中画一条从 Pi 指向 Pj 的有向边。

**判断死锁**：定期在等待图中检测是否存在环，环的检测算法复杂度为 **O(n²)**，其中 n 是进程数。如果存在环，则存在死锁。

### 8.2 多实例资源：检测算法

类似银行家算法的安全性算法，但有一个关键区别：

- 安全性算法中，初始化 Finish[i] = false（保守，假设每个进程都可能需要更多资源）
- 检测算法中，对于 `Allocation[i] == 0` 的进程（没有持有任何资源），初始化 Finish[i] = true（乐观，这些进程不可能是死锁的一部分）

完整算法步骤（复杂度 **O(m × n²)**）：

```
初始化：
  Work = Available
  若 Allocation[i] != 0，则 Finish[i] = false；否则 Finish[i] = true

循环寻找满足以下条件的进程 i：
  Finish[i] == false 且 Request[i] <= Work
找到则：Work = Work + Allocation[i]，Finish[i] = true，继续

结束：若存在 Finish[i] == false，则 Pi 处于死锁状态
```

> ⚠️ **与安全算法的区别**：检测算法使用 `Request`（当前实际请求量），安全算法使用 `Need`（最大剩余需求）。这是两个算法本质上的不同——检测算法是在现实状态下检测当前死锁，安全算法是在假设最坏情况下预测未来死锁。

### 8.3 检测频率的权衡

检测算法应该多频繁地运行，是一个工程权衡问题：

运行太频繁（如每次资源请求后都运行）：能精确定位是哪次请求导致的死锁，有利于恢复；但计算开销极大，影响系统性能。

运行太稀疏（如每小时一次）：开销小；但死锁可能已经存在很长时间，难以确定是哪些进程"导致"了死锁（图中可能有很多循环）。

实践中常用的策略：**周期性检测**，或者**当 CPU 利用率低于某个阈值时检测**（CPU 利用率低可能是进程都在等待资源，暗示可能有死锁）。

## 九、死锁恢复（Recovery）

一旦检测到死锁，操作系统必须打破它。主要有两大类方法：进程终止和资源抢占。

### 9.1 进程终止（Process Termination）

**方案一：一次性终止所有死锁进程。** 简单粗暴，肯定能解除死锁，但代价极大——所有已完成的工作（计算结果、临时文件等）都丢失。这是操作系统最常用的方案。

**方案二：逐个终止，每次终止后重新检测。** 按照"最小代价"原则逐一终止进程，直到死锁解除。每次终止后需重新运行检测算法，代价是多次运行检测算法。

**最小代价的判断依据**：选择哪个进程终止时，综合考虑以下因素——该进程的优先级、已运行时间（时间越短，损失越小）、还需运行多长时间、已占用的资源量（资源越多，终止后释放越多）、是否是交互式进程（交互式进程终止对用户体验影响大）。

### 9.2 资源抢占（Resource Preemption）

强制从某个进程手中剥夺资源，分配给其他进程，从而打破循环等待。核心问题有三：

**选择受害者（Selecting a Victim）**：与进程终止类似，选择代价最小的进程（考虑其持有的资源量、已运行时间等）。

**回滚（Rollback）**：被抢占资源的进程无法继续正常执行，必须回滚到某个安全检查点，从那里重新开始执行。这要求系统实现检查点（Checkpoint）机制，定期保存进程状态。

**防止饥饿（Starvation）**：如果每次都选同一个进程作为受害者，该进程会不断被回滚而永远无法完成，导致饥饿。解决方案是把**回滚次数**计入代价因子，被回滚越多次的进程代价越高，从而减少被再次选中的概率。

## 十、综合比较

|方法|资源分配策略|所需信息|主要优点|主要缺点|
|---|---|---|---|---|
|**预防（一次性申请）**|保守，低承诺|最大需求（进程声明）|无需抢占|效率低，延迟启动，需提前知道需求|
|**预防（抢占）**|保守|当前分配状态|适用于状态可保存/恢复的资源|抢占次数多于必要|
|**预防（资源排序）**|保守|无运行时开销|编译时可验证，设计时解决问题|禁止增量申请|
|**避免（银行家）**|介于预防和检测之间|最大需求 + 分配状态|无需抢占|需提前声明需求，可能长时间阻塞|
|**检测**|非常宽松，按需分配|分配状态 + 实际请求|不延迟进程启动，便于在线处理|固有的抢占损失，恢复代价高|
|**忽略**|无限制|无|零开销|发生死锁时只能重启|

## 十一、哲学家就餐问题——综合应用

哲学家就餐问题是死锁相关知识的经典综合应用场景，同时涉及互斥、死锁、饥饿三个概念。

**问题描述**：5 位哲学家围坐在圆桌旁，桌上有 5 根筷子（每两位哲学家之间各放一根）。哲学家有两个状态：思考和就餐。就餐需要同时拿到左右两根筷子（可重用资源）。哲学家持有一根筷子时，不会主动放下（占有且等待）；筷子不能被强夺（非抢占）。

两个核心要求：不允许两位相邻的哲学家同时就餐（互斥）；不允许任何哲学家饿死（无死锁、无饥饿）。

### 11.1 朴素方案（存在死锁）

```c
semaphore fork[5] = {1, 1, 1, 1, 1};

void philosopher(int i) {
    while (true) {
        think();
        wait(fork[i]);           // 拿左边筷子
        wait(fork[(i+1) % 5]);  // 拿右边筷子
        eat();
        signal(fork[(i+1) % 5]);
        signal(fork[i]);
    }
}
```

**死锁场景**：5 人同时拿起左边筷子，每人都等待右边（被邻居持有）的筷子，形成循环等待，死锁。这违反了循环等待条件。

### 11.2 改进方案一：限制同时就餐人数（信号量 room = 4）

```c
semaphore fork[5] = {1, 1, 1, 1, 1};
semaphore room = 4;   // 最多 4 人同时"进入就餐流程"

void philosopher(int i) {
    while (true) {
        think();
        wait(room);                    // 最多4人排队，保证至少1人能拿到两根筷子
        wait(fork[i]);
        wait(fork[(i+1) % 5]);
        eat();
        signal(fork[(i+1) % 5]);
        signal(fork[i]);
        signal(room);
    }
}
```

**为什么有效**：最多 4 人同时排队，而筷子共 5 根，所以在 4 人中，至少有一人可以拿到两根筷子，打破了"所有人都只拿到一根"的僵局。**无死锁，但可能饥饿**（某哲学家可能长期抢不到 room）。

### 11.3 改进方案二：管程方案（无死锁，可能仍饥饿）

```c
monitor dining_controller {
    enum {THINKING, HUNGRY, EATING} state[5];
    condition ForkReady[5];
    boolean fork[5] = {true, true, true, true, true};

    // 尝试就餐：只有两侧筷子都空闲才能开始
    void get_forks(int pid) {
        int left = pid;
        int right = (pid + 1) % 5;
        if (!fork[left])
            ForkReady[left].wait();   // 左筷不可用则等待
        fork[left] = false;
        if (!fork[right])
            ForkReady[right].wait();  // 右筷不可用则等待
        fork[right] = false;
    }

    // 释放筷子，并唤醒等待该筷子的哲学家
    void release_forks(int pid) {
        int left = pid;
        int right = (pid + 1) % 5;
        if (ForkReady[left].empty())
            fork[left] = true;
        else
            ForkReady[left].signal();
        if (ForkReady[right].empty())
            fork[right] = true;
        else
            ForkReady[right].signal();
    }
}
```

**管程方案的优点**：互斥由管程自动保证；逻辑清晰。**潜在问题**：仍可能饥饿（哲学家 i 两侧的邻居交替就餐，i 永远等待）。

### 例题 1：四个必要条件的判断与分析

**题目**：以下哪些场景不会发生死锁？请逐一分析原因（从四个必要条件角度）。

**(A)** 系统中有 2 个进程，只有 1 种资源，总量为 2 个实例。每个进程最多申请 1 个实例。

**(B)** 系统中有 3 个进程，共 3 种资源，每种 1 个实例。P1 持有 R1 等 R2，P2 持有 R2 等 R3，P3 持有 R3。P3 不需要任何其他资源。

**(C)** 系统中所有进程对任何资源的申请都是"原子性的"——要么立即拿到所有需要的资源，要么什么都不拿。

**解析：**

**(A) 不会发生死锁。** 每个进程最多申请 1 个实例，而总量为 2，所以两个进程各拿 1 个都能满足，不存在"等待"的情形。根本原因：**循环等待不可能形成**（因为没有进程会在持有资源的情况下等待另一个资源）。

**(B) 不会发生死锁。** 注意 P3 持有 R3 且**不需要任何其他资源**，因此 P3 可以顺利完成并释放 R3；P2 得到 R3 后完成，释放 R2；P1 得到 R2 后完成。**循环等待不存在**（等待链是 P1→P2→P3，P3 可以自行解脱，不是闭合的环）。这正好验证了：资源分配图中有等待链但**不成环**，则不死锁。

**(C) 不会发生死锁。** 原子性申请破坏了**占有且等待**条件——进程要么持有所有需要的资源（不等待），要么一个都不持有（等待但不占有）。没有"持有部分资源同时等待其余资源"的状态，循环等待无法形成。

### 例题 2：银行家算法——完整状态分析

**题目**：系统有 4 个进程（P1–P4），3 种资源（R1=9个, R2=3个, R3=6个）。当前状态如下：

| Claim(Max) R1,R2,R3 | Allocation R1,R2,R3 |         |
| ------------------- | ------------------- | ------- |
| P1                  | 3, 2, 2             | 1, 0, 0 |
| P2                  | 6, 1, 3             | 6, 1, 2 |
| P3                  | 3, 1, 4             | 2, 1, 1 |
| P4                  | 4, 2, 2             | 0, 0, 2 |

Available = (0, 1, 1)

**(1)** 计算 Need 矩阵。  
**(2)** 判断系统当前是否处于安全状态，若安全给出安全序列。  
**(3)** 若 P1 申请 (1, 0, 1)，能否批准？

**解析：**

**(1) Need = Max - Allocation：**

| 进程  | Need(R1,R2,R3) |
| --- | -------------- |
| P1  | 2, 2, 2        |
| P2  | 0, 0, 1        |
| P3  | 1, 0, 3        |
| P4  | 4, 2, 0        |

**(2) 运行安全性算法：** Work 初始 = (0, 1, 1)

第一轮：找 Need[i] ≤ (0,1,1)：

- P1: (2,2,2) ≤ (0,1,1)？ 否
- P2: (0,0,1) ≤ (0,1,1)？ 是！ → P2 完成，Work = (0,1,1)+(6,1,2) = (6,2,3)

第二轮：Work = (6,2,3)：

- P1: (2,2,2) ≤ (6,2,3)？ 是！ → P1 完成，Work = (6,2,3)+(1,0,0) = (7,2,3)

第三轮：Work = (7,2,3)：

- P3: (1,0,3) ≤ (7,2,3)？ 是！ → P3 完成，Work = (7,2,3)+(2,1,1) = (9,3,4)

第四轮：Work = (9,3,4)：

- P4: (4,2,0) ≤ (9,3,4)？ 是！ → P4 完成

**所有进程均可完成，系统处于安全状态，安全序列为 <P2, P1, P3, P4>。**

**(3) P1 申请 (1,0,1)：**

- 步骤1：(1,0,1) ≤ Need[1]=(2,2,2)？ 是 ✓
- 步骤2：(1,0,1) ≤ Available=(0,1,1)？ **否！(1 > 0)**，R1 不够。

**结论：P1 必须等待，此次申请不能批准**（不是不安全，而是资源当前不可用）。

> 注意区分"资源不够"（步骤2失败）和"分配后不安全"（步骤4失败）这两种被拒绝的原因！前者是暂时性的，等其他进程释放后可能被批准；后者是安全性考虑，即使资源够也不能给。

### 例题 3：死锁检测算法

**题目**：系统有 5 个进程（P0–P4），3 种资源（A:7个, B:2个, C:6个）。当前 Available=(0,0,0)（所有资源都被分配出去了）。

|Allocation(A,B,C)|Request(A,B,C)|
|---|---|---|
|P0|0, 1, 0|0, 0, 0|
|P1|2, 0, 0|2, 0, 2|
|P2|3, 0, 3|0, 0, 0|
|P3|2, 1, 1|1, 0, 0|
|P4|0, 0, 2|0, 0, 2|

**(1)** 系统当前是否存在死锁？若有，哪些进程处于死锁状态？

**(2)** 若此后 P2 又发出请求 (0,0,1)，系统状态如何变化？

**解析：**

**(1) 运行检测算法：**

初始化：Work = (0,0,0)。`Allocation[i] = 0` 的进程没有，但注意 P0 的 Allocation=(0,1,0) ≠ 0，P2 的 Allocation=(3,0,3) ≠ 0，均初始化 Finish[i]=false。

但等等——检测算法中，Allocation 全为 0 的进程才 Finish=true，其余均 false。本例中所有进程都有 Allocation ≠ 0，所以全部 Finish[i]=false。

第一轮：找 Request[i] ≤ Work=(0,0,0)：

- P0: (0,0,0) ≤ (0,0,0)？ 是！ → P0 完成，Work=(0,0,0)+(0,1,0)=(0,1,0)
- P2: (0,0,0) ≤ (0,1,0)？ 是！ → P2 完成，Work=(0,1,0)+(3,0,3)=(3,1,3)

第二轮：Work=(3,1,3)：

- P3: (1,0,0) ≤ (3,1,3)？ 是！ → P3 完成，Work=(3,1,3)+(2,1,1)=(5,2,4)

第三轮：Work=(5,2,4)：

- P1: (2,0,2) ≤ (5,2,4)？ 是！ → P1 完成，Work=(5,2,4)+(2,0,0)=(7,2,4)

第四轮：Work=(7,2,4)：

- P4: (0,0,2) ≤ (7,2,4)？ 是！ → P4 完成

**所有进程均可完成，系统当前无死锁。**（即使 Available 为 0，P0 和 P2 的 Request 也为 0，可以直接"完成"并释放资源给其他进程。）

**(2) P2 的 Request 变为 (0,0,1)：**

重新运行检测算法，Work=(0,0,0)：

第一轮：找 Request[i] ≤ (0,0,0)：

- P0: (0,0,0) ≤ (0,0,0)？ 是！ → P0 完成，Work=(0,1,0)
- 其他进程 Request 中至少有一个分量 > 0，均不满足

第二轮：Work=(0,1,0)：

- P1: (2,0,2) ≤ (0,1,0)？ 否
- P2: (0,0,1) ≤ (0,1,0)？ 否（C 分量：1 > 0）
- P3: (1,0,0) ≤ (0,1,0)？ 否（A 分量：1 > 0）
- P4: (0,0,2) ≤ (0,1,0)？ 否

没有更多进程可以完成，算法终止。**Finish[1]=Finish[2]=Finish[3]=Finish[4]=false。**

**结论：P1、P2、P3、P4 处于死锁状态。**（P2 多要了 1 个 C 资源，这 1 个 C 资源正好打破了安全执行序列，形成死锁。）

### 例题 4：死锁预防——资源排序的边界情况

**题目**：系统有互斥锁 L1、L2、L3，编号分别为 1、2、3（F(L1)=1, F(L2)=2, F(L3)=3）。规定进程必须按编号递增顺序申请锁。以下代码是否存在死锁风险？

```c
// 线程 A
void threadA() {
    lock(L1);
    lock(L2);
    // ... 操作共享数据
    unlock(L2);
    unlock(L1);
}

// 线程 B
void threadB() {
    lock(L2);
    lock(L3);
    // ... 操作共享数据
    unlock(L3);
    unlock(L2);
}

// 线程 C
void threadC() {
    lock(L1);
    lock(L3);
    // ... 操作共享数据
    unlock(L3);
    unlock(L1);
}
```

**(1)** 以上代码是否满足资源排序原则？  
**(2)** 三个线程并发执行，是否可能发生死锁？请给出证明或反例。  
**(3)** 若将线程 B 改为先申请 L3 再申请 L2，结果如何？

**解析：**

**(1) 满足资源排序原则。** 线程 A 按 L1→L2（1<2）；线程 B 按 L2→L3（2<3）；线程 C 按 L1→L3（1<3）。所有线程都按编号递增顺序申请锁，符合规定。

**(2) 不可能发生死锁。反证法：** 假设存在死锁，设涉及线程的集合形成循环等待 T_i1→T_i2→...→T_ik→T_i1。循环等待意味着 T_i1 等待 T_i2 持有的某个锁 La，而 T_i2 同时持有 La 并在等待 T_i3 持有的 Lb。由顺序申请规则，T_i2 持有 La 时申请 Lb，则 F(La) < F(Lb)。沿着循环依次推导，得到 F(La) < F(Lb) < ... < F(La)，矛盾。故不存在死锁。

**(3) 若线程 B 改为先 L3 后 L2（违反顺序）：** 此时线程 B 的申请顺序为 L3→L2（3>2，违规）。死锁可能发生：线程 B 持有 L3 等待 L2；线程 A 持有 L2 等待 L1（如果线程 C 同时持有 L1 等待 L3），则三者形成循环等待。具体构造：线程 A 持有 L1 申请 L2（L2 被 B 等待的路径上，但实际上 A 只申请 L2），线程 B 持有 L3 申请 L2，线程 C 持有 L1 和 L3。注意：B 持有 L3，C 在申请 L3 时会被阻塞；A 申请 L2 时，如果 L2 被 B 持有...实际上 A 和 B 不会形成简单的二元死锁，但这个例子说明了**打破顺序规则就为死锁埋下隐患**。

### 例题 5：综合分析——安全序列计算与动态请求

**题目**：系统有 4 个进程（P0–P3），2 种资源（A 共 6 个, B 共 4 个）。初始状态：

||Max(A,B)|Allocation(A,B)|Need(A,B)|
|---|---|---|---|
|P0|4, 2|1, 2|3, 0|
|P1|2, 3|1, 1|1, 2|
|P2|5, 4|3, 1|2, 3|
|P3|3, 2|1, 0|2, 2|

Available = (0, 0)（注意：所有资源全部分配完毕）

**(1)** 当前是否安全？  
**(2)** 若 P1 完成并释放其资源，新的 Available 是多少？此时是否安全？  
**(3)** 在 (2) 的基础上，P0 申请 (1,0)，能否批准？批准后系统是否仍安全？  
**(4)** 在 (2) 的基础上，P3 申请 (2,2)，能否批准？

**解析：**

**(1) Available=(0,0)：**

找 Need[i] ≤ (0,0)：

- P0: (3,0)？ 否（A 分量 3 > 0）
- P1: (1,2)？ 否
- P2: (2,3)？ 否
- P3: (2,2)？ 否

没有任何进程可以完成。**系统当前不安全！但尚未死锁**（注意：因为 Allocation 非零的进程有 Request=Need，但当前 Available 不够满足任何人）。

实际上，若进程按当前状态继续等待，确实会死锁——所有进程都等待资源，但没有资源可以被释放，这就已经是死锁状态了。

> ⚠️ **关键辨析**：安全算法中 Finish[i] 的初始值在检测算法和安全算法中不同！本题如果按**安全算法**（Need = 最大剩余需求），所有 Finish 初始为 false，且 Work=(0,0)，没有进程满足 Need≤Work，所有 Finish 仍为 false，不安全。若按**检测算法**（Request = 实际当前请求），结果相同（因为 Need = 实际请求，且 Available=0）。

**结论：当前已处于死锁状态**（P0、P1、P2、P3 均死锁）。

**(2) P1 完成并释放 Allocation[1]=(1,1)：**

Available = (0,0) + (1,1) = (1,1)

重新计算 Need（P1 已退出，只考虑 P0、P2、P3）：

Work = (1,1)：

- P0: Need=(3,0)，(3,0) ≤ (1,1)？ 否
- P2: Need=(2,3)，否
- P3: Need=(2,2)，否

仍然没有进程可以完成，**系统仍不安全**。（P1 的提前退出释放了一些资源，但还不足以启动任何进程的剩余需求。）

**(3) P0 申请 (1,0)：**

- (1,0) ≤ Need[0]=(3,0)？ 是 ✓
- (1,0) ≤ Available=(1,1)？ 是 ✓
- 假装分配：Available=(1,1)-(1,0)=(0,1)，Allocation[0]=(2,2)，Need[0]=(2,0)

运行安全算法，Work=(0,1)：

- P0: (2,0) ≤ (0,1)？ 否
- P2: (2,3) ≤ (0,1)？ 否
- P3: (2,2) ≤ (0,1)？ 否

仍无安全序列。**不能批准！撤销假装分配，P0 等待。**

**(4) P3 申请 (2,2)：**

- (2,2) ≤ Need[3]=(2,2)？ 是 ✓
- (2,2) ≤ Available=(1,1)？ **否！B 分量：2 > 1**

**因资源不足，直接拒绝，P3 等待。**（不需要运行安全算法，资源根本不够。）

**本题深层教训**：一个状态下 Available=(0,0)，而所有进程都还需要资源，这本身就是死锁。即使某个进程提前完成并释放资源，也不一定能解除其余进程的死锁——这体现了死锁的"传染性"和难以局部解决的特点。
