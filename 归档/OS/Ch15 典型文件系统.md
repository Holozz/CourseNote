## 一、前置回顾：文件系统架构

```
User Space:    Process ──→ fopen() / fread() / fwrite() / fclose()   (库调用)
                              ↓
Kernel:                       open() / read() / write() / close()    (系统调用)
                              ↓
                     FS Operations (文件系统操作层)
                    ┌─────────┼─────────┐
                    ↓         ↓         ↓
               Ext4 函数   FAT32 函数  NTFS 函数 ...   (FS 特定实现)
                    ↓         ↓         ↓
Devices:         ─────── 存储设备 ───────
```

> [!important] 关键分层
> - **库调用**（`fopen`、`fread`）→ 用户态，提供缓冲
> - **系统调用**（`open`、`read`）→ 内核态，真正进入 OS
> - **FS 特定函数** → 每种文件系统实现自己的底层逻辑
> - 进程通过系统调用触发 FS 操作，再去访问存储设备

## 二、文件与文件属性

### 2.1 文件的基本问题

> **通俗理解**：文件是一个"黑盒子"——用户看到的是一个有名字、有内容的东西，不需要关心它怎么在磁盘上物理存储。文件系统负责把用户看到的"逻辑视图"翻译成磁盘上的"物理存储"。

对于一个文本文件 `test.txt`，里面存着 `hello_world\n`，我们需要回答三个问题：

| 问题 | 答案 | 本质 |
|------|------|------|
| **Content？**（内容） | 文件的内容是什么 | 文件的数据 |
| **Filename？**（文件名） | 文件叫什么 | 其**父目录**的内容 |
| **File size？**（大小） | 文件有多大 | 文件的**属性**（元数据） |

> [!important] 关键洞察
> **一旦文件有了名字，它就独立于进程、用户甚至创建它的系统**——文件变成了一种持久化、可共享的抽象。

---

### 2.2 文件属性

文件属性（File Attributes）是文件系统管理文件的**元数据**，不同文件系统支持的属性有所不同。

| 属性 | 说明 | FAT32 | NTFS | Ext2/3/4 |
|------|------|:-----:|:----:|:--------:|
| **Name** | 人类可读的文件名 | ✅ | ✅ | ✅ |
| **Identifier** | 文件系统内部的唯一编号 | ✅ | ✅ | ✅ |
| **Type** | 文本文件/源文件/可执行文件等 | — | — | — |
| **Location** | 指向设备和文件在设备上位置的指针 | ✅ | ✅ | ✅ |
| **Size** | 文件大小（字节/字/块数） | ✅ | ✅ | ✅ |
| **Time/Date** | 创建、最后修改、最后访问时间 | ✅ | ✅ | ✅ |
| **Permission** | 访问控制信息（读/写/执行） | ❌ | ✅ | ✅ |
| **Owner** | 文件所有者 | ❌ | ✅ | ✅ |

> [!warning] FAT32 的设计缺陷
> FAT32 的设计**没有任何安全成分**——没有权限控制和所有者概念。这是 FAT32 作为早期文件系统的历史局限性。

---

### 2.3 文件权限（Unix 系统）

Unix/Linux 权限模型示例：

```
$ ls -l
-rwxr-xr-x  1 alice  cs_staff  2048  Jan  1  12:00  myfile
```

权限字符串 `rwxr-xr-x` 分三段，每段 3 位：

| 段 | 目标 | 解释 | 示例值 |
|----|------|------|--------|
| 第 1 段 | **Owner**（文件所有者） | rwx = 7 | 可读、可写、可执行 |
| 第 2 段 | **Group**（文件所属组） | r-x = 5 | 可读、可执行（不可写） |
| 第 3 段 | **Others**（其他人） | r-x = 5 | 可读、可执行（不可写） |

常见权限数字：

| 数字 | 权限 | 含义 |
|------|------|------|
| 755 | rwxr-xr-x | 所有者全权，其他人读+执行 |
| 775 | rwxrwxr-x | 所有者和组全权，其他人读+执行 |
| 664 | rw-rw-r-- | 所有者和组可读写，其他人只读 |
| 600 | rw------- | 仅所有者可读写 |

---

### 2.4 修改文件属性

| 属性 | 命令 | 系统调用 |
|------|------|----------|
| Name | `mv` | `rename()` |
| Size | 写入文件的各种工具 | `write()`, `truncate()` 等 |
| Permission | `chmod` | `chmod()` |
| Owner | `chown` | `chown()` |
| Access/Creation/Modification time | `touch` | `utime()` |

## 三、文件操作的系统调用

### 3.1 FILE 结构揭秘

> **通俗理解**：C 语言的 `FILE*` 是标准库在用户态给每个打开文件分配的一个"记录本"，里面记着这个文件的内核编号（文件描述符）和一个缓冲区。

```c
FILE *fopen(const char *filename, const char *mode);
```

**FILE 结构内部有什么？**
1. **文件描述符（File Descriptor）**：内核中定位打开文件的"编号"
2. **缓冲区（Buffer）**：用户态缓冲，减少系统调用次数

> [!tip] 验证文件描述符
> ```c
> int main(void) {
>     printf("fd of stdin  = %d\n", fileno(stdin));   // 0
>     printf("fd of stdout = %d\n", fileno(stdout));  // 1
>     printf("fd of stderr = %d\n", fileno(stderr));  // 2
> }
> ```
> stdin、stdout、stderr 的类型就是 `FILE*`！每个进程默认打开这三个。

---

### 3.2 打开文件的完整流程

> **核心事实**：**打开一个文件只涉及文件的路径名和属性，而不涉及文件内容！**

```
进程 ──(1) 提供路径名──→  OS  ──(2) 在磁盘上查找目标文件的属性──→  磁盘
                              ←──(3) 磁盘返回文件属性─────────
       ┌─────────────────
       │  (4) OS 将属性关联到一个编号，这个编号就是文件描述符
       │  (5) OS 将文件描述符返回给进程
       ↓
  进程拿到 fd=3
```

| 步骤 | 谁做的 | 做什么 |
|------|--------|--------|
| (1) | 进程 | 提供路径名给 OS |
| (2) | OS（FS Operations） | 在磁盘上查找目标文件的属性 |
| (3) | 磁盘 | 返回文件属性 |
| (4) | OS | 将属性关联到一个编号 → 文件描述符 |
| (5) | OS | 返回文件描述符给进程 |

> [!important] 此过程是 OS 无关和 FS 无关的！所有操作系统的基本文件打开流程是一样的。

---

### 3.3 文件描述符的本质

> **通俗理解**：文件描述符就是一个**数组下标**。每个进程有一个"打开文件数组"，fd 就是这个数组的索引。

```
进程 A:                       进程 B:
fd 数组                       fd 数组
[0] → stdin                   [0] → stdin
[1] → stdout                  [1] → stdout
[2] → stderr                  [2] → stderr
[3] → ──────┐                 [3] → ──────┐
[4] → ──┐   │                 [4]         │
         │   │                             │
         ↓   ↓                             ↓
     Open-File Table (打开文件表)
     ┌─────────────────────────────┐
     │  同一个文件被两个进程打开时， │
     │  内核只用一个结构维护它！     │
     └─────────────────────────────┘
```

> [!important] 关键结论
> - 文件描述符是**每个进程独立**的数组索引
> - 内核的 Open-File Table 是**全局的**
> - 同一个文件即使被多个进程打开，内核只用**一个结构**来维护文件信息

---

### 3.4 read() 系统调用

```c
int read(int fd, void *buffer, int bytes_to_read);
// 从文件 → 用户态缓冲区
```

**read() 的四个步骤**：

| 步骤 | 操作 |
|------|------|
| **Step 1** | 检查是否到达文件末尾（比较文件大小和文件当前 seek 位置） |
| **Step 2** | 通过 FS 特定函数，从磁盘读取数据到**内核缓冲区** |
| **Step 3** | 文件数据先存放在内核的固定大小缓存中 |
| **Step 4** | 将数据从内核缓存**复制到用户态缓冲区** |

```
进程 (userspace buffer)          ← Step 4: 复制数据
     ─────────────────────────
内核 (fixed-size cache)          ← Step 2-3: 磁盘读取
     ─────────────────────────
磁盘                              ← Step 2: 物理 I/O
```

> [!tip] 常见的触发 read() 的库调用
> `scanf()`, `fscanf()`, `getchar()`, `fgetc()`, `gets()`, `fgets()`, `fread()` → 最终都调用 `read()`

---

### 3.5 write() 系统调用

```c
int write(int fd, void *buffer, int bytes_to_write);
// 从用户态缓冲区 → 文件
```

**write() 的四个步骤**：

| 步骤 | 操作 |
|------|------|
| **Step 1** | 将数据从用户态缓冲区写入**内核缓存** |
| **Step 2** | 根据数据长度更新文件大小（如有变化）和文件 seek 位置 |
| **Step 3** | 系统调用返回 |
| **Step 4** | 内核缓存中的数据会**不时地被刷新（flush）到磁盘** |

> [!warning] write() 返回 ≠ 数据已落盘！
> `write()` 返回只表示数据已复制到内核缓冲区，实际写入磁盘是**延迟的**（由内核调度）。这就是为什么突然断电可能丢失"已经写入"的数据。

> [!tip] 常见的触发 write() 的库调用
> `printf()`, `fprintf()`, `putchar()`, `fputc()`, `puts()`, `fputs()`, `fwrite()` → 最终都调用 `write()`

## 四、目录与目录遍历

### 4.1 目录的本质

> [!important] 核心认知
> **目录就是一个文件！**——目录也有文件属性，也有文件内容。目录的"内容"就是它所包含的文件名和对应属性的映射表。

| 问题 | 答案 |
|------|------|
| 目录有文件属性吗？ | **有**（FS 相关） |
| 目录有文件内容吗？ | **有**（即文件名到属性的映射） |

---

### 4.2 路径名遍历过程

以打开 `/bin/ls` 为例：

```
Step (1) 进程提供路径名 "/bin/ls"
         ↓
Step (2) OS 读取根目录 '/' 的目录文件
         ↓
Step (3) 磁盘返回根目录文件
         ↓
Step (4) OS 在根目录文件中查找名字 "bin"
         （找到后，利用 bin 的属性信息获取其目录文件）
         ↓
Step (5) OS 读取 "/bin" 的目录文件
         ↓
Step (6) OS 在 bin 目录中查找名字 "ls"
         （找到后，就知道了 "/bin/ls" 的文件属性）
         ↓
         开始之前讨论的打开文件流程
```

> [!tip] 这就是为什么路径名中每个目录都要依次查找——OS 需要**逐级解析**路径，直到找到最终目标文件。

---

### 4.3 文件创建的本质

> [!important] 
> **文件创建 = 目录文件的更新！**

| 操作 | 系统调用 | 对目录的影响 | 例子 |
|------|----------|-------------|------|
| 创建目录 | `mkdir()` | 新增一个目录文件 | `mkdir test` |
| 创建文件 | `open()`, `creat()` | 在目录中添加一个条目 | `cp src dst` |
| 删除文件 | `unlink()` | 在目录中移除一个条目 | `rm file` |
| 删除目录 | `rmdir()` | 移除目录文件 | `rmdir test` |

## 五、典型文件系统 — FAT32

### 5.1 FAT 系列概述

FAT（File Allocation Table，文件分配表）是微软 DOS/Windows 最早的文件系统家族。

| 版本 | 簇地址长度 | 最大簇数 | 说明 |
|------|-----------|----------|------|
| **FAT12** | 12 bits | ~4K | 最早版本，用于软盘 |
| **FAT16** | 16 bits | ~64K | DOS/早期 Windows |
| **FAT32** | 32 bits（实用 28 bits） | ~256M | 目前最常见的 FAT 版本 |

FAT 的核心思想：**文件分配表**（一个大数组，每个条目指向文件的下一个簇）。

---

### 5.2 FAT32 分区布局

```
┌──────────┬───────┬──────────┬──────────┬─────────────────────┐
│   Boot   │ FSINFO│   FAT1   │   FAT2   │    Data Area        │
│  Sector  │       │ (主 FAT) │ (备 FAT) │ (Root Dir + Files)  │
│  32扇区  │       │ 1009扇区 │ 1009扇区 │ 从扇区 2050 开始...  │
└──────────┴───────┴──────────┴──────────┴─────────────────────┘
```

**各区域的作用**：

| 区域 | 作用 |
|------|------|
| **Boot Sector** | 存储 FS 元信息：每扇区字节数、每簇扇区数、保留扇区数、FAT 数量及大小、根目录起始簇号、数据区起始位置 |
| **FSINFO** | 记录空闲簇数量和下一个空闲簇号，加速分配 |
| **FAT1** | 主文件分配表：每项 32 bits（实用 28 bits），记录每个簇的状态 |
| **FAT2** | FAT1 的备份副本 |
| **Data Area** | 从 Cluster #2 开始存储实际数据（Cluster #0 和 #1 保留） |

**FAT 表项的含义**（32-bit 条目）：

| 值 | 含义 |
|----|------|
| `0x00000000` | 空闲（未分配）簇 |
| `0x0FFFFFF7` | 损坏簇 |
| `>= 0x0FFFFFF8` | 文件结束（EOF）标记 |
| 其他值 | 指向文件下一个簇的编号 |

---

### 5.3 目录项（Directory Entry）

**短文件名目录项（8+3 命名约定）**——32 字节固定结构：

| 字节偏移 | 长度 | 内容 |
|----------|------|------|
| 0 | 1 | 文件名首字符（`0x00`=未使用，`0xE5`=已删除） |
| 1-10 | 10 | 文件名 + 扩展名（8+3 格式） |
| 11 | 1 | 文件属性（只读/隐藏/系统/卷标/目录/归档） |
| 12 | 1 | 保留 |
| 13-19 | 7 | 创建和访问时间信息 |
| 20-21 | 2 | **首簇号高 2 字节**（FAT32 专用） |
| 22-25 | 4 | 最后写入时间信息 |
| 26-27 | 2 | **首簇号低 2 字节** |
| 28-31 | 4 | **文件大小**（最大 4GB-1） |

> [!warning] 文件大小上限
> 目录项中文件大小字段为 32 位 → **单个文件最大 4GB - 1 字节**。这是 FAT32 的硬限制！

> [!warning] 8+3 命名限制
> FAT32 的原生目录项只支持 **8 字符文件名 + 3 字符扩展名**。那长文件名怎么存？→ 使用 LFN 机制。

---

### 5.4 长文件名（LFN）机制

LFN（Long File Name）通过**额外的目录项**存储长文件名。

**LFN 目录项结构**：

| 字节偏移 | 长度 | 内容 |
|----------|------|------|
| 0 | 1 | **序号**（序号 OR 0x40 表示最后一个 LFN 条目） |
| 1-10 | 10 | 5 个 Unicode 字符 |
| 11 | 1 | 文件属性 → **永远是 0x0F**（标记这是 LFN 条目） |
| 12 | 1 | 保留 |
| 13 | 1 | **校验和** |
| 14-25 | 12 | 6 个 Unicode 字符 |
| 26-27 | 2 | 保留 |
| 28-31 | 4 | 2 个 Unicode 字符 |

> [!important] LFN 关键特征
> - 每个 LFN 条目存 **13 个 Unicode 字符**（每个字符 2 字节）
> - 序号**倒序排列**（序号最大的在最前面）
> - 终末条目的序号 **OR 0x40**
> - LFN 条目后紧跟**正常的短文件名目录项**

**示例**：文件名 `I_love_the_operating_system_course.txt`

```
目录文件中:
  LFN #3 (序号 = 0x43): "m_cou" "rse.tx" "t"
  LFN #2 (序号 = 0x02): "erati" "ng_sys" "te"
  LFN #1 (序号 = 0x41): "I_lov" "e_the_" "op"   ← 0x40 标记终止
  Normal Entry:          "I_LOVE~1.TXT" ...       ← 短文件名别名
```

> [!tip] 短文件名别名
> 即使使用长文件名，FAT32 仍会生成一个 8+3 格式的**短文件名别名**（如 `I_LOVE~1.TXT`），以兼容旧系统。

---

### 5.5 读取文件的过程

任务：读取 `C:\windows\explorer.exe`（假设首簇 = #32）

```
Step 1: 从 Cluster #32 读取数据
        在 FAT 表中查 Cluster #32 → 值为 33
        ↓
Step 2: 从 Cluster #33 读取数据
        在 FAT 表中查 Cluster #33 → 值为 EOF (>= 0x0FFFFFF8)
        ↓
Step 3: 遇到 EOF → 已到文件末尾
        根据文件大小确定最后一个簇中有多少有效字节
```

---

### 5.6 删除文件的过程

任务：删除 `C:\windows\explorer.exe`

```
Step 1: 释放所有簇
        - 在 FAT 中将该文件的所有簇标记为 0（空闲）
        - 更新 FSINFO：空闲簇数增加，下一个空闲簇更新

Step 2: 修改目录项
        - 将目录项的第一字节改为 0xE5（标记为"已删除"）
        - LFN 条目也做同样处理
        完成！文件"已删除"
```

> [!warning] 删除 ≠ 真正删除！
> FAT32 删除文件时：
> - **数据内容本身没有被擦除**——只是 FAT 条目和目录项首字节被改
> - 只要这些簇没有被新数据覆盖，**删除的数据可以恢复**
> - 安全删除需要**覆写数据**（多次随机覆写）
> - 这是**性能（快速删除）与安全**之间的权衡

---

## 六、典型文件系统 — Ext2/3/4

### 6.1 Ext 系列概述

| 版本 | 最大文件大小 | 最大分區大小 | 说明 |
|------|-------------|-------------|------|
| **Ext2** | 1 TB | 4 TB | 经典 Linux FS，无日志 |
| **Ext3** | 2 TB | 4 TB | 添加了日志功能（journaling） |
| **Ext4** | 16 TB | 1 EB | 48 位寻址，extent 分配，2008 年并入内核 |

> **Ext4 是向后兼容的**——可以当作 Ext2/3 来挂载。

---

### 6.2 索引节点分配

Ext 系列采用**索引节点（Index-Node, inode）分配**方式——用一个集中式的 inode 数组来管理所有文件。

```
目录项：                     Inode Table:
Filename  | Inode#          ┌──────────────────┐
rock.mp3  | 1         ←──→  │ Inode #1 (rock)   │
game.exe  | 2         ←──→  │ Inode #2 (game)   │
ubuntu.iso| 3         ←──→  │ Inode #3 (ubuntu) │
          |                 │ ...               │
          |                 └──────────────────┘
```

> [!tip] 数组布局 → 快速查找
> Inode 表是**数组**结构，已知 inode 号就能 O(1) 定位该 inode。这与 FAT 的链表式遍历根本不同。

---

### 6.3 组结构布局

Ext2/3/4 为提高**可靠性**和**性能**，将文件系统划分为多个**块组（Block Group）**：

```
Group 0:  ┌─────────┬────────┬───────┬───────┬──────────────┐
          │Superblock│  GDT   │ Block │ Inode │ Inode │ Data  │
          │ (主超块)  │        │Bitmap │Bitmap │ Table │Blocks │
          └─────────┴────────┴───────┴───────┴───────┴──────┘
                                    ↑        ↑
Group 1:  ┌─────────┬────────┬───────┬───────┬───────┬──────┐
          │Superblock│  GDT   │ Block │ Inode │ Inode │ Data │
          │ (备超块)  │(不同)   │Bitmap │Bitmap │ Table │Blocks│
          └─────────┴────────┴───────┴───────┴───────┴──────┘
```

**各区域说明**：

| 区域 | 作用 |
|------|------|
| **Superblock** | 存储 FS 全局信息：inode 总数、块总数、保留块数、空闲块数、空闲 inode 数、块大小等 |
| **GDT**（Group Descriptor Table） | 存储该组的：block bitmap 起始位置、inode bitmap 起始位置、inode table 起始位置、空闲块计数、空闲 inode 计数 |
| **Block Bitmap** | 位图，标记每个数据块的分配状态 |
| **Inode Bitmap** | 位图，标记每个 inode 的分配状态 |
| **Inode Table** | 该组所有 inode 的数组 |
| **Data Blocks** | 实际存储文件数据的块 |

**为什么分组？**

| 目的 | 机制 |
|------|------|
| **可靠性** | 每个组都有 Superblock 和 GDT 的**备份副本**（Group 0 的称为主超块，其他的称为备份超块） |
| **性能** | 同一组的 inode 通常引用同一组的数据块 → inode 和数据**物理上接近** → 减少磁盘寻道 |

> [!tip] 局部性原则
> 分组利用了存储的**局部性原理**：将文件的元数据（inode）和数据放在同一组，查找更快。

---

### 6.4 Inode 结构

Inode 是 Ext 文件系统的核心结构（128 字节长），存储了除文件名外的**所有**文件信息。

| 字节偏移 | 长度 | 内容 |
|----------|------|------|
| 0-1 | 2 | 文件类型和权限 |
| 2-3 | 2 | User ID |
| 4-7 | 4 | 低 32 位文件大小 |
| 8-23 | 16 | 时间信息（创建/修改/访问） |
| 24-25 | 2 | Group ID |
| 26-27 | 2 | **链接计数**（该 inode 被多少个目录项指向） |
| ... | ... | ... |
| 40-87 | 48 | **12 个直接数据块指针** |
| 88-91 | 4 | **单重间接块指针**（指向一个存满块地址的块） |
| 92-95 | 4 | **双重间接块指针** |
| 96-99 | 4 | **三重间接块指针** |
| ... | ... | ... |
| 108-111 | 4 | 高 32 位文件大小 |

> [!important] 文件名不存于 inode！
> Inode 存储了文件的**几乎所有信息，唯独没有文件名**。文件名存储在**目录文件**的目录项中，目录项将文件名映射到 inode 号。

---

### 6.5 数据块寻址：直接/间接/双重间接/三重间接

Ext 文件系统采用**多级索引**来管理文件的数据块：

```
Inode
├── Direct Block #0     → Data Block (数据)
├── Direct Block #1     → Data Block (数据)
├── ... (共 12 个)
├── Direct Block #11    → Data Block (数据)
├── Indirect Block      → Block[0] → Data Block
│                        → Block[1] → Data Block
│                        → ... (共 块大小/4 个)
├── Double Indirect     → Indirect[0] → Block[...] → Data Blocks
│                        → Indirect[1] → ...
│                        → ... (共 块大小/4 个间接块)
└── Triple Indirect     → Double Indirect[...] → ...
```

> [!important] 最大文件大小计算
> 
> 设块大小为 4096B (= 2^12)，每个块地址 4 字节：
> 
> | 层 | 可寻址块数 | 可寻址大小 |
> |----|-----------|-----------|
> | 直接 (12 个) | 12 | 48 KB |
> | 单重间接 | 4096/4 = 1024 | 4 MB |
> | 双重间接 | 1024² | 4 GB |
> | 三重间接 | 1024³ | 4 TB |
> 
> 理论最大文件大小 ≈ **4 TB**（对 Ext2/3），Ext4 扩展到 **16 TB**。
> 
> 公式：2^64 - 1 ≈ 16 × 2^30 GB

## 七、链接文件

### 7.1 硬链接（Hard Link）

> **通俗理解**：硬链接就是给同一个文件**起了多个名字**。就像一个人有中文名和英文名，但指的是同一个人。

```bash
$ ls /dir1/12.jpg
12.jpg
$ ln /dir1/12.jpg /my_link     # 创建硬链接
$ _
```

**硬链接的本质**：

```
创建前：                        创建后：
目录 /dir1:                    目录 /dir1:          目录 /:
Inode#  Filename               Inode#  Filename     Inode#  Filename
5086    12.jpg                 5086    12.jpg       5086    my_link
                                ↑                    ↑
                                 └── 指向同一个 inode ──┘
```

> [!important] 关键特性
> - **不创建新文件内容**——只增加一个目录项
> - 两个路径名指向**完全相同的 inode**
> - 删除任何一个链接不影响另一个（只要链接计数 > 0）

---

### 7.2 链接计数

Inode 中的 **link count** 字段记录有多少个目录项指向该 inode。

```
Inode #5086
Link Count: 2          ← 因为 12.jpg 和 my_link 都指向它
```

**特殊硬链接**：

| 目录项 | 含义 | Link Count 的影响 |
|--------|------|-------------------|
| `.` | 指向自身的硬链接 | — |
| `..` | 指向父目录的硬链接 | — |

> [!tip] 为什么新目录的 link count 初始为 2？
> ```bash
> $ mkdir temp
> $ stat temp
> Links: 2
> ```
> - **链接 #1**：父目录中的 `temp` 条目
> - **链接 #2**：temp 目录内部的 `.` 条目
> - 每个子目录还会通过 `..` 给父目录增加 link count。所以有大量子目录的目录，link count 很大。

---

### 7.3 符号链接（Symbolic Link）

> **通俗理解**：符号链接（软链接）就像 Windows 中的**快捷方式**——它是一个独立的文件，内容存储的是目标路径字符串。

```bash
$ ln -s /dir1/12.jpg /my_link   # 创建符号链接
$ ls -l /my_link
/my_link -> /dir1/12.jpg
```

**符号链接的本质**：

```
目录 /:             
Inode#  Filename    Inode #6120 (全新的 inode!)
6120    my_link     → 内容存储字符串 "/dir1/12.jpg"
```

> [!important] 关键特性
> - **创建一个新的 inode**（与硬链接不同）
> - 符号链接文件的**内容**就是目标路径字符串
> - 删除原始文件后，符号链接变成**悬挂链接**（指向不存在）

---

### 7.4 硬链接 vs 符号链接

| 特性 | 硬链接 (Hard Link) | 符号链接 (Symbolic Link) |
|------|:---:|:---:|
| 新建 inode？ | ❌ | ✅（新的 inode） |
| 跨文件系统？ | ❌ | ✅ |
| 链接到目录？ | ❌（通常不允许） | ✅ |
| 原文件删除后？ | 仍可访问（link count > 1） | 悬挂链接（broken） |
| 存储内容 | 与原文件共享数据块 | 目标路径字符串 |
| `ln` 命令 | `ln target link` | `ln -s target link` |

## 九、例题精讲

### 例题 1：文件打开流程

<details>
<summary>题目：以下关于文件打开过程的描述中，哪个是正确的？</summary>

A. 打开文件时，操作系统会读取文件的全部内容到内存
B. 打开文件时，操作系统只获取文件的属性（元数据），不读取文件内容
C. 文件描述符是一个全局唯一的标识符，所有进程共用
D. 每个文件被打开时，内核都会创建一个新的文件属性结构

</details>

<details>
<summary>答案</summary>

**B** 是正确的。

**解析**：
- A ❌：打开文件只涉及属性和路径名，**不涉及文件内容**
- B ✅：这正是课件的核心结论
- C ❌：文件描述符是**每个进程独立的**数组索引，不同进程可以有相同编号的 fd 指向不同文件
- D ❌：同一个文件被多个进程打开时，内核只用**一个结构**维护它

</details>

---

### 例题 2：FAT32 单文件大小上限

<details>
<summary>题目：为什么 FAT32 单个文件最大不能超过 4 GB？</summary>

</details>

<details>
<summary>答案</summary>

因为 FAT32 的目录项中，**文件大小字段只有 4 字节（32 位）**，最大能表示的无符号整数是：
> 2^32 - 1 = 4,294,967,295 字节 ≈ **4 GB - 1 字节**

这 4 个字节位于目录项结构的字节偏移 28-31 处，是 FAT32 设计的硬性限制。

</details>

---

### 例题 3：FAT32 删除文件

<details>
<summary>题目：FAT32 删除文件时具体做了什么？删除的数据是否还能恢复？为什么？</summary>

</details>

<details>
<summary>答案</summary>

**删除操作做了两件事：**

1. **释放所有簇**：在 FAT 表中将该文件占用的所有簇条目设为 `0x00000000`（空闲），更新 FSINFO 中的空闲计数
2. **标记目录项**：将目录项的第一个字节改为 `0xE5`（表示"此条目已释放"）

**数据可以恢复**，因为：
- 删除操作**没有真正擦除数据块**的内容
- 只要这些簇没有被新数据覆盖，原始数据仍然完整存在
- 数据恢复软件就是扫描所有标记为空闲的簇，尝试重建文件

**安全删除**需要多次随机覆写数据块（如 DoD 5220.22-M 标准的 3-pass 覆写），这正是安全与性能之间的经典权衡。

</details>

---

### 例题 4：硬链接与链接计数

<details>
<summary>题目：某个 inode 的 link count 为 0 意味着什么？什么时候文件数据会被真正删除？</summary>

</details>

<details>
<summary>答案</summary>

- **link count = 0** 意味着没有任何目录项指向该 inode
- 当 link count 降到 0 **且**没有进程打开该文件时，文件的数据块和 inode 才会被真正释放（de-allocate）
- 如果有进程仍打开着文件（即使 link count = 0），数据不会被立刻释放——进程关闭文件后才释放

**示例**：
```bash
$ ln file hardlink    # link count = 2
$ rm file             # link count = 1（hardlink 仍存在，文件可访问）
$ rm hardlink         # link count = 0（文件数据被释放）
```

> [!tip] 这就是"unlink"系统调用的名字由来——它不是"delete"，只是"断开一个链接"。

</details>

### 例题 5：Ext 多级索引

<details>
<summary>题目：设 Ext2 文件系统块大小为 4 KB，每个块地址占 4 字节。请问：
(1) 一个 inode 的 12 个直接指针能管理多大的文件？
(2) 单重间接指针能额外管理多大？
(3) 使用直接+单重间接+双重间接，能管理的最大文件约为多少？</summary>

</details>

<details>
<summary>答案</summary>

**(1) 直接指针**：12 × 4 KB = **48 KB**

**(2) 单重间接指针**：
- 一个间接块可存储 4 KB / 4 B = 1024 个块地址
- 可管理：1024 × 4 KB = **4 MB**

**(3) 双重间接**：
- 一个双重间接块指向 1024 个间接块，每个间接块指向 1024 个数据块
- 可管理：1024² × 4 KB = 1024 × 4 MB = **4 GB**

合计：48 KB + 4 MB + 4 GB ≈ **4 GB**

> 加上三重间接（1024³ × 4 KB = 4 TB），可管理最大文件 ≈ **4 TB**。

</details>

## 十、知识点速查

| 知识点 | 核心内容 | 要点提示 |
|--------|----------|----------|
| **FILE 结构** | 包含 fd + 用户态缓冲区 | 由 `fopen()` 通过 `malloc()` 创建 |
| **文件描述符 (fd)** | 每个进程独立的打开文件数组索引 | stdin=0, stdout=1, stderr=2 |
| **打开文件流程** | 仅涉及路径名和属性，不涉及内容 | OS/FS 无关的通用流程 |
| **read() 四步** | 检查 EOF → 磁盘读 → 进内核缓存 → 复制到用户空间 | 数据过内核缓存 |
| **write() 四步** | 复制到内核缓存 → 更新大小/seek → 返回 → 延迟刷盘 | 返回 ≠ 落盘！ |
| **目录** | 目录也是文件，有属性和内容 | 目录内容 = 文件名→属性映射表 |
| **路径遍历** | OS 逐级解析路径直到找到目标 | /bin/ls → 读 / → 找 bin → 读 /bin → 找 ls |
| **文件创建** | = 目录文件的更新 | open/creat/mkdir 都是修改目录 |
| **FAT 布局** | Boot → FSINFO → FAT1 → FAT2 → Data | FAT 是簇的链表 |
| **FAT 表项** | 0=空闲, ≥0x0FFFFFF8=EOF, 其他=下一簇号 | 类似链表结构的 next 指针 |
| **FAT 目录项** | 32 字节：文件名(8+3) + 属性 + 首簇 + 大小 | 大小字段 32 位 → 最大 4GB |
| **LFN** | 额外目录项存 13 个 Unicode 字符/项 | 序号倒排，字节 11=0x0F |
| **FAT 删除** | FAT 条目清 0 + 目录项首字节改 0xE5 | 数据不擦除，可恢复！ |
| **Ext Inode** | 128 字节结构，数组布局 | 除文件名外的所有文件信息 |
| **Ext 分组** | 每个 Block Group 独立管理 | 可靠性(超块备份) + 性能(局部性) |
| **多级索引** | 12 直接 + 1 间接 + 1 双间接 + 1 三间接 | 块大小 4KB → 最大约 4TB |
| **硬链接** | 多个目录项 → 同一 inode | 不创建新 inode，不能跨 FS |
| **link count** | inode 中被引用的次数 | 降至 0 才释放 |
| **符号链接** | 新建 inode，内容=路径字符串 | 可跨 FS，原文件删除后悬挂 |

## 核心思想总结

> [!important] 本章三大核心主题

**一、文件操作的系统调用机制**：从 `fopen` 到 `open`，从 `fread` 到 `read`，理解用户态库与内核态系统调用的分层协作。文件描述符是贯穿始终的核心抽象——它只是一个数组下标，却承载了进程与文件之间所有交互的桥梁。

**二、FAT32 的链表式管理**：FAT 文件系统用文件分配表作为簇的"next 指针"，简单直观但有先天局限——4 GB 文件上限、无权限控制、删除不擦数据。理解 FAT 就是理解"最简单的文件系统怎么工作"。

**三、Ext 系列的索引式管理**：从 FAT 的链表进化到 inode 的数组索引，用多级间接指针突破文件大小限制，用块组结构同时保证可靠性和性能。硬链接和符号链接的区分体现了 Unix 哲学中"一切皆文件"的设计理念。
