## 1. I/O 系统概述

### 1.1 为什么 I/O 管理重要？

I/O 管理是操作系统设计和运行的**主要组成部分**，原因如下：

- I/O 设备种类极其繁多，差异巨大（键盘 vs. 显卡 vs. 磁盘）
- 不同设备的控制方法各不相同，需要统一抽象
- I/O 是计算机性能的主要瓶颈之一
- 新型设备（NVMe、GPU、加速器）不断涌现

### 1.2 I/O 设备分类

按功能分三大类：

|类别|举例|
|---|---|
|**存储设备**|磁盘、SSD、U盘|
|**传输设备**|网卡、调制解调器|
|**人机交互设备**|键盘、鼠标、显示器、打印机|

### 1.3 I/O 系统的层次结构

```
用户进程 (User Process)
    ↕  系统调用 (System Call)
内核 I/O 子系统 (Kernel I/O Subsystem)
    ↕
设备驱动程序 (Device Driver)  ← 每种设备一个，封装细节
    ↕
设备控制器 (Device Controller / Hardware)
    ↕
物理设备 (Physical Device)
```

**设备驱动程序**是关键：它封装了设备的所有细节，向上层（I/O子系统）提供**统一的设备访问接口**。这样内核不需要了解每种设备的细节，大大降低了复杂度。

## 2. I/O 硬件基础

### 2.1 三个核心概念

**端口（Port）**：设备的连接点，即设备的"地址"。CPU 通过端口号或内存地址与设备通信。

**总线（Bus）**：一组线路加上严格定义的通信协议。是多个设备共享的传输通道。常见总线：

|总线|用途|速度|
|---|---|---|
|PCIe（PCI Express）|连接高速设备（GPU、SSD、网卡）|极高（PCIe 3×16 达 16 GB/s）|
|扩展总线（Expansion Bus）|连接慢速设备（USB等）|较低|
|SAS|串行连接SCSI，企业级磁盘接口|中等|

**设备控制器（Device Controller）**：操作端口、总线、设备的电子设备（芯片/电路板），是 CPU 和 I/O 设备之间的桥梁。

### 2.2 主板 I/O 结构（北桥/南桥）

传统 PC 主板将控制器分为两级：

**北桥（Memory Controller Hub, MCH）**：连接高速设备

- CPU ↔ 内存（高速，3.2 GB/s）
- CPU ↔ AGP/PCI-Express（显卡，1 GB/s）

**南桥（I/O Controller Hub, ICH）**：连接低速设备

- ATA/IDE 硬盘（266 MB/s）
- PCI 总线（133 MB/s）
- USB、串口、并口
- DMA 控制器、中断控制器

> [!tip] 现代架构变化 现代 CPU 已将内存控制器集成进 CPU 芯片内部，北桥几乎消失。PCIe 总线也直接连接 CPU。南桥功能由 PCH（Platform Controller Hub）取代。

### 2.3 设备寄存器

每个设备控制器内部有若干**寄存器**，设备驱动程序通过读写这些寄存器来控制设备：

|寄存器类型|功能|
|---|---|
|**数据输入寄存器**|CPU 从设备读取数据|
|**数据输出寄存器**|CPU 向设备写入数据|
|**状态寄存器**|反映设备当前状态（忙/就绪/错误）|
|**控制寄存器**|CPU 向设备发送命令|

寄存器通常 1~4 字节，或 FIFO 缓冲区（先进先出队列）。

## 3. CPU 与设备的通信方式

### 3.1 I/O 指令（Port-Mapped I/O）

CPU 使用**专用 I/O 指令**通过端口号访问设备寄存器。

```asm
; x86 汇编：向端口 0x21 写入 AL 寄存器的值
out 0x21, AL

; 从端口读取
in AL, 0x21
```

这种方式需要专用指令，端口地址空间与内存地址空间**分离**。

### 3.2 内存映射 I/O（Memory-Mapped I/O, MMIO）

**核心思想**：把设备的寄存器/存储**映射到物理内存地址空间**中。CPU 通过普通的 load/store 指令操作这段内存地址，实际上就是在操作设备。

```c
// 设备寄存器被映射到地址 0x8f008020
volatile uint32_t *device_reg = (uint32_t *)0x8f008020;
*device_reg = 0x01;  // 相当于向设备发命令
uint32_t status = *device_reg;  // 读设备状态
```

**映射方式**：MMU 设置映射关系，或硬件跳线/启动时程序设置。

> [!warning] 易错点：MMIO 与普通内存的区别 映射到设备的地址不能被 CPU 缓存（必须标记为不可缓存），否则 CPU 读的是缓存中的旧值而不是设备实时状态。这是驱动开发中常见的 bug 来源，所以常用 `volatile` 关键字。

**PC 标准 I/O 端口地址（部分）**：

|地址范围（十六进制）|设备|
|---|---|
|000–00F|DMA 控制器|
|020–021|中断控制器|
|040–043|定时器|
|320–32F|硬盘控制器|
|3D0–3DF|图形控制器|
|3F8–3FF|串口（主）|

## 4. I/O 技术：轮询、中断、DMA

I/O 技术按是否使用中断、数据如何传输分为四类：

| 无中断             | 使用中断               |          |
| --------------- | ------------------ | -------- |
| **I/O经由CPU到内存** | 轮询（Programmed I/O） | 中断驱动 I/O |
| **I/O直接到内存**    | —                  | DMA      |

### 4.1 轮询（Polling / Programmed I/O）

**核心思想**：CPU 主动、反复检查设备状态，直到设备就绪。

**工作流程**（以输出一个字节为例）：

1. CPU 循环读取状态寄存器的**忙位（busy bit）**，直到该位为 0（设备空闲）
2. 主机设置读/写位，若写入则把数据写入**数据输出寄存器**
3. 主机设置**命令就绪位**，通知控制器有命令
4. 控制器看到命令就绪位，设置**忙位**（表示正在处理）
5. 控制器从数据输出寄存器取数据，执行 I/O 操作
6. 操作完成，控制器清除忙位、错误位、命令就绪位

**步骤1是关键**：CPU 在这里做**忙等待（Busy Wait）**，一直空转检查，不做其他事。

轮询可在 3 条指令内完成一次检查（读状态、逻辑与提取状态位、条件跳转）。

**优缺点分析**：

|场景|效果|
|---|---|
|设备速度快（如 GPU 寄存器）|**合理**，轮询几次就完成，开销小|
|设备速度慢（如磁盘）|**效率极低**，CPU 大量时间空转等待|
|设备偶发响应|若错过时机，数据可能丢失或被覆盖|

> [!warning] 易错点：轮询不等于"傻等"，它在特定场景（高速设备、实时性要求极高）下优于中断 因为中断有上下文切换开销，如果设备非常快（微秒级），上下文切换的开销反而比轮询大。

---

### 4.2 中断驱动 I/O（Interrupt-Driven I/O）

**核心思想**：CPU 发出 I/O 请求后去做其他事，设备完成时**主动通知** CPU（产生中断信号）。

**工作流程**：

1. 设备驱动程序初始化 I/O 请求，向 I/O 控制器发出命令
2. I/O 控制器开始执行 I/O 操作；CPU **不等待**，继续执行其他进程
3. I/O 操作完成（或出错），控制器产生**中断请求**（IRQ）
4. CPU 执行完当前指令后检查中断请求，发现中断
5. CPU 将当前上下文（寄存器状态）保存（**上下文切换**）
6. 根据中断号查**中断向量表**，找到对应的**中断服务例程（ISR）**
7. 中断服务例程处理中断（读取结果，通知等待的进程）
8. 恢复被打断进程的执行

**中断向量（Interrupt Vector）**：

中断向量是一张表，每个中断号对应一个处理函数的地址。CPU 收到中断后用中断号作索引查这张表，跳到对应处理函数。

Intel x86 部分中断向量：

|向量号|描述|
|---|---|
|0|除零错误|
|1|调试异常|
|3|断点|
|8|双重错误|
|13|通用保护错误|
|**14**|**缺页（Page Fault）**|
|16|浮点错误|
|**32–255**|**可屏蔽中断（设备中断）**|

**两条中断线**：

- **非屏蔽中断（NMI）**：不可被屏蔽，用于严重错误（硬件故障等）
- **可屏蔽中断（Maskable Interrupt）**：可通过指令屏蔽，用于普通设备

**中断链（Interrupt Chain）**：多个设备共享同一中断号时，形成链表，逐个检查哪个设备发出了中断。

**中断的其他用途**（重要！）：

中断机制不仅用于 I/O，还广泛用于：

- **异常处理**：除零、非法指令（由硬件触发）
- **缺页异常（Page Fault）**：访问不在内存的页时触发
- **系统调用（System Call）**：通过软件中断（Trap/INT指令）进入内核
- **多 CPU 系统**：可并发处理中断

> [!important] 中断 vs 轮询的选择原则
> 
> - 设备**慢且不频繁**触发（如键盘、磁盘）→ **中断更好**，CPU 可做其他事
> - 设备**极快且频繁**（如高速网络、NVMe）→ **轮询可能更好**，避免中断开销
> - 现代高性能网络驱动常混合使用：先轮询一段时间，超时未完成再转中断

### 4.3 DMA（直接内存访问）

**核心思想**：对于大块数据传输，**绕过 CPU**，让专用的 DMA 控制器直接在 I/O 设备和内存之间传输数据，CPU 只负责发出命令和接收完成通知。

**为什么需要 DMA？**

如果用轮询或中断，每传输一个字节 CPU 都要介入一次。传输 1MB 数据就要介入 100 万次，CPU 几乎被 I/O 占满。DMA 让整块传输一次性完成，CPU 只参与开始和结束。

**DMA 工作流程**（以磁盘读数据为例）：

```
1. 设备驱动收到"读磁盘数据到内存地址X"的请求
   ↓
2. 设备驱动控制磁盘控制器，从磁盘读取数据
   ↓
3. 磁盘控制器初始化 DMA 传送
   （OS 将命令块写入内存：源地址、目标地址X、读/写模式、字节数）
   ↓
4. 磁盘控制器传送数据到 DMA 控制器
   ↓
5. DMA 控制器传送 C 字节数据到内存地址 X
   （DMA 控制器"抢占"总线：Bus Mastering）
   ↓
6. DMA 完成后，产生中断请求，通知 CPU 传送完成
```

**周期窃取（Cycle Stealing）**：DMA 控制器在传输数据时需要占用内存总线，会短暂"偷走" CPU 的总线使用权。但因为 DMA 远比字节逐一传输高效，整体上 CPU 反而更自由。

**DVMA（Direct Virtual Memory Access）**：DMA 的增强版，能识别虚拟地址，自动处理地址映射，效率更高。

> [!warning] 易错点：DMA 完成后仍需中断 DMA 传输数据的过程中 CPU 是自由的，**但 DMA 完成时需要发送一次中断**来通知 CPU。所以 DMA 并非完全不用中断，只是中断次数从"每字节一次"减少为"整块传输一次"。

## 5. 应用程序 I/O 接口

### 5.1 分层抽象的意义

I/O 子系统通过**设备驱动程序层**隐藏了不同控制器之间的差异。上层应用调用统一的系统调用接口（`read()`, `write()`, `ioctl()`），不需要关心设备是 SCSI、SATA 还是 USB。

```
应用程序 → read("/dev/sda") 
内核 I/O 子系统 → 统一接口
设备驱动程序 → SCSI驱动 / SATA驱动 / USB驱动...
设备控制器 → 硬件
```

### 5.2 设备分类（OS 视角）

**块设备（Block Device）**：

- 以**固定大小的块**传输数据（如磁盘、SSD）
- 支持：`read`、`write`、`seek`（随机访问）
- 访问方式：Raw I/O（原始块）、Direct I/O（绕过缓存）、文件系统访问、内存映射文件
- 使用 DMA 传输

**字符设备（Character Device）**：

- 以**字节流**传输，无块结构（如键盘、鼠标、串口）
- 支持：`get()`、`put()`
- 不可随机访问，顺序读写

**网络设备（Network Device）**：

- 既不完全像块设备也不完全像字符设备，有自己的接口
- Unix/Linux 使用 **Socket** 接口：`connect()`, `accept()`, `send()`, `receive()`
- `select()` 系统调用用于多路复用：同时监听多个 socket，哪个有数据就处理哪个

**时钟/定时器**：

- 提供当前时间、经过时间、计时器
- 普通分辨率约 1/60 秒，高精度定时器分辨率更高
- 用于进程调度的时间片、定期中断
- Unix 通过 `ioctl()` 访问

### 5.3 设备特性总结

|特性|变体|示例|
|---|---|---|
|数据传输模式|字符 / 块|终端 / 磁盘|
|访问方法|顺序 / 随机|调制解调器 / CD-ROM|
|传输调度|同步 / 异步|磁带 / 键盘|
|共享方式|专用 / 共享|磁带 / 键盘|
|I/O 方向|只读 / 只写 / 读写|CD-ROM / 图形控制器 / 磁盘|

### 5.4 Linux 设备编号

UNIX/Linux 用 **主设备号（major）+ 次设备号（minor）** 标识设备：

```bash
$ ls -l /dev/sda*
brw-rw---- 1 root disk 8, 0 /dev/sda    # 主8，次0（整盘）
brw-rw---- 1 root disk 8, 1 /dev/sda1   # 主8，次1（第1分区）
```

主设备号标识**设备类型**（8 = SCSI 磁盘），次设备号标识**具体实例**（0=整盘, 1=第1分区…）。

## 6. I/O 的阻塞模型

### 6.1 三种 I/O 模型

**阻塞 I/O（Blocking I/O）**：进程调用 I/O 后**挂起等待**，直到 I/O 完成才返回。

```
进程 → read() → [阻塞挂起] → I/O完成 → 继续执行
```

- 优点：简单易用，顺序思维
- 缺点：等待期间 CPU 资源浪费（进程无法做其他事）
- 适用：普通程序、I/O 不频繁的场景

**非阻塞 I/O（Nonblocking I/O）**：调用立即返回，返回当前已有的数据（可能是 0 字节）。

```
进程 → read() → 立即返回（有多少数据返回多少） → 进程继续执行其他事 → 再次检查
```

- 通过 `select()` / `poll()` / `epoll()` 检查数据是否就绪
- 适用：UI 程序、网络服务器（处理多路连接）
- 实现：多线程，一个线程非阻塞轮询 I/O 状态

**异步 I/O（Asynchronous I/O）**：进程发出 I/O 请求后**立即返回继续执行**，I/O 完成后操作系统通过**信号或回调**通知进程。

```
进程 → aio_read() → 立即返回，继续运行 → [I/O子系统信号通知] → 处理完成
```

- 优点：最高并发性，充分利用 CPU
- 缺点：编程复杂，需要处理回调/信号
- 适用：高性能服务器、数据库

> [!important] 易错点：非阻塞 ≠ 异步
> 
> - **非阻塞**：调用立即返回，但数据未必准备好（可能返回0），进程需要**主动轮询**检查
> - **异步**：调用立即返回，进程完全不管，等系统**主动通知**
> - 异步的并发性更高，但编程难度也更大

### 6.2 两种 I/O 方式图示

```
(a) 同步阻塞 I/O            (b) 异步 I/O
用户进程  ——等待中——→        用户进程  →继续运行→ [通知] →
                                         ↑
内核  →device driver→           内核  → driver → [硬件] → 完成 → 通知
      →interrupt handler→
      →硬件数据传输→
```

### 6.3 向量 I/O（Vectored I/O / Scatter-Gather）

一次系统调用完成**多个缓冲区**的 I/O：

```c
// Unix readv()：将数据读入多个分散的缓冲区
struct iovec iov[3];
iov[0].iov_base = buf1;  iov[0].iov_len = 100;
iov[1].iov_base = buf2;  iov[1].iov_len = 200;
iov[2].iov_base = buf3;  iov[2].iov_len = 300;
readv(fd, iov, 3);  // 一次系统调用，读入三块
```

优点：减少系统调用次数（减少上下文切换），某些版本保证原子性（防止多线程数据竞争）。

## 7. 内核 I/O 子系统

内核 I/O 子系统是 OS 提供给应用程序的 I/O 服务集合，包括以下功能：

### 7.1 I/O 调度（I/O Scheduling）

内核为每个设备维护一个 I/O 请求队列，对队列中的请求进行**排序/调度**以提高效率（类似磁盘调度，参考 CH11）。

- 部分 OS 追求公平性
- 部分实现 QoS（服务质量保证）

### 7.2 缓冲（Buffering）

**缓冲**：在数据从一个地方传到另一个地方的过程中，先在内存里暂存数据。

**三个目的**：

1. **速度不匹配（Speed Mismatch）**：发送方快，接收方慢（或反之）。比如网络接收数据很快，但磁盘写入慢，需要缓冲队列暂存。
    
2. **传输大小不匹配（Transfer Size Mismatch）**：不同设备的传输单位不同。比如网络以包（packet）传输，磁盘以块（block）传输，中间需要缓冲来适配大小。
    
3. **维护"复制语义"（Copy Semantics）**：用户调用 `write(buf, size)` 后，内核把 buf 的内容复制到内核缓冲区，这样用户可以立即修改 buf 而不影响正在进行的写操作。
    

**双缓冲（Double Buffering）**：维护两份缓冲区，一个在填充/被处理，另一个在被使用，交替切换，提高流水线效率。

### 7.3 缓存（Caching）

**缓存**：用更快的存储设备保存数据的**副本**，以便快速访问。

- 缓存永远只是副本，原始数据在慢速设备上
- 是提高 I/O 性能的关键手段
- 常与缓冲结合使用（如磁盘读缓冲兼做读缓存）

> [!warning] 易错点：缓冲 vs 缓存
> 
> - **缓冲（Buffer）**：临时存放正在传输中的数据，解决速度/大小不匹配问题，传输完成后缓冲内容就无用了
> - **缓存（Cache）**：保存已访问数据的副本，为了**下次更快访问**，重复利用价值高
> - 有时同一块内存区域同时起两种作用（如文件系统的 page cache）

### 7.4 假脱机（Spooling）

**假脱机**（Simultaneous Peripheral Operations On-Line）：为**独占设备**（一次只能服务一个请求的设备）维护一个输出队列，多个进程的输出先写到队列里，由后台进程逐一发送给设备。

典型例子——**打印机**：

- 多个进程都想打印，但打印机一次只能打一个
- 每个进程把打印内容写到假脱机队列（磁盘上的临时文件）
- 后台打印守护进程（print daemon）逐一取出并发送给打印机
- 进程调用"打印"后立即返回，不需要等待实际打印完成

### 7.5 设备预留（Device Reservation）

为需要**独占访问**设备的应用提供排他性访问：

- 通过系统调用申请（allocation）和释放（de-allocation）
- **注意死锁风险**：多个进程互相等待对方释放设备

### 7.6 错误处理

OS 可以从以下错误中恢复：

- 磁盘读错误（尝试重试）
- 设备暂时不可用
- 瞬时写失败

高级系统（如 Solaris FMA、AIX）会跟踪错误频率，若设备错误越来越频繁，主动停止使用该设备（预防性维护）。

### 7.7 设备状态表

内核维护一张**设备状态表**，每个设备有一个条目，记录设备状态（idle/busy）和等待队列：

```
设备      状态    请求队列
键盘      idle    （空）
激光打印机 busy   → [请求: 地址38546, 长度1372]
鼠标      idle    （空）
磁盘单元1  idle   （空）
磁盘单元2  busy   → [读xxx, 地址43046] → [写yyy, 地址03458]
```

### 7.8 内核数据结构

内核维护复杂的数据结构跟踪 I/O 状态：

- 打开的文件表（open file table）
- 网络连接信息
- 字符设备状态
- 缓冲区信息
- "脏"块（已修改但未写回磁盘的缓冲块）

有些使用面向对象的方法和 **消息传递** 来实现（主要是微内核）

**Unix I/O 结构**（文件描述符到设备的映射链）：

```
用户进程内存
  文件描述符(fd) → 进程打开文件表
                        ↓
内核内存（系统全局打开文件表）
  文件系统记录 {
    inode指针
    read/write函数指针
    select函数指针
    ioctl函数指针
    close函数指针
  }
  → active-inode表
  
  网络(socket)记录 {
    网络信息指针
    read/write函数指针
    ...
  }
  → network-information表
```

这种设计使得文件、设备、网络套接字对上层来说都是统一的**文件描述符**，`read()`/`write()` 对所有类型都适用。

## 8. I/O 保护

**问题**：用户进程可能通过非法 I/O 指令破坏系统（比如直接操作磁盘控制器、修改网卡寄存器）。

**解决方案**：

1. **所有 I/O 指令定义为特权指令**：用户态无法直接执行，必须通过系统调用
2. **I/O 必须通过系统调用进行**：用户调用 `read()` → trap 进入内核态 → 内核执行实际 I/O → 返回结果
3. **内存映射 I/O 的地址和 I/O 端口地址也需要保护**：防止用户态进程直接映射访问

**利用系统调用执行 I/O 的过程**：

```
用户态:  read() 系统调用 (int 0x80 / syscall 指令)
           ↓  ① trap to kernel
内核态:  系统调用分发表 → 找到 sys_read
           ↓  ② 执行读操作（访问磁盘/网络/设备）
         完成 I/O
           ↓  ③ return to calling thread
用户态:  read() 返回，继续执行
```

## 9. I/O 性能

### 9.1 I/O 性能开销来源

I/O 是影响系统整体性能的主要因素，开销来自：

1. **CPU 执行开销**：运行设备驱动程序和内核 I/O 代码消耗 CPU 时间
2. **上下文切换**：中断导致的上下文保存/恢复（每次中断需要保存几十个寄存器）
3. **数据复制**：数据从设备→内核缓冲区→用户空间，可能经过多次复制
4. **网络 I/O**：网络流量密集时，协议栈处理消耗大量资源

### 9.2 性能改进方法

|优化方法|原理|
|---|---|
|**减少上下文切换**|合并 I/O 操作，减少中断次数|
|**减少数据复制**|零拷贝（Zero-Copy）技术：数据直接从内核缓冲到网卡，不经用户空间|
|**用大型传输减少中断**|一次传更多数据，减少"每字节一中断"的开销|
|**用智能控制器轮询**|高速设备（NVMe）用轮询比中断更快|
|**使用 DMA**|大块传输绕过 CPU|
|**使用更智能的硬件**|将协议处理下推到硬件（如 TCP Offload Engine）|
|**平衡各组件**|CPU、内存、总线、I/O 性能要匹配，短板决定整体|
|**用户进程移到内核线程**|减少用户态/内核态切换|

### 9.3 计算机内部通信中的 I/O 开销

以发送一个键盘字符到网络为例，发送端需要：

- 键盘中断 → 状态保存 → 中断处理 → 设备驱动 → **上下文切换** → 用户进程 → 系统调用 → 网络驱动 → 发送

接收端需要：

- 网络中断 → 状态保存 → 中断处理 → 设备驱动 → **上下文切换** → 网络守护进程 → 用户进程

每次 I/O 可能涉及多次上下文切换（`state save`），这是高 I/O 负载下系统性能下降的主要原因。

## 10. 流式 I/O（STREAMS）

STREAMS 是 Unix System V 引入的一种**模块化 I/O 框架**，提供用户进程与设备之间的**全双工通信通道**。

**结构**（从上到下）：

```
用户进程
    ↕
流头（Stream Head）    ← 与用户进程交互的接口
  [读队列] [写队列]
    ↕
STREAMS 模块（可有多个）
  [读队列] [写队列]
    ↕
驱动程序端（Driver End）  ← 与设备交互的接口
  [读队列] [写队列]
    ↕
物理设备
```

**关键特性**：

- 每个模块有独立的**读队列和写队列**
- 模块之间通过**消息传递**通信（而非共享内存）
- 支持**流量控制**：可以指示模块繁忙或空闲
- 内部**异步**，用户进程与流头通信**同步**

## 11. 电源管理

虽然不是严格意义上的 I/O 领域，但电源管理与 I/O 密切相关：

### 11.1 OS 的角色

- 云计算：在服务器间迁移虚拟机，关闭空闲服务器节省电力
- 移动计算：电源管理是**第一类**操作系统功能（电量是稀缺资源）

### 11.2 Android 电源管理机制

**组件级电源管理**：

- 维护设备树（Device Tree），描述设备间的依赖关系
- 设备驱动程序跟踪每个设备是否在使用
- 未使用的设备 → 关闭
- 设备树某分支上所有设备都未使用 → 关闭整个分支

**唤醒锁（Wake Lock）**：

- 类似互斥锁，持有唤醒锁时阻止设备进入睡眠
- 用于需要保持唤醒的任务（如音乐播放、GPS导航）

**电源崩溃（Power Collapse）**：深度睡眠状态，极低功耗，只保留响应外部刺激（按键、来电）的最小功能。

### 11.3 ACPI

现代系统使用 **ACPI（Advanced Configuration and Power Interface）** 固件，提供：

- 设备发现（枚举系统中的硬件）
- 设备管理
- 错误报告
- 电源管理

ACPI 代码作为内核调用的例程运行，是硬件和 OS 电源管理协作的标准接口。

## 12. 例题精选

> [!example] 例题1：轮询 vs 中断的比较分析（综合）
> 
> **题目**：某系统有两种 I/O 设备：
> 
> - 设备A：鼠标，每秒产生约 100 次事件，每次处理需要 1μs
> - 设备B：网卡，每秒处理 10 万个包，每包处理需要 1μs
> 
> (1) 对设备A，采用轮询还是中断更合适？说明理由。 (2) 对设备B，是否有更好的方案？ (3) 轮询时，CPU 的利用率如何（假设轮询间隔为 1ms，每次轮询需要 0.1μs）？
> 
> **解**：
> 
> (1) **设备A（鼠标）→ 中断更合适**
> 
> 鼠标每秒 100 次事件，间隔约 10ms。若用轮询，CPU 需要每隔很短时间就检查一次，大量时间在"设备没有新事件"时空转。用中断，有鼠标移动/点击时才打扰 CPU，其余时间 CPU 可做其他事。
> 
> (2) **设备B（高速网卡）→ 轮询（或混合模式）可能更好**
> 
> 每秒 10 万包 = 每 10μs 一个包。若用中断，每秒 10 万次中断，每次中断都有上下文切换开销（假设 1~2μs），光是中断开销就可能占用大量 CPU。 现代高性能网络驱动（如 Linux NAPI）采用**混合模式**：第一个包到来时触发中断，进入中断处理后切换为轮询模式（快速处理后续包），一段时间内无包再关闭轮询，恢复中断。
> 
> (3) **轮询时 CPU 利用率分析**：
> 
> 每 1ms 轮询一次，每次 0.1μs：
> 
> - 1秒内轮询次数 = 1000ms / 1ms = 1000 次
> - 轮询消耗 CPU 时间 = 1000 × 0.1μs = 0.1ms = 0.01%
> 
> 实际处理事件：100 次/秒 × 1μs = 0.1ms = 0.01%
> 
> 总 I/O 相关 CPU 占用 ≈ 0.02%，轮询开销极小。 但如果轮询间隔太短（如每 10μs 一次），轮询本身就占 1%，并且可能错过两次轮询之间的事件。

> [!example] 例题2：DMA 传输过程详解
> 
> **题目**：进程 P 调用 `read(fd, buf, 4096)` 读取磁盘上的 4KB 数据。系统使用 DMA 方式。
> 
> (1) 详细描述从系统调用到数据到达用户缓冲区的完整过程（至少7步）。 (2) 在此过程中，哪些步骤 CPU 是空闲的（可以执行其他进程）？ (3) 如果改用轮询方式，最大的区别是什么？ (4) DMA 传输中"周期窃取"指什么？对系统性能有何影响？
> 
> **解**：
> 
> (1) **完整过程**：
> 
> ① 进程 P 调用 `read()`，陷入（trap）内核态 ② 内核 I/O 子系统检查是否有缓存命中（page cache），若无则继续 ③ 内核将 DMA 命令块写入内存（包含：磁盘 LBA 地址、内核缓冲区目标地址、传输字节数=4096、读模式） ④ 内核通知磁盘控制器：将 DMA 命令块地址告诉 DMA 控制器 ⑤ 进程 P **被阻塞**，调度器切换到其他进程（CPU 自由） ⑥ 磁盘控制器开始读取数据，通过 PCI 总线传给 DMA 控制器 ⑦ DMA 控制器将数据写入内核缓冲区（内存地址X），每次若干字节，**占用总线（周期窃取）** ⑧ 4096 字节全部传输完毕，DMA 控制器向 CPU 发**中断** ⑨ CPU 处理中断：数据已在内核缓冲区，将其复制到用户缓冲区 `buf` ⑩ 唤醒进程 P，`read()` 返回 4096
> 
> (2) **CPU 空闲阶段**：步骤⑤～⑧（即DMA 传输数据的整个过程中），CPU 可以执行其他进程。这正是 DMA 的核心价值。
> 
> (3) **轮询方式最大区别**：
> 
> 轮询方式下，CPU 在步骤⑤不会切换到其他进程，而是循环读取磁盘控制器的状态寄存器，等待就绪信号，然后**一字节一字节（或一次几字节）地读取数据**并写入内存。CPU 全程被占用，无法做其他事，且中间涉及大量 I/O 指令执行。
> 
> (4) **周期窃取**：
> 
> DMA 控制器传输数据时需要使用内存总线（系统总线）。由于 CPU 和 DMA 共用同一内存总线，DMA 在传输数据的某些时钟周期内会"占据"总线，此时 CPU 不能访问内存（即 CPU 的内存访问被延迟）——这就是"窃取"了 CPU 的总线周期。
> 
> 对性能的影响：CPU 访问内存的延迟略有增加（某些内存访问需要等待 DMA 让出总线）。但总体上，DMA 仍然比 CPU 直接传输高效得多，因为 CPU 可以利用被"窃取"之外的时间做有用的工作，而不是像轮询那样全程空转。

> [!example] 例题3：阻塞/非阻塞/异步 I/O 辨析
> 
> **题目**：一个 Web 服务器需要同时处理 1000 个客户端的请求，每个请求需要从磁盘读取文件。
> 
> (1) 如果使用阻塞 I/O，该如何实现？有何缺点？ (2) 如果使用非阻塞 I/O + `select()`，基本逻辑是什么？ (3) 异步 I/O 方案有何优势？ (4) 下列操作各属于哪种 I/O 模型？ a. `socket` 设置为阻塞模式，调用 `read()` b. 调用 `aio_read()`，然后继续处理其他请求，之后收到完成信号 c. 设置 `O_NONBLOCK`，调用 `read()`，若返回 EAGAIN 则等一会儿再试
> 
> **解**：
> 
> (1) **阻塞 I/O 实现**：每个客户端连接分配一个线程，线程调用阻塞 `read()` 等待磁盘数据。
> 
> 缺点：1000 个客户端需要 1000 个线程，每个线程占用栈空间（通常 2~8MB），总内存消耗 2~8 GB；线程切换开销大；大多数线程在等待 I/O，CPU 利用率低。
> 
> (2) **非阻塞 I/O + select() 逻辑**：
> 
> ```python
> # 伪代码
> fds = [所有连接的socket列表]
> while True:
>     ready_fds = select(fds, timeout=100ms)  # 等待任意fd就绪
>     for fd in ready_fds:
>         data = read(fd, ...)  # 此时read肯定有数据，不会阻塞
>         process(data)
> ```
> 
> 单线程/少量线程管理所有连接，`select()` 阻塞等待"任意一个连接有数据"，哪个有数据就处理哪个。
> 
> (3) **异步 I/O 优势**：
> 
> 调用 `aio_read()` 后**立即返回**，进程继续处理其他请求。磁盘读取在后台进行，完成时内核发信号通知进程。全程没有等待，CPU 利用率最高。适合 I/O 密集型高并发场景（如 Nginx 的 AIO 模式）。
> 
> (4) 分类：
> 
> - **a**：**阻塞 I/O**（调用后挂起等待）
> - **b**：**异步 I/O**（立即返回，事后通知）
> - **c**：**非阻塞 I/O**（立即返回，但主动轮询重试）

> [!example] 例题4：缓冲与缓存的综合分析
> 
> **题目**：Linux 的 page cache（页缓存）同时起到缓冲和缓存的作用。
> 
> (1) 解释 page cache 如何作为"缓存"使用。 (2) 解释 page cache 如何作为"缓冲"使用（以写操作为例）。 (3) 什么是"脏页"（dirty page）？何时会被写回磁盘？ (4) 如果进程 A 写文件后立即崩溃，数据还在 page cache 中未写回磁盘，数据会丢失吗？如何保证数据持久性？
> 
> **解**：
> 
> (1) **page cache 作为缓存**：
> 
> 当进程读文件时，OS 将文件数据读入 page cache（内存中）。下次访问同一文件时，直接从 page cache 返回，不需要再读磁盘。因为内存访问比磁盘快约 10 万倍，这大大加速了重复读取。
> 
> (2) **page cache 作为缓冲（写操作）**：
> 
> 进程调用 `write()` 时，数据先写入 page cache（标记为"脏"），`write()` 立即返回，此时数据**尚未到达磁盘**。OS 在后台异步地将脏页写回磁盘（write-back 策略）。
> 
> 这就是"缓冲"：调和了进程（快速写内存）和磁盘（慢速写磁盘）之间的速度差异。
> 
> (3) **脏页（Dirty Page）**：
> 
> page cache 中已被修改但尚未写回磁盘的页。OS 会在以下时机将脏页写回（flush）：
> 
> - 定期（如 pdflush/writeback 内核线程，默认30秒）
> - 内存压力大时（需要回收内存，必须先写回脏页）
> - 进程调用 `fsync()` / `fdatasync()` 强制刷盘
> - 文件关闭时（如果配置了）
> 
> (4) **数据丢失风险与持久性保证**：
> 
> 如果只是进程崩溃（不是断电/内核崩溃），脏页仍然在内存中，OS 会继续将其写回磁盘，**数据不会丢失**。
> 
> 但如果断电或内核崩溃，脏页中的数据**会丢失**。
> 
> 保证持久性的方法：
> 
> - `fsync(fd)`：强制将指定文件的脏页全部写回磁盘，写完才返回。数据库（如 PostgreSQL、MySQL）在提交事务时必须调用 `fsync()`
> - 日志文件系统（如 ext4、XFS）：先写操作日志（journal），保证崩溃后可以重放日志恢复一致性
> - `O_DIRECT`：绕过 page cache，直接写磁盘，性能低但无延迟丢失风险

> [!example] 例题5：中断向量与中断处理综合题
> 
> **题目**：Intel x86 系统中，中断向量号 14 对应缺页异常（Page Fault）。
> 
> (1) 中断向量表是什么？它存储在哪里？谁负责初始化它？ (2) 当进程访问一个不在内存中的页时，描述从产生 Page Fault 到最终恢复进程执行的完整过程。 (3) Page Fault 的处理属于"中断"还是"异常"？有什么区别？ (4) 若 Page Fault 处理程序发现对应页不在磁盘的 swap 区（非法地址），应如何处理？
> 
> **解**：
> 
> (1) **中断向量表（IDT, Interrupt Descriptor Table）**：
> 
> 一个数组，每个元素是一个"门描述符"，包含：中断处理函数的地址（代码段+偏移）、权限级别等。索引即中断向量号（0~255）。
> 
> 存储位置：物理内存中由 OS 分配，**IDTR 寄存器**指向其基地址。
> 
> 初始化：OS 内核在启动时（boot阶段）初始化，写入每个中断号对应的处理函数地址。
> 
> (2) **Page Fault 完整处理过程**：
> 
> ① CPU 执行指令，内存访问 → MMU 查页表 → 发现页不在内存（Present位=0） ② **硬件**自动保存当前 CPU 状态（EIP、CS、EFLAGS、SS、ESP），产生中断号 14 ③ CPU 查 IDT，跳转到 Page Fault 处理程序（内核代码） ④ 处理程序分析 CR2 寄存器（存放引发缺页的虚拟地址） ⑤ 检查该地址是否在进程的合法虚拟地址空间内（查 VMA 链表） ⑥ 若合法：在物理内存中分配一个页框，从磁盘 swap 区读入数据（发起 I/O） ⑦ 进程被阻塞等待 I/O 完成，CPU 调度其他进程 ⑧ 磁盘 I/O 完成（DMA + 中断），数据已在内存 ⑨ 更新进程页表，将虚拟页映射到新物理页框，设置 Present 位 ⑩ 唤醒进程，**从产生缺页的那条指令重新执行**（不是下一条）
> 
> (3) **中断 vs 异常**：
> 
> - **中断（Interrupt）**：由**外部硬件**（设备）异步触发，与 CPU 当前执行的指令无关（如磁盘完成、键盘输入）
> - **异常（Exception）**：由 CPU **当前执行的指令**同步触发，是指令执行的直接结果（如除零、缺页、非法指令）
> 
> Page Fault 是**异常**（由访问内存的指令触发）。但两者在处理机制上类似（都查 IDT，都有处理程序）。
> 
> 系统调用（`int 0x80` 或 `syscall`）是**陷阱（Trap）**，是特殊的异常，用于主动进入内核。
> 
> (4) **非法地址的处理**：
> 
> 若虚拟地址不在进程的合法地址空间（如访问 NULL 指针、数组越界），Page Fault 处理程序向进程**发送 SIGSEGV 信号**（Segmentation Fault）。默认处理是**终止进程**并可能产生 core dump。

## 重点总结

> [!summary] 核心考点速览
> 
> **I/O 通信方式**（必考）：
> 
> - I/O 指令：专用指令访问端口
> - 内存映射 I/O：load/store 指令访问设备，注意 volatile/不可缓存
> 
> **三种 I/O 技术**（必考）：
> 
> - 轮询：CPU 忙等，适合高速设备
> - 中断：设备完成后通知 CPU，中断向量分派到处理程序
> - DMA：大块传输绕过 CPU，完成后中断，周期窃取
> 
> **阻塞模型**（必考）：
> 
> - 阻塞 = 挂起等待
> - 非阻塞 = 立即返回，主动轮询
> - 异步 = 立即返回，被动通知
> 
> **内核 I/O 子系统**（必考）：
> 
> - 缓冲：解决速度/大小不匹配，维护复制语义
> - 缓存：保存副本加速重复访问（与缓冲的区别！）
> - 假脱机：独占设备的排队方案（打印机典型例子）
> 
> **I/O 保护**：
> 
> - I/O 指令是特权指令，用户态必须通过系统调用
> 
> **性能优化**：
> 
> - 减少上下文切换、减少数据复制、用 DMA、用智能硬件
