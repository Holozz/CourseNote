## 一、本人承担的工作

本次实验中，我作为成员 3，主要负责在服务器端使用 Wireshark 抓包，对比 ACL 应用前后的报文变化，并整理 ACL 配置检查、基本与高级 ACL 的区别以及设备时间同步等实验思考题。我的工作重点是用实际报文验证访问控制效果，使实验结论能够与路由器配置和客户端测试结果相互对应。

### 1. 确认抓包位置与过滤条件

员工机 PC1 的实验地址为 `192.168.10.10/24`，服务器 PC2 的实验地址为 `10.1.1.10/24`，分别连接路由器的 GE0/0/2 和 GE0/0/3 接口。实验室 PC 同时具有管理网卡和实验网卡，因此我在 PC2 上选择地址为 `10.1.1.10` 的实验网卡进行抓包，避免将管理网络中的流量误认为实验数据。

确认抓包正常后，我按员工机的源地址和服务器的目的地址筛选报文：

```wireshark
ip.src == 192.168.10.10 && ip.dst == 10.1.1.10
```

该条件只显示员工机发往服务器的数据包，不包含反方向的应答。如果只需要查看 ICMP 请求，还可以在条件前加入 `icmp &&`。显示过滤器决定的是哪些已捕获报文出现在列表中，并不会改变网络设备的转发行为

### 2. 对比 ACL 应用前后的抓包结果

为了进行对照测试，我与负责路由器配置的成员配合，在 GE0/0/3 接口上解除 ACL 绑定，再重新应用 ACL 2000。解除绑定使用 `undo traffic-filter outbound`，重新应用使用 `traffic-filter outbound acl 2000`。两轮测试保持相同的通信地址、抓包网卡和显示过滤条件，在员工机上执行 `ping 10.1.1.10 -n 10`，并分别保存结果截图。

| 测试状态 | 员工机测试结果 | 服务器端抓包结果 |
| --- | --- | --- |
| 未应用 ACL | 能够 ping 通服务器 | 可以看到源地址为 `192.168.10.10`、目的地址为 `10.1.1.10` 的 ICMP Echo Request |
| 应用 ACL 2000 | ping 失败 | 未显示符合相同过滤条件的员工机请求报文 |

结合小组已经完成的 HTTP 访问测试，可以说明报文的转发路径：员工机请求从 GE0/0/2 进入路由器，正常情况下经 GE0/0/3 发往服务器。ACL 2000 在 GE0/0/3 的出方向拒绝源地址为 `192.168.10.10` 的报文，因此服务器端无法再观察到这些请求。它限制的是匹配源地址的流量，所以不仅 HTTP 访问受到限制，ICMP 测试也会失败

### 3. 整理实验思考题

在配置检查方面，我整理了 `display acl 2000` 和 `display current-configuration interface GigabitEthernet 0/0/3` 的用途。前者用于检查规则编号、匹配条件和动作，后者用于确认接口上存在 `traffic-filter outbound acl 2000`。仅创建 ACL 不会使接口自动开始过滤，还必须确认绑定的接口和方向正确。

对于基本与高级 ACL，我结合本次配置理解了它们的差别。实际验证使用的基本 ACL 2000 根据源 IP 匹配，规则中的通配符掩码 `0` 表示精确匹配员工机地址；它能够达到本实验要求，与其应用在通往服务器网段的出接口有关。高级 ACL 则可以同时指定源地址、目的地址、协议和端口，能够更精确地描述访问控制范围。小组报告中的 ACL 3000 是思考题给出的另一种实现方案，本次抓包结果对应的是 ACL 2000。

对于时间同步，我整理了使用统一 NTP 时间服务器、保持时区一致并检查同步状态的思路。PC 可通过 `w32tm /query /status` 检查 Windows 时间服务状态，路由器可通过 `display clock` 查看当前时间；但仅查看当前时间不能证明 NTP 已同步。本实验要求任何时间均禁止访问，因此没有使用 `time-range`，NTP 方案也属于思考题分析，没有作为已完成的实验配置记录。

## 二、遇到的困难及解决方法

### 1. 设备网络问题

将实验网线连接到作为员工机的实验室主机后，我在设置 IP 地址时遇到了地址未能正常生效的问题，界面中还出现了地址重复相关提示。随后校园网络也断开，重启后仍未恢复。当时没有确认具体原因，因此不能直接将网络中断归因于某一项设置。

为继续完成实验，我们更换了一台实验室主机。更换后，管理网络和实验网卡的地址配置均恢复正常。这次经历让我认识到，配置双网卡电脑时，应先确认正在修改哪块网卡，保留管理网络原有配置，并检查实验 IP 是否与其他设备重复。出现异常后，需要分开检查地址配置、网卡状态和路由，换机只是解决当次实验受阻的方法，并不代表已经查明原主机的故障原因。

### 2. Wireshark 抓包过滤条件问题

最初设置过滤条件时，我将目的地址字段误写为 `ip == ...`，没有得到预期的报文，无法判断是员工机请求没有到达，还是过滤条件本身有误。在未应用 ACL、员工机能够 ping 通服务器的情况下，抓包结果仍不符合预期，这提示我应先检查过滤表达式。

我先清除原有过滤条件，再用 `icmp` 观察测试报文，确认抓包网卡和通信正常。随后展开报文，核对源地址与目的地址，将目的地址条件更正为 `ip.dst == 10.1.1.10`，并结合 `ip.src == 192.168.10.10` 重新筛选，最终观察到预期的 ICMP 请求。通过这个过程，我学会了先用简单条件确认流量，再逐步增加过滤条件，避免把过滤器错误误判为网络故障。

### 3. 区分抓包为空与 ACL 生效

应用 ACL 后，Wireshark 中匹配的数据包数量为 0，但单独这一现象还不足以证明过滤成功：选错网卡、过滤条件错误或员工机没有发送请求，也可能产生相同结果。因此，我将未应用 ACL 时能够捕获请求作为对照，在重新绑定 ACL 后保持相同条件再次测试，并结合员工机 ping 失败及接口绑定配置判断过滤效果。

整理思考题时，我也注意到，现有 ACL 查看截图主要展示规则内容，接口截图展示绑定情况，没有展示具体的命中次数。因此，心得中不写未经截图核实的统计数字；如果后续需要补充命中统计，应在设备支持的查询方式下记录测试前后的计数变化。这样可以将“规则存在”“规则已应用”和“测试流量被过滤”区分开来。

## 三、体会与总结

这次实验使我对 ACL 的理解从规则语法扩展到实际数据包的转发过程。相同的规则应用在不同接口或不同方向，影响的流量范围可能不同。只有把源地址、目的地址、报文路径和接口方向联系起来，才能解释为什么本次配置能够阻止员工机访问服务器

作为负责抓包验证的成员，我体会到，对照测试比单独观察一次失败更有说服力。先确认网络和服务正常，再改变 ACL 绑定状态，并保持其余测试条件一致，才能更清楚地判断配置带来的变化。Wireshark 报文、客户端测试结果和路由器配置各自反映不同环节，结合起来才能形成较完整的验证依据

在小组协作中，我主要负责把配置效果转化为可观察的报文证据，并整理相关思考题，与其他成员的网络搭建、Web 服务部署和 ACL 配置工作相互配合。在测试前记录网卡、地址、接口和过滤条件，及时保存原始抓包文件与前后对比截图，区分已经验证的结果和仍需排查的原因，会对实验的记录和报告的填写比较重要，也有利于回顾反思
